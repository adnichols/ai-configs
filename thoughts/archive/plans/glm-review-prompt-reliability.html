Goal

Alter the review prompts and workflow instructions so GLM reviews remain thorough inside a bounded review packet, reliably stop tool use, and return an explicit verdict that can be consumed by pre-pr-implementation-review, scoped-plan-run, and plan-readiness workflows.

Decision Attention / Low-confidence Areas

  • No product decision required: browser feedback has resolved the tool-call question. The plan uses scope bounding plus elapsed-time review windows, not hard tool-call caps.
  • Locked review windows: normal scoped GLM reviews use an 8-minute target review window with the last minute reserved to return a final response; narrow adversarial or follow-up slices use a 12-minute target window with the last 90 seconds reserved to return a final response. If scope is incomplete at the checkpoint, the reviewer returns REVIEW_INCOMPLETE_RERUN_NEEDED with completed checks, remaining checks, and the exact follow-up slice.
  • Locked fan-out threshold: split GLM review when a diff has more than 12 changed files, more than 1200 diff lines, three or more product surfaces, or any adversarial rerun after escaped PR feedback. This threshold limits scope per reviewer, not how much exploration a reviewer may do inside that scope.
  • Scope of implementation: this plan changes prompt/skill doctrine only. It does not modify Pi subagent harness behavior or provider routing.

Why this plan exists

Recent HEDL review transcripts showed GLM review failures that surfaced as No output. The problematic runs were not a single-provider issue: some were provider quota failures and others were long tool-loop reviews ending without a final assistant verdict. The prompt layer can reduce the second class by making completion discipline, elapsed-time review windows, scope fan-out, incomplete-review handoff, and malformed-output handling explicit.

Authority and Inputs

  • User request: propose alterations to review prompts in pre-pr-implementation-review, scoped-plan-run, and anywhere else this could happen.
  • Observed failure family: GLM reviewer output files contain tool activity but no final verdict, causing parent workflows to see unusable No output.
  • Relevant repo guidance: active HTML plans live under thoughts/plans/*.html; reviewed plans should be registered through plan-review.

Product Intent Alignment

This is an agent-operator reliability change. The product should do the useful default: a review gate should either return a verdict or clearly report review infrastructure failure. It should not silently treat empty GLM output as a clean pass, and it should not require operators to infer from transcripts why a review failed.

UI impact: text-only. This changes reviewer-facing prompt and workflow instructions, not runtime UI.

Locked Decisions

  • Do not reduce substantive review coverage; split broad GLM reviews by surface or failure family instead.
  • Do not substitute OpenCode, OMP, or non-Pi agents for the Pi GLM review gate.
  • Empty, tool-only, or provider-error GLM output never clears a review gate.
  • GLM should be treated as a bounded adversarial specialist for broad reviews; parent workflow synthesizes slice results.

Acceptance Criteria

AC1 — Pre-PR GLM reviews are bounded and verdict-driven

pre-pr-implementation-review requires GLM to return scope checked, evidence table, findings, and one verdict. If the assigned scope is incomplete, the verdict must be REVIEW_INCOMPLETE_RERUN_NEEDED with completed checks, remaining checks, and the recommended follow-up slice. Empty/tool-only output remains infrastructure failure.

AC2 — Broad reviews fan out without losing coverage

Broad or adversarial reviews split GLM work by failure family/surface instead of asking one GLM subagent to audit everything. Parent workflows must synthesize all slice verdicts and cannot clear the gate until every required slice is complete or blocked with explicit evidence.

AC3 — Scoped-plan-run has explicit GLM packets

Runtime scoped review and adversarial escalation define the exact packet GLM receives, the stop condition it must follow, and the coverage ledger it must return when more review work remains.

AC4 — Plan-readiness GLM reviews cannot silently pass empty or incomplete output

Reviewed HTML plan and plan-reviewer execution-ready flows reject empty/tool-only GLM output, rerun once narrower, then block truthfully if still unavailable. Incomplete GLM coverage is represented either by REVIEW_INCOMPLETE_RERUN_NEEDED where the caller supports it, or by the caller’s non-ready verdict with required completed-checks, remaining-checks, and follow-up-slice fields.

AC5 — GLM agent defaults reinforce completion discipline

The GLM reviewer agent prompt globally instructs scoped review, elapsed-time review windows, final verdict requirements, and incomplete-review handoff without imposing a hard tool-call cap.

BDD Scenarios

Small diff review

Given a small pre-PR diff, when GLM runs, then it freely explores inside the named scope during the review window and returns exactly one verdict.

Incomplete review handoff

Given a GLM review reaches its time checkpoint before completing the assigned scope, when it returns, then it reports REVIEW_INCOMPLETE_RERUN_NEEDED or the caller’s equivalent non-ready verdict, lists completed and incomplete checks, and tells the parent which follow-up subagent slice to run next.

Parent orchestrator rerun

Given a reviewer returns incomplete coverage, when the parent orchestrator receives the result, then it launches the recommended follow-up slice, appends the new result to the coverage ledger, and does not clear the gate until all required slices are complete or explicitly blocked.

Broad diff review

Given a broad PR touching multiple surfaces, when the pre-PR gate runs, then GLM review is split into focused slices and the parent synthesizes the slice verdicts.

Empty GLM output

Given a GLM transcript ends in tool output or provider error, when the workflow interprets results, then it records review infrastructure failure, reruns once with a narrower slice, and records a tooling blocker if the narrowed rerun is still unusable.

Escaped PR feedback

Given PR feedback exposes a missed failure family, when adversarial escalation runs, then GLM gets narrow slices around the escaped pattern, sibling callsites, inverse boundary, and tests that should have caught it.
