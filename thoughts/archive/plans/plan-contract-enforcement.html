Target contract

Layered enforcement architecture

  1. Shared doctrine: ai-configs skills define the universal semantic floor.
  2. Repo contract: downstream repos adapt that floor to local templates, validators, and domain constraints.
  3. Service boundary: plan-reviewer service metadata and comment queues support review; they do not become the global structural schema source.
  4. Readiness gate: execution-ready status requires resolved blockers, fresh independent sign-off, and no contradictions between artifact readiness and registered metadata where both exist.
  5. Downstream enforcement: Heddle and other repos implement stricter local validators separately.

Shared floor

  • Decision Attention appears near the top of non-trivial plans and indexes blockers, user-input needs, low-confidence areas, and unresolved decisions.
  • Progress contains the only checkboxes; every progress item maps to exactly one phase, and every phase maps to exactly one progress item.
  • Each phase includes End state, Tests first, Expected files, Work, Verify, and Open questions / decision dependencies.
  • Every non-trivial plan triages UI impact. Execution-ready UI-impacting plans include existing and target high-fidelity mocks plus repo-appropriate design evidence.
  • unknown UI impact, unresolved blockers, stale review, self-certification, or later non-pass review prevents execution-ready status.

UI impact triage

UI impact: text-only impact on plan artifacts. This work changes the written structure and review expectations for plans. It does not change app-shell UI, plan-reviewer runtime UI, visual styling, or browser interaction behavior in this session.

  • Current weak structure: plans can hide blockers in body sections, leave progress detached from phase details, omit phase-specific decision dependencies, and claim execution readiness without clearly exposing UI-impact evidence.
  • Target structure: plans should state Decision Attention near the top, keep progress and phases one-to-one, include explicit Open questions / decision dependencies per phase, and explain UI-impact evidence requirements in prose.
  • Evidence expectation: shared skills should require repo-appropriate design evidence for real UI-changing work, but this ai-configs plan only needs a textual rendition because no plan-reviewer runtime UI is being changed.

Product intent alignment

This plan improves the shared agent/operator workflow by making the correct planning behavior the default behavior. Agents should not have to infer hidden readiness semantics, and reviewers should not have to hunt for blockers, decisions, UI impact, or phase details. The right action is to write plans with visible risk surfaces and executable phases before implementation starts.

Locked decisions

  • Layered model: shared skills define the floor; downstream repos enforce local detail.
  • Owner files: structure belongs in planning-workflow, readiness review in reviewed-html-plan, operator/product rationale in product-principles, and service mechanics in html-plan-reviewer.
  • Repo-neutral doctrine: no Heddle-specific Weft, Linear, native, or schema rules go into global skills.
  • No runtime code: no product/runtime code changes in plan-reviewer from this ai-configs session.
  • Downstream separate: Heddle enforcement remains follow-up or a separate approved phase outside this session.

BDD scenarios

Prominent decisions before execution

Given an agent writes a non-trivial plan with an unresolved low-confidence API decision, when the shared planning doctrine is followed, then Decision Attention near the top shows the blocker and the plan cannot be marked execution-ready until resolved or downgraded to research-ready with a next research step.

Progress maps to phase details

Given a plan has a progress item for P2, when another agent resumes the plan, then exactly one P2 phase exists with end state, tests first, expected files, work, verify, and open questions / decision dependencies.

UI-impacting work requires design evidence

Given a plan changes visible UI or reviewer-facing artifacts, when it requests execution-ready status, then it includes high-fidelity existing and target mocks, repo-appropriate design evidence, and verification gates proving design match.

Service mechanics do not become structural doctrine

Given an agent reads html-plan-reviewer, when it needs plan structure or readiness doctrine, then the skill points back to planning-workflow and reviewed-html-plan instead of duplicating or inventing a daemon schema.

Downstream enforcement stays separate

Given Heddle needs stricter local validator enforcement, when this ai-configs plan is executed, then Heddle-specific work is recorded as follow-up and no Heddle file is modified.
