Product-owner context

When agents use the delivery workflow to publish a coding plan for browser review in Doct, reviewers sometimes land on a page titled Untitled Plan with No section entries generated in the Contents panel. The tree/document name can still look reasonable, but the plan chrome itself is empty of identity.

Key conclusion: this is an agent-workflow / guidance defect in how plans are authored and registered, not a customer runtime product bug in Heddle. Operators and reviewers lose orientation; the plan content may still exist below the chrome.

What's new

Plans keep a real title through delivery → Doct

Promise: a delivery-published browser-review plan shows the human plan title in Doct chrome, not Untitled Plan.

Before: agents could omit --title on doct-agent plans register, and Markdoc sources often lacked YAML frontmatter title:. Doct’s Markdoc compiler renders frontmatter.title ?? "Untitled Plan", so chrome showed Untitled Plan and empty TOC when template section tags were also missing.

After: one canonical title is written to source content (Markdoc frontmatter title: and matching heading, or HTML <title> and <h1>), passed as register --title (Doct document/tree name), and verified after register so chrome and sidebar never disagree. delivery check warns with PLAN_TITLE on missing, mismatched, or drifted titles.

Preserved: guidance-not-gates doctrine (advisory only), existing stage authorization boundaries, and Doct registration/listener flow.

Goal

Make delivery + planning + doct-document-ops guidance and the delivery CLI prevent Untitled Plan registrations: agents always pass a real title, Markdoc/HTML sources carry that title in the places Doct actually reads, and delivery surfaces a soft advisory when the recorded plan path would still publish untitled.

Decision Attention / Low-confidence Areas

No product decision required. Doct’s Markdoc chrome title source is confirmed in lib/plan-review/markdoc.ts (frontmatter.title ?? "Untitled Plan"). This change fixes the ai-configs / delivery agent side; a future Doct-side fallback from first heading remains optional and out of scope.

Why this plan exists

Screenshot evidence showed Status browser-review-draft, title Untitled Plan, and empty Contents during delivery browser review. Live delivery Markdoc sources (for example account-detail-add, signout-fix) started with a # heading and no frontmatter title:. Skill text previously said to add --title only when destination was specified, so agents skipped it.

  • Tests in skills/delivery-run/tests/test_delivery_cli.sh cover extraction + advisory.

Locked decisions

  • D1: Markdoc browser chrome title comes from YAML frontmatter title:; a leading # heading alone is insufficient.
  • D2: Always pass doct-agent plans register --title; do not rely on filename inference.
  • D3: Delivery detection is advisory (PLAN_TITLE), not a hard stage gate.
  • D4: No Doct product code change in this PR; ai-configs only.

Acceptance criteria

  1. AC1 — Title contract documented: skills require one canonical title in source content, register --title, and Doct document metadata; retitles must update all sides.
  2. AC2 — Detection: heading-only Markdoc, mismatched HTML <title>/<h1>, or recorded Doct title ≠ content each yield PLAN_TITLE on delivery check --json.
  3. AC3 — Extraction: aligned Markdoc/HTML sources yield a canonical title; mismatched or heading-only sources yield none.
  4. AC4 — Tests: bash skills/delivery-run/tests/test_delivery_cli.sh passes, including mismatch and drift cases.
  5. AC5 — Self-consistent artifact: this plan’s <title>, <h1>, and register --title are the identical string; post-register Doct document title matches.
