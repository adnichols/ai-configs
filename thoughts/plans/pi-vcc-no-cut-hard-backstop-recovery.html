Pi VCC No-Cut Hard-Backstop Recovery Plan

Plan to prevent Pi VCC hard-backstop compaction from halting active sessions when reported context is high but no safe compaction cut exists.

Scope: repo-owned Pi VCC package and percentage-compaction extension only; no Pi core/provider accounting changes in this implementation plan.

Goal

Make hard-backstop compaction resilient: when Pi reports high context usage but pi-vcc/core cannot form a safe cut, the active agent session should continue instead of halting with Compaction failed: Nothing to compact (session too small).

The fix should distinguish no-cut states, recover active turns with a continuation, avoid repeated no-cut loops, and preserve existing pi-vcc safety boundaries.

Decision Attention / Low-confidence Areas

  • No product decision required: this is a reliability bug in an agent workflow; default behavior should self-heal and continue.
  • Low confidence to defer: Pi core/provider context accounting may still over-report usage after compaction. This plan intentionally mitigates halt behavior in pi-vcc first and records core accounting as a non-goal/follow-up.
  • Review focus: ensure continuation is sent only when a compaction attempt likely interrupted an active turn, waits until tool-call/tool-result ordering is safe, and survives transient continuation delivery failures.

Why this plan exists

A real session in jul5-quarantine-investigation showed the extension interrupting an agent at high reported context:

↻ Context at 96% (hard backstop: 80%). Interrupting agent for pi-vcc compaction...
Error: Compaction failed: Nothing to compact (session too small)
Nothing to compact

Inspection showed a prior pi-vcc compaction had already summarized the old history, and the live post-compaction tail was mostly in-flight agent/tool turns. Core compaction could not find a safe old segment to summarize, but the extension still treated the hard-backstop attempt as an interrupting compaction. The result was a halted workflow instead of a recoverable no-op with continuation.

Current implementation reality

  • _pi/extensions/percentage-compaction.ts triggers hard-backstop compaction at HARD_AUTO_COMPACTION_PERCENT = 80 and uses ctx.compact(...).
  • The extension currently treats Already compacted and Nothing to compact (session too small) as no-op-ish errors by ratcheting the percent and notifying Nothing to compact, but it does not have a clear active-turn no-cut recovery contract.
  • _pi/packages/pi-vcc/src/hooks/before-compact.ts has active-turn continuation for successful pi-vcc compactions through session_compact, plus agent-only fallback cuts and tool-result boundary adjustment.
  • When buildOwnCut(...) cannot form a pi-vcc cut, the hook currently lets core fallback for manual/threshold/overflow events without a pi-vcc-specific no-cut classification.
  • Existing tests cover active-turn continuation after successful compaction and some no-cut fallback behavior, but not hard-backstop no-cut recovery from the extension’s onError path.
  • Pi core’s agent-session.js throws Nothing to compact (session too small) when prepareCompaction(...) returns undefined, even when the true state is “post-compaction/no safe cut.” This plan does not edit Pi core.

Product intent alignment

  • Golden path: a long-running Pi agent should continue doing the requested work even if compaction cannot safely reduce context at that instant.
  • Self-healing: a no-cut hard-backstop attempt is a recoverable condition; the extension should explain it, suppress immediate retry loops, and resume the interrupted work.
  • Fail-closed boundary: pi-vcc must not force unsafe compaction cuts or drop tool-call/tool-result evidence just to satisfy a context percentage.
  • Agent-legible status: notifications and continuation content must say what happened and what to do next without requiring source-code inspection.
  • UI impact triage: no app/browser UI changes. User-visible surfaces are Pi TUI notifications, model-visible steer/follow-up messages, and debug metadata.

Locked decisions

  • Do not wait for Pi core/provider accounting fixes to prevent halted sessions.
  • Do not broaden this plan into changing context percentage calculation or footer rendering.
  • No-cut recovery must not rewrite existing history, create a compaction entry, mark compaction successful, or drop/cut messages.
  • No-cut recovery may add one model-visible custom continuation event with diagnostic metadata when an active turn was interrupted and continuation delivery is safe.
  • No-cut recovery must not mark a compaction as successful; it should be a recoverable skip with continuation when appropriate.
  • Hard-backstop no-cut retry suppression is required to avoid immediate repeated interruption loops, with an explicit re-arm predicate defined in P4.

BDD scenarios

BDD-1 — Active hard-backstop no-cut continues

Given a prior pi-vcc compaction and a live post-compaction active tool turn, when hard-backstop compaction fails with Nothing to compact (session too small), then the extension clears compaction state, resets stale post-compaction wait state, records the no-cut ratchet, shows an agent-legible skip notification, and sends one successfully delivered continuation steer/follow-up after tool-result ordering is safe.

BDD-2 — Idle no-cut does not resume

Given no active interrupted agent turn, when a no-cut compaction error occurs, then the extension reports a recoverable no-op and does not trigger a new agent turn.

BDD-3 — No immediate retry loop

Given a no-cut hard-backstop recovery at 96%, when subsequent tool turns report the same floored percent and no re-arm signal occurred, then the extension does not repeatedly interrupt the agent for the same no-cut condition.

BDD-4 — Later compactable tail still compacts

Given a no-cut hard-backstop was recovered earlier, when the floored usage percent rises by at least one point or a new user message arrives and enough live history accumulates to form a safe cut, then pi-vcc compaction still runs normally and successful continuation behavior remains intact.

BDD-5 — Safety boundary beats forced compaction

Given a live tail where cutting would orphan a tool result or drop un-interpreted evidence, when usage is above the hard backstop, then pi-vcc must prefer no-cut recovery over unsafe summary/cut behavior.

  • Manual /compact-now and compact_context tool paths pass recoverNoCutWithContinuation: false or omit the option so no-cut errors there remain notify-only.

Work

  • Suppress repeated hard-backstop attempts for the same floored usage percentage, e.g. repeated 96.x, until a concrete re-arm signal occurs.
  • Re-arm no-cut retry suppression when either the floored usage percent increases by at least one point or a new user message is observed since the last no-cut recovery, whichever comes first. A completed assistant boundary alone is not sufficient unless paired with one of those re-arm signals.
