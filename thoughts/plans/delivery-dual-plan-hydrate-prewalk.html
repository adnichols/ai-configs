Product-owner context

Situation: Delivery’s reviewed HTML plans are one document asked to serve two audiences. Operators review product intent, decisions, and acceptance in Doct. Agents also need files, RED contracts, verify recipes, and resume detail. At implementation cutover, Pi Full starts a new session pinned to Luna/Terra and asks it to re-read the plan — without prewalk’s commit → todo → continue → checklist framing.

Why now: Live review of the delivery cutover showed three material gaps: (1) new-tab plan handoff is not same-thread continuity, (2) delivery does not inject prewalk’s behavioral framing, and (3) the single plan overloads human review. The proposed dual-plan + hydrate/prewalk shape addresses all three.

Key conclusion: This is an operator/agent workflow product defect in ai-configs delivery tooling, not a stale-test problem and not an external customer app bug.

Why this exists

Delivery already solved ownership handoff (planning tab → dedicated impl tab) and profile pinning. It did not solve (a) human vs agent plan audiences, (b) same-thread hydrate→executor framing, or (c) truthful accounting for an expected mid-impl model transition. Prewalk already solved framing inside one session; this plan composes those strengths without pretending today’s cold-start is the same thing.

  • Same-model case: If hydrate and executor resolve equally, still advance protocol phases and inject executor checklist (do not copy prewalk’s silent early disarm).
  • Hydrate authority: Hydration reconstructs execution state (orientation, todos, risks, continuation). Material contract contradictions revoke readiness; hydration must not invent product decisions.
  • Rollout: Opt-in Pi Full trial only. Default Pi Full remains today’s single-profile launch until a later explicit cutover plan.
  • Post-impl gates: Scoped review, PM outcome, autoreview, completeness, verify, PR remain required on the trial path as they are for Pi Full today.

BDD2 — Sync fail closed

Given an agentic companion missing an operator AC ID or with a stale hash,
When the agent attempts EXECUTION_READY,
Then delivery rejects with an agent-legible fix command and does not launch implementation.

BDD3 — Hydrate then executor

Given an authorized trial launch on Luna xhigh with executor terra-high,
When hydrate completes todos and the D1-selected mutation/transition boundary fires successfully,
Then ledger reaches executor-verified and subsequent code work runs on terra-high with checklist framing present.

BDD4 — Transition failure

Given hydrate armed for an executor but the model switch fails,
When verify/transition checks run,
Then ledger records failed-transition (not silent Luna continuation) and emits a recovery command.

BDD5 — Legacy path untouched

Given a Pi Full ledger without the trial flag,
When EXECUTION_READY launches implementation,
Then today’s single-profile launch + verify-implementation-profile contract still holds.

BDD6 — Hydrate must not replan product intent

Given a locked operator decision in the operator plan,
When hydrate finds an apparent contradiction in the repo,
Then it revokes/blocks readiness rather than silently changing product intent.
