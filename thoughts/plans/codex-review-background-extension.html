Product-owner context

Situation: Pi already uses Codex as the primary GPT reviewer, but Pi starts it through a skill-owned shell wrapper rather than a managed Pi review tool. The inner Codex command is reasonably deterministic; the outer lifecycle is not. A process can emit progress commentary without a final verdict, return an empty or stale artifact, be interrupted without a durable classification, or require the coordinating agent to infer whether a usable review actually finished.

Why now: session evidence shows this is not hypothetical. In an identifiable cohort of about 210 Codex review-partner invocations, roughly a dozen lacked a recorded completed turn and ended with progress-only commentary such as “I’ll inspect the diff…”. Separately, Pi GPT reviewer subagents have returned completed-but-empty outputs. We have therefore selected the Codex CLI as the more reliable GPT review runtime, but its Pi integration still needs the same managed lifecycle that already exists for claude_review.

Key conclusion: this plan addresses an agent/review infrastructure reliability defect, not a customer runtime defect. The fix is a purpose-built Pi extension plus a hardened Codex launcher contract. It improves completion truthfulness and transport reliability; it does not claim that any model will find every defect.

  • Canonical boundary: retain skills/codex-review-partner/scripts/run-review.sh as the cross-runtime launcher. The Pi extension manages it; it does not duplicate Codex CLI policy.
  • Final-message boundary: use Codex CLI’s supported --output-last-message option. Do not treat streamed progress, stdout activity, or process exit alone as the review artifact.
  • Review-only surface: the Pi tool supports implementation, adversarial implementation, and plan reviews. Existing non-gating pair mode remains available through the cross-runtime wrapper and is not migrated into the required-review tool.
  • Session durability: jobs are session-scoped and are not resumed after host loss. Graceful shutdown cancels them immediately; abrupt host termination is reconciled on the next extension startup by classifying persisted running jobs as interrupted, safely reaping any identity-matched orphan group, and releasing stale reservations. The launcher’s own inner watchdog bounds orphan lifetime even if Pi never restarts.

Goal

Create one Pi tool named codex_review that starts the canonical Codex review launcher invisibly in the background, returns immediately, captures only the final Codex message as the requested artifact, validates its verdict, and wakes Pi exactly once with either a usable review or a classified infrastructure failure.

Why this plan exists

The repository’s review policy already says Codex is the primary GPT review leg and that Pi should not substitute a GPT subagent. However, the actual Pi launch remains a shell/process concern distributed through prompts and skills. The result is a policy/implementation mismatch: we selected Codex for reliability without yet giving it the deterministic outer controller that makes required reviews trustworthy.

Observed facts versus proposal: observed sessions show progress-only and incomplete Codex review turns. The proposed plugin will detect and classify those outcomes; it cannot retroactively prove why each historical process stopped, and it cannot guarantee model defect recall.

Product intent alignment

  • Golden path: write a bounded prompt, call codex_review, continue other work, receive one completion notification, and read the validated artifact.
  • Safe defaults: implementation review is the default review type; the extension fixes background behavior, model, high effort, read-only sandbox, launcher, timeout policy, and no-overlay presentation.
  • Self-healing: output identity is reserved atomically, caller-owned pre-existing output is never deleted or truncated, and the controller preserves logs/state needed for a narrow rerun. It does not automatically rerun with a modified prompt because narrowing review scope is a coordinating-agent decision.
  • Fail closed: empty output, missing final message, progress-only text, missing verdict, invalid verdict, nonzero exit, provider error, timeout, and cancellation cannot become a clean review.
  • Actionable errors: every terminal failure names the classification, job ID, output path, stdout/stderr logs, state path, and recommended next action.
  • Repo alignment: skills, prompts, install docs, source-policy tests, and system tool guidance must all describe the same canonical Pi route.

BDD scenarios

S1 — Background implementation review

Given a valid bounded prompt and output path, when Pi calls codex_review start, then reservation and starting state persist, the launcher spawns, running identity persists, and only then Pi receives an accepted job ID; the final Codex message is published and one completion notification follows.

S2 — Progress-only process output

Given Codex emits “I’ll inspect the diff…” but never writes a valid final verdict, when the process exits or is interrupted, then progress remains diagnostic log content and the requested artifact is missing/invalid; the job cannot pass.

S3 — Existing or raced output is never destroyed

Given the requested output already contains unrelated data or a prior verdict, when a start is requested, then the job is rejected before launch and the bytes remain unchanged. Given the path was absent at start but another writer creates it before publication, then no-clobber publication fails and preserves the other writer’s bytes.

S4 — Wrong, quoted, misplaced, or duplicate verdict

Given a final message contains no verdict, an unsupported verdict, multiple verdict candidates, a verdict inside a fenced example, a quoted/prefixed verdict, or trailing non-empty text after an otherwise valid verdict, when artifact validation runs, then the job fails as invalid. CRLF and trailing horizontal whitespace normalize deterministically, and only one exact final logical line can pass.

S5 — Explicit incomplete review uses profile policy

Given Codex returns VERDICT: REVIEW_INCOMPLETE_RERUN_NEEDED with a coverage ledger and one follow-up slice, when completion is processed, then the infrastructure job succeeds but the gate remains non-clean. Pre-PR/run-plan PM permit one narrowed follow-up for that reviewer/cycle; reviewed-plan follows required slices until complete or a workflow stop condition; generic profiles report the slice without choosing a retry policy.

S6 — Healthy silence

Given Codex produces no output for longer than prior quiet thresholds while reasoning, when it later writes a valid final verdict before the watchdog, then the job remains running and succeeds normally.

S7 — Provider or authentication failure

Given Codex cannot authenticate, is rate limited, or receives a provider error, when an enabled evidence-backed mapping matches, then the job reports that stable specialized classification and guidance. When the shape lacks authoritative evidence, then it preserves stderr/stdout/state paths, reports generic nonzero guidance, leaves the gate blocked, and never guesses a cause or substitutes another model.

S8 — Concurrent isolation

Given two reviews with distinct output paths and a third targeting the first path, when they start concurrently, then the distinct jobs complete independently and the duplicate output request is rejected before launch.

S9 — Timeout, cancellation, shutdown, and persistence failure

Given a review and descendant Codex process are still running, when the launcher timeout, outer watchdog, or explicit user cancellation occurs, then the full group is reaped and exactly one notification is emitted. When graceful Pi shutdown cancels it, then state is persisted and the group is reaped with zero notifications/new turns. Given terminal-state persistence fails, then the original notification is suppressed, the job becomes CODEX_REVIEW_STATE_PERSIST_FAILED, emergency evidence is attempted, and at most one degraded notification is emitted.

S10 — Canonical routing without overblocking
