Delivery single-owner tab lifecycle

Make every Herdr delivery workspace converge on one obvious owning tab. Role tabs exist only while that role is live; fulfilled and failed tabs are retired automatically. Workspace chrome always mirrors the current owner.

Product-owner context

Delivery workspaces for Heddle (and other repos) currently accumulate many Herdr tabs: a planning tab, several failed or superseded implementation tabs, and a completeness tab. Operators look at the first tab or the workspace row and cannot tell whether work finished, because ownership moved elsewhere and dead tabs were never cleaned up.

Why now: Live multi-delivery supervision under heddle shows the failure mode clearly (empty shell tabs after agent_pane_busy retries; planning tabs stuck on PL: after handoff; DONE workspaces still showing three tabs). This is an operator-attention defect in the delivery workflow product, not a Heddle application bug.

Key conclusion: Fix the delivery/Herdr lifecycle so the workspace always has one current owner tab and retires fulfilled helpers. Do not return to multi-pane splits as the primary layout.

CustomersNo change to end-user Heddle/Doct product behavior.
Runtime product behaviorDelivery/Herdr operator UX changes: tab create/close/focus/label ownership during delivery runs.
Security / permissionsNo change. Still best-effort Herdr control of tabs the workflow created; no broader session teardown.
Testing / release confidenceExtend delivery CLI fake-herdr tests for owner transfer, close-on-failure, and close-on-fulfillment.
Deployment / migrationNot applicable for hosted deploy. Existing in-flight workspaces keep junk tabs until a delivery command runs a best-effort reconcile, or operator closes them manually.

What's new

One owner tab is the workspace truth

After this change, a delivery workspace no longer keeps a museum of planning, failed-impl, and finished-reviewer tabs. The workspace label and focus follow a single ledger owner; when a role finishes or fails, its tab is closed so the remaining tab is obviously the place to look.

Before After
Planning tab stays forever on PL:; impl/completeness tabs pile up; failed starts leave empty shells. Planning tab lives only during planning; impl becomes sole owner after ready handoff; failed tabs close immediately; completeness tab closes after accept/waive.
Workspace rename uses whichever agent last called delivery (HERDR_TAB_ID drift). Workspace chrome always targets the ledger workspaceOwner.
Evidence often assumed live sibling tabs remain open. Live tabs while role is active; after close, ledger + artifacts + Pi session transcripts are authoritative.

Observable result: At DONE, the workspace has one settled implementation tab and a phase label that matches that tab.

Preserved: Multi-tab only for concurrent live roles; no return to multi-pane as the default; single-writer implementation handoff; visible completeness review while pending; guidance-not-gates for advisory evidence; DELIVERY_SKIP_HERDR=1 still disables Herdr side effects.

Goal

Redesign delivery’s Herdr tab lifecycle around a single workspace owner so operators always have one obvious tab, failed/fulfilled role tabs are retired automatically, and skill guidance matches that architecture without compatibility cruft.

Decision Attention / Low-confidence Areas

No open product decisions blocking execution. Locked choices below reflect operator direction from the design thread.

  • Locked: Multi-tab is allowed only for concurrent live roles; not permanent multi-pane.
  • Locked: Close planning tab after implementation is confirmed live—not earlier.
  • Locked: Evidence after close comes from ledger/artifacts/Pi sessions, not preserved TUIs.
  • Locked: Completeness remains a short-lived witness tab, never the long-term owner.
  • Locked: Do not self-close the tab running the delivery CLI; the new owner retires the previous owner.

Intended end state

A delivery workspace has exactly one long-lived owner tab at a time. That owner’s agent status and phase label are what the workspace chrome shows. Helper tabs exist only while their role is live and are closed when the role succeeds, fails, is revoked, or is superseded. 

Planning:     [ PL owner ]
Handoff:      [ PL retiring ] [ I owner ]  → close PL after I ready
Implementing: [ I owner ]
Completeness: [ I owner ] [ complete witness ]  → close witness after accept
DONE:         [ D owner ]

Zero-tech-debt review

1. End state first

Build the owner lifecycle as if multi-tab museums never existed. Do not add a “cleanup mode” flag beside the old forever-tabs behavior.

2. Callers / delete non-callers

  • Real callers today: create_labeled_agent_tab, launch_implementation_agent, cmd_completion_review, maybe_herdr_label, spawn bootstrap, stage/set/reflect paths, run-plan/delivery skill prose about sibling tabs.
  • Delete or stop teaching: assumptions that planning tabs remain after handoff; label sync via ambient HERDR_TAB_ID when it disagrees with ledger owner; leaving start-failed tabs for humans to notice; dual permanent role labels (impl · forever) once owner phase codes exist on the owner tab.
  • Do not preserve a parallel “legacy multi-tab keep-all” path unless a test proves a current external caller needs it. None identified outside this repo’s delivery skill/tests.

3. One product surface

One ledger object workspaceOwner is the product surface for “where is this run?” Implementation profile and completeness review still record their own pane/tab identities as role records, but chrome and retirement decisions read owner + explicit retire lists—not ad hoc env vars.

4. Shared rules in one place

  • claim_workspace_owner(...) — set owner, rename workspace+owner tab, focus owner tab, persist labels.
  • retire_tab(tab_id, reason) — best-effort herdr tab close, history note, never close the caller’s current tab.
  • retire_pending_tabs(ledger) — drain tabsToRetire[] from the new owner context.
  • launch_role_tab(role) — create tab, start agent with same-pane busy retry, close tab on terminal start failure.

Impl and completeness both use launch_role_tab; no duplicated busy-retry only on completeness.

5. Names by intent

  • Prefer workspaceOwner, tabsToRetire, claim_workspace_owner, retire_tab.
  • Avoid history-shaped names like legacyTabCleanup, compatKeepPlanner.

What we explicitly will not do

  • No generic tab-GC framework or background daemon.
  • No forced single-tab-from-second-zero that reintroduces multi-pane splits.
  • No requirement that agents scroll closed TUIs; transcripts/artifacts suffice.
  • No hard-fail of delivery stage transitions solely because Herdr close failed (log + advisory); owner claim still records intent.

Current implementation reality

  • create_labeled_agent_tab always creates a new tab with role label impl · / complete ·.
  • launch_implementation_agent on start failure records start-failed and leaves the shell tab open; retries create another tab.
  • Completeness has a short same-pane agent_pane_busy retry; implementation does not share that helper.
  • maybe_herdr_label renames workspace + one tab from HERDR_* / labels / spawn—after handoff this drifts to whichever agent last ran delivery, while tab 1 often stays PL:.
  • No herdr tab close anywhere in delivery today.
  • Skills tell planning to stop after handoff but never retire the planning tab; completeness accept writes an artifact but keeps the reviewer tab.
  • Live evidence (2026-08-04 heddle deliveries): NOD-1501 left three agentless tabs; supersession left stopped early impl agents; DONE hub-membership kept PL+impl+complete.

Target architecture

Ledger: workspaceOwner

{
  "workspaceOwner": {
    "role": "planning" | "implementation" | "done",
    "tabId": "wEY:t3",
    "paneId": "wEY:p3",
    "agentName": "implementation-nod-1501-59efcf",
    "claimedAt": "…Z"
  },
  "tabsToRetire": [
    { "tabId": "wEY:t1", "reason": "planning-handoff-complete", "enqueuedAt": "…Z" }
  ]
}
  • Spawn/init claims owner planning on the spawn tab.
  • Successful impl launch claims owner implementation, enqueues previous owner tab for retire, focuses new owner.
  • Completeness is not owner; it is a witness recorded only under completenessReview.
  • DONE/reflect may set owner role done (same tab) and phase label D:.

Self-close hazard (critical)

Planning often runs delivery stage EXECUTION_READY, which launches impl inside the planning pane. Closing the planning tab from that process would kill the caller. Therefore:

  1. On impl ready: claim owner=implementation, focus impl tab, enqueue planning tab in tabsToRetire, do not close caller tab from the launch process if it is the retire target.
  2. Implementation agent’s required early path (verify-implementation-profile and/or first successful delivery write from the impl pane) calls retire_pending_tabs.
  3. Failed launch tabs are never the caller; close them immediately from the launch process.
  4. Completeness accept/waive closes the witness tab from the impl owner context (not self).

Launch lifecycle

  1. If ledger has a start-failed role tab still open for this attempt, retry agent start on that same pane with busy backoff (unify with completeness).
  2. Else create one labeled tab.
  3. Start agent; on terminal failure → retire_tab that tab, clear role pane/tab ids that are dead, history note.
  4. On ready → claim owner (impl only), enqueue prior owner for retire, prompt agent.

Label chrome

  • maybe_herdr_label / rename always targets workspaceOwner.tabId (fallback spawn only if owner missing).
  • Ignore ambient HERDR_TAB_ID for rename when it disagrees with owner (env remains useful for “who is calling” and self-close guards only).
  • Owner tab label uses phase code (PL:/I:/R:/PR:/D:/B:). Witness tabs may keep short role labels (complete · …) until closed.

Revoke / return to planning

On revoke-implementation-approval or explicit return to plan stages before a live impl owner is needed: claim or create a planning owner tab, enqueue impl tab for retire after stop guidance, drain retires from the new planning context. Do not leave both forever.

Guidance changes

  • delivery-run / run-plan: document owner lifecycle; while completeness tab is live, read it via Herdr; after accept, read artifact.
  • After planning handoff, do not instruct agents to inspect the planning tab.
  • For historical planning context, use plan files, ledger history, and Pi session paths from ledger/history—not closed Herdr tabs.
  • Impl brief: after verify, retire pending tabs is part of becoming owner (automatic in CLI preferred over asking the model to remember).

Acceptance criteria

  • AC1: After successful implementation launch, ledger workspaceOwner.role=implementation and owner tab/pane match the live impl agent.
  • AC2: Planning tab id is enqueued for retire on that handoff and is closed by a delivery command running from the impl owner (not by killing the launch caller mid-flight).
  • AC3: Terminal impl agent start failure closes the just-created tab and does not leave an agentless tab recorded as live owner.
  • AC4: Retry after start-failed reuses the same pane when still open and appropriate, or creates a replacement only after the dead tab was retired—no unbounded tab pile-up on repeated busy failures.
  • AC5: Completeness accept or waive closes the completeness witness tab; owner remains implementation.
  • AC6: maybe_herdr_label renames workspace + owner tab from workspaceOwner, not a disagreeing ambient HERDR_TAB_ID.
  • AC7: Skills/brief no longer require reading closed planning tabs; completeness live-tab read remains until accept; artifact is authoritative after.
  • AC8: DELIVERY_SKIP_HERDR=1 still skips Herdr mutations including close/focus/rename.
  • AC9: Existing delivery CLI tests stay green; new tests cover fail-close, owner claim, pending retire drain, accept-close.

BDD scenarios

Happy handoff

Given a delivery workspace owned by the planning tab
When EXECUTION_READY launches a dedicated implementation agent successfully
Then workspaceOwner points at the impl tab
And the planning tab is listed in tabsToRetire
And the impl agent’s verify/first delivery command closes the planning tab
And the workspace label phase tracks implementation stages on the impl tab

Start failure does not litter

Given implementation launch creates a new tab
When herdr agent start fails terminally (including busy timeout)
Then delivery closes that tab
And ledger does not claim it as workspaceOwner
And a retry does not retain multiple dead shell tabs

Completeness is temporary

Given an implementation owner tab
When completion-review launches a witness tab and later --accept succeeds
Then the completeness artifact is recorded
And the witness tab is closed
And workspaceOwner remains the implementation tab

Evidence after close

Given the planning tab was retired after handoff
When an implementation agent needs planning context
Then it uses the plan path, ledger history, and validation artifacts
And it does not fail solely because herdr agent read on the old planning pane is unavailable
