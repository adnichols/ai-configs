Goal

Make the normal reviewed-plan execution path keep three sources aligned:

  1. the checked-in HTML plan file under thoughts/plans/, especially Progress, status text, and Decisions / Deviations history;
  2. the plan-reviewer service metadata, especially lifecycle, board column, source sync, execution-readiness metadata, and PR metadata;
  3. repo-local prerequisites such as Heddle's requirement for one Linear issue before non-trivial execution.

The intended behavior is: when an agent starts implementation through run-plan or the plan-reviewer Build Plan button, the plan-reviewer card is no longer left in Backlog/Planning, the plan source remains the authoritative progress record, and repos with mandatory Linear policy fail closed before code is changed.

Decision Attention / Low-confidence Areas

D1 — Do not make plan-reviewer own Heddle policy. Plan-reviewer should emit generic status-sync instructions. Heddle-specific Linear enforcement belongs in repo guidance plus the shared run-plan preflight that honors repo guidance.

D2 — Board column names are locally configurable. The default column key is in_progress, but the service allows columns to be renamed/hidden. Implementation should prefer in_progress when present and fail with an actionable message or use a configured equivalent if a future API exposes one.

D3 — Existing plans may not be registered. run-plan should align plan-reviewer metadata when a matching registered plan exists. If no matching reviewer record exists, it should register the plan or continue with a clear note depending on repo guidance and user intent.

D4 — This is a coordinated two-repo change. The ai-configs repo owns the shared skills/prompts plan and primary PR. The plan-reviewer repo owns the service-emitted agentInstructions code/test change and must be changed on its own branch with its own commit/PR. Completion requires both PR URLs or a documented blocker; do not mix plan-reviewer source edits into the ai-configs PR.

Why this plan exists

Reviewed HTML plans are live-linked to plan-reviewer, but current execution guidance mostly updates the source file checkbox after each phase. The reviewer board column and lifecycle can remain in Backlog/Planning even while code is being built. This creates false status for operators and makes the reviewer index less useful as a work queue.

Separately, repos such as Heddle already require one Linear issue before non-trivial product work. That rule exists in repo AGENTS.md, but the shared execution workflow does not call it out as a concrete pre-code gate. Agents can therefore start implementation without verifying the issue.

Product intent alignment

This is an agent/operator workflow change. The golden path should do the obvious status updates automatically instead of relying on agents to remember separate manual plan-reviewer maintenance. Routine recoverable gaps, such as a reviewer record that can be found or registered, should be healed in the normal execution flow. Ambiguous identity or policy gaps, such as a repo that requires Linear but has no issue, should fail closed with an agent-legible blocker.

UI impact: text-only plus existing status controls. The plan changes guidance, emitted instructions, and CLI/status usage. It does not require a new browser UI component.

Locked decisions

  • run-plan is the single execution entry point. Direct agent invocation and the plan-reviewer Build Plan button must both enter the same run-plan <plan-path> workflow. It is the only shared path that can reliably stop before code edits and update state during phase execution.
  • agentInstructions is the cross-agent reminder point. Registration output reaches agents even outside the full reviewed-plan skill path, so it should include generic status-sync instructions.
  • plan-reviewer-build remains a thin bridge into run-plan. The browser Build Plan button may create a plan-reviewer comment handled by this bridge, but the bridge must call the same run-plan <plan-path> entry point as a direct agent request. It should not duplicate the execution workflow; it should pass context and require durable run state or a blocker before acking.
  • Linear policy remains repo-local. Shared guidance should detect and honor repo-local Linear requirements rather than hard-code Heddle behavior into plan-reviewer.
  • PR state belongs in plan-reviewer metadata where supported. Agents should use plan-review pr link and plan-review pr refresh for the primary ai-configs PR. The second plan-reviewer service PR must be recorded in the plan Decisions / Deviations log and final handoff because the current reviewer metadata tracks one PR per registered plan.
  • Two repos mean two PRs. The implementing agent must not claim completion until both the ai-configs PR and the plan-reviewer PR are created, or a concrete blocker explains why one cannot be opened.

Acceptance criteria

  1. Starting a run-plan execution for a registered reviewed HTML plan instructs the agent to set the plan-reviewer lifecycle active and board column in progress before code edits.
  2. Completing a phase requires updating the source plan progress, then verifying that plan-reviewer source sync or re-registration reflects the latest progress.
  3. When repo guidance requires a Linear issue before execution, run-plan requires a verified issue before code changes and stops with a blocker if missing.
  4. New plan-reviewer registration instructions include generic execution-start status alignment and progress/PR sync guidance with concrete commands.
  5. Plan-reviewer Build Plan bridge instructions require the bridge to invoke run-plan <plan-path>, perform only non-duplicative context/status handoff, and wait for durable run state before acking/resolving the build request.
  6. Pi PR creation guidance matches the existing Linear-aware requirement already present in shared AGENTS, Claude, OMP, and Codex surfaces.
  7. Execution produces two isolated delivery artifacts when both repos change: one ai-configs PR for skills/prompts and one plan-reviewer PR for service instructions/tests.
