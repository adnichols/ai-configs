Product-owner context

Recent evaluation evidence showed two complementary failures. One implementation split producer and consumer work until positional and configuration contracts drifted. Another had a single integration owner and a real dispatch test, yet stopped at a helper and top-level request event instead of populating all required production call sites with meaningful dimensions. Current guidance notices pieces of those risks, but it puts most durable execution mechanics in run-plan. Ordinary fixes, direct execution, and unplanned work can therefore miss the same checks.

Why now: the workflow needs one portable, trigger-based execution rule that applies whenever an agent is authorized to implement. Plans, run-plan, RED tests, and reviews should store or validate the same evidence at different levels of detail. The current externally installed tdd-test-writer also delegates test authorship to a subagent and has no repo-owned source or installer entry, contradicting the primary-agent ownership rule.

Key conclusion: this is an agent-workflow and release-confidence correction, not an application-runtime defect. The change adds a small common integration-integrity invariant, makes plan/review/test layers enforce their separate responsibilities, and ships a versioned direct-authorship TDD skill.

What’s new — integration proof follows every implementation path

Promise: whether work starts from a reviewed plan, run-plan, or an ordinary implementation request, an agent will identify relevant exact contracts and distributed behavior, re-read definitions before dependent edits, and prove the real boundary or dispatch path.
  • Before: plans mention consumers and parity, reviewers can spot round-trip or sibling gaps, and run-plan has a coverage ledger; no-plan work has no common required integration record.
  • After: a concise base execution rule triggers a compact integration record only when the change crosses an untyped exact contract or distributes behavior across production sites.
  • Observable result: a completion report can identify the source definition, producer/consumer or call-site inventory, production-path proof, and reconciliation result instead of citing helper existence.
  • Preserved guarantees: simple local typed refactors stay lightweight; reviews remain read-only detection gates; plans remain optional; and a contract or inventory discovered to require a new product outcome still stops for owner direction.

Goal

Establish portable, trigger-based integration-integrity behavior across direct execution, planning, TDD, and review; make tdd-test-writer repository-owned and directly authored; and preserve semantic alignment in the managed Hermes copies of the affected planning/execution guidance.

Locked decisions

  1. One common invariant: use the term integration integrity for a triggered executor rule, not a second planning-only doctrine.
  2. Trigger: it applies only to (a) exact information the type system cannot fully verify and (b) behavior required across multiple production call sites, handlers, resources, operations, or environments.
  3. Minimum record: record source of truth, producers/consumers or inventory basis, dependent docs/examples, verification, and reconciliation status. A local typed refactor records that neither trigger applies rather than fabricating a table.
  4. Reread and search: before changing a dependent side, reopen the current definition. After changing a contract, search readers, writers, importers, string references, and documented examples; update in-scope results, run the boundary check, then repeat the stale-reference search.
  5. Completion: helpers, middleware, wrappers, and event-existence assertions are infrastructure only. Completion requires inventory reconciliation and production-path or cross-boundary evidence for the intended outcome.
  6. Review boundary: review detects and validates integration evidence. The driving agent owns inventory updates, remediation tasks, tests, and fixes.
  7. TDD ownership: create skills/tdd-test-writer/SKILL.md as a default universal repo-owned skill. It directs the driving agent to author and execute RED tests directly and does not invoke a test-writing subagent.
  8. Portable adoption: add the compact invariant to the repo-bootstrap skill and root AGENTS.md template. Do not duplicate the full theory in downstream repo-local guidance; those files supply domain-specific contracts, inventories, and commands.
  9. Hermes boundary: update applicable managed source mirrors and their manifest through the documented source workflow. Do not install live Hermes configuration without an explicit later request.

BDD scenarios

BDD1 — Local typed work stays lightweight

Given a local refactor with no exact untyped contract and no distributed behavior, when the executor begins, then it records that neither trigger applies and does not create a fictitious inventory.

BDD2 — Producer output reaches the real consumer

Given a change crosses a serialized, positional, configuration, migration, or CLI/documentation contract, when the executor tests it, then the producer representation reaches the real consumer or nearest deterministic service-boundary equivalent; disconnected hand-written producer and consumer fixtures do not suffice.

BDD3 — Contract changes force dependent recall

Given a shared contract changes, when the executor updates dependents or resumes after a compaction/handoff, then it rereads the source definition, searches all readers/writers/importers/string references/documented examples, updates the in-scope results, and reruns the boundary test.

BDD4 — Distributed work is not completed by infrastructure

Given required behavior spans multiple operation families, when a helper, wrapper, or middleware is added, then the work remains incomplete until the source-derived inventory is reconciled and production-path tests cover the declared scope.

BDD5 — Review findings become owned work

Given a reviewer identifies an in-scope contract, call-site, or verification gap, when the driving agent acts, then it first maps the finding to an acceptance criterion/phase and an inventory row, creates named remediation work, strengthens proof where practical, and requests focused rereview.

BDD6 — RED tests remain directly authored

Given an agent uses tdd-test-writer, when it enters RED, then the driving agent writes and runs the test itself and records the expected failure without delegating test changes to another persona.

BDD7 — Documented commands are parser contracts

Given a documented command form is part of the requested contract, when tests are designed, then representative documented invocations execute through the actual parser rather than being proven only by documentation-string assertions.

BDD8 — Shared guidance is distributed truthfully

Given the repo-owned TDD source and managed Hermes mirrors are updated, when isolated installer and source-bundle checks run, then they prove the declared consumers received the intended text while the final report states that non-adopting external repos remain outside immediate enforcement.

Verification strategy

  1. Run focused source-contract assertions before implementation wording is accepted, then run the full shared-skill installer test suite because it owns temp-home installation behavior and cross-surface consistency assertions.
  2. Validate the install matrix as JSON before invoking installer behavior.
  3. Use scripts/render_pi_append_system.py and the existing temporary-home Pi install tests to prove the common rule survives rendering and installation.
  4. Use the standard installer only after isolated tests pass; compare the resulting local TDD skill and provenance marker.
  5. For Hermes source mirrors, refresh the source manifest and verify the bundle. Do not treat live deployment/install as pre-PR evidence.
  6. Before review, audit every changed file against this plan’s integration inventory. The reviewer receives the cited search results and proof claims, not just the prose plan.
  7. After any review fix, rerun only invalidated focused checks plus the required targeted rereview. Final evidence must distinguish source-review consensus from behavioral/distribution verification.

Delivery order

  1. Define and test the smallest common invariant and portable bootstrap representation.
  2. Make planning, execution, and review carry/validate the invariant at their proper layers.
  3. Replace external TDD guidance with the repository-owned direct-authorship skill and prove normal distribution.
  4. Reconcile Hermes source mirrors, regenerate the source manifest, and verify the bundle.
  5. Run bounded review, complete only in-scope remediation, then follow the selected execution workflow’s normal commit/PR steps.
  6. Post-merge delivery / operations: if the owner later wants live Hermes updated, run the documented install --dry-run, request/perform install --apply, then export and verify. This is explicitly non-blocking for the implementation PR.

Non-goals

  • Changing application/product behavior, public APIs, persistence formats, deployment behavior, or release policy.
  • Requiring full plans or a repository artifact for every small implementation task.
  • Claiming to enforce the rule in arbitrary already-existing Claude/Codex repositories that do not load the updated shared skills or adopt the root AGENTS.md template.
  • Adding an implementation or test-writing subagent, a new review persona, a parallel exploration ceremony, or a new test framework.
  • Moving task-specific contract checks into _pi/agents/reviewer.md or making reviewers implementation owners.
  • Adding bespoke installer algorithms, changing the fixed Pi review-stack payload, or making local skill synchronization a planning-time action.
  • Installing or exporting live Hermes configuration as part of this implementation slice.
  • Building a static validator that attempts to infer all application-specific contracts or call sites without repository evidence.
