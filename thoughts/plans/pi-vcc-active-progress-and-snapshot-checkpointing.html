Product-owner context

Situation: Pi VCC resumes long-running work after context compaction by tracking a continuation transaction. The latest deployment fixed lost acceptance and tool-progress attribution, but post-deploy sessions exposed two narrower defects in the same coordinator.

Why now: the conservative post-deploy audit found 13 continuation transactions. Two were marked failed_loudly exactly 60 seconds after their last tool completed even though the model was still generating the next response; normal assistant work appeared 4.6 and 16 seconds after the false warnings. Separately, those 13 transactions produced 34,114 continuation snapshots, including 27,136 snapshots in one 43-minute transaction, and expanded the shared pi-vcc log to roughly 70 MB.

Key conclusion: both are shipped runtime defects, not stale tests. Continuation delivery is succeeding, but the coordinator confuses active model inference with inactivity and durably records every streaming tool update instead of checkpointing liveness at a bounded cadence.

Goal

Keep continuation ownership truthful and bounded: never fail an accepted continuation while Pi reports that its next model turn is still active, preserve exact in-memory tool-stall freshness, and reduce durable session/log writes from one per streaming update to one bounded liveness checkpoint per interval without weakening reload or terminal-state recovery.

No product decision required. The host already exposes ExtensionContext.isIdle(), and the deployed coordinator already uses it to gate retry submission. The same host truth should prevent active inference from being terminalized as inactivity.

Why this plan exists

  • The July 14 remediation correctly separated acceptance, progress, and tool-stall timers, but the no-tool progress deadline still terminalizes unconditionally when its timer fires.
  • agent_start and turn_start increment diagnostic epochs but do not cancel or defer the progress deadline. A provider response taking more than 60 seconds after a tool result is therefore classified as dead work.
  • Every correlated tool_execution_update calls the normal transition path. Every applied transition appends a full snapshot and a full transaction log record, so a tool emitting updates every roughly 250 ms creates four durable records per second.
  • The resulting session growth can immediately recreate context pressure after compaction and makes runtime audits unnecessarily expensive, even when continuation delivery itself succeeds.

Current implementation reality

  • DEFAULT_IDLE_PROGRESS_DEADLINE_MS = 60_000. After the last correlated tool finishes, the coordinator arms progressDeadlineAt.
  • The progress timer callback applies progress_deadline without consulting ctx.isIdle(). The pure transition then writes failed_loudly: deadline_expired.
  • agent_start and turn_start are subscribed but only increment lifecycle epochs; ordinary model inference produces no persisted progress until an assistant result is available.
  • tool_execution_update correctly correlates the active tool ID and refreshes the in-memory tool-stall deadline, but it calls apply().
  • apply() persists every applied transition through pi.appendEntry() and logContinuationTransaction(). There is no distinction between material state changes and high-frequency liveness refreshes.
  • The persisted protocol shape already contains all required state. The defect is write policy, so a protocol-version bump would add migration risk without adding information.

Product intent alignment

  • Golden path: compaction remains invisible recovery infrastructure; a slow provider response after tool completion does not ask the operator to send “continue.”
  • Self-healing: when the progress timer fires during active host work, the coordinator retains ownership and re-arms a bounded check automatically.
  • Fail-closed boundary: an idle host with no correlated progress by the deadline still produces the existing durable, actionable failure. Session replacement, real user input, tool stall, retry, and terminal semantics do not weaken.
  • Truthful durability: live deadline state remains exact in memory; durable checkpoints bound reload staleness without pretending every streaming update is a distinct workflow milestone.
  • UI impact: no UI implementation. The only observable text impact is suppression of the false warning while work is active; true failure/stall warning copy remains unchanged.
  • Repository alignment: existing unit, real-host, soak, audit, install, and source/installed hash gates remain the release path; no manual live-file patching is introduced.

Locked decisions

  1. Host activity is the timeout authority. At a no-tool progress deadline, ctx.isIdle() === false means Pi is still running the turn. The coordinator must retain ownership and must not emit a terminal outcome or warning.
  2. Lifecycle starts remain diagnostic. agent_start and turn_start do not themselves prove successful progress or settlement. They may update epochs, but the timeout decision uses current host activity and the successful terminal boundary remains agent_settled after progress.
  3. Active deferral is bounded and durable. When a progress deadline fires at time at while the host is active, persist exactly one snapshot and matching transaction-log record with unchanged state, lastProgressAt, pending count, and assistant result; set progressDeadlineAt = deadlineAt = at + idleProgressDeadlineMs; increment the phase epoch; emit no outcome or warning; and arm the persisted remaining interval. Rehydrate computes max(0, deadlineAt - now()); a past-due restored deadline therefore fires immediately and re-evaluates current host activity rather than reusing the old decision. If the host later becomes idle without a qualifying settlement/progress event, the next deadline preserves the existing fail-loudly path.
  4. Only high-frequency tool updates are coalesced. Requests, activation, submission, acceptance, assistant results, tool starts, tool completions, pending-count changes, retry transitions, stalls, supersession, settlement, and failures remain immediate durable snapshots.
  5. In-memory liveness remains exact. Every correlated tool_execution_update still refreshes lastProgressAt, toolStallDeadlineAt, deadlineAt, phase epoch, and the live timer immediately.
  6. Timing options have a supported domain. The checkpoint interval and tool-stall deadline must be finite positive integer milliseconds, and toolStallDeadlineMs must be at least 2. Invalid zero, one-millisecond stall, negative, fractional, or non-finite values fail coordinator construction with an actionable option-specific error.
  7. Durable liveness uses a 30-second default checkpoint. For valid options, effectiveCheckpointMs = min(configuredCheckpointMs, floor(toolStallDeadlineMs / 2)), so a shorter configured stall window cannot be invalidated by a slower durability cadence.
  8. Checkpoint origin is durable progress time. On creation or rehydrate, derive the next checkpoint from the latest durable snapshot’s lastProgressAt, falling back in order to its acceptedAt and createdAt. A process reload therefore loses at most one effective checkpoint interval of tool-update freshness. When an active tool is restored, stale durable liveness cannot prove inactivity after process downtime, so rehydrate grants one fresh configured tool-stall interval from now(); this may delay a genuine stall by at most one configured stall interval per reload but prevents a pre-crash uncheckpointed update from being falsely stalled.
  9. No protocol-version bump. The existing version-2 snapshot shape is sufficient. Checkpoint cadence is coordinator policy and test/options configuration, not persisted wire semantics.
  10. No hidden per-update log path. A coalesced update writes neither a session snapshot nor a transaction log record. The checkpoint snapshot produces the existing matching log record once.
  11. Terminal truth flushes. Any material or terminal transition persists the current full in-memory snapshot before/outside its outcome as the existing state machine requires, so checkpointing cannot hide final pending count, deadline, state, or terminal reason.
  12. Existing RED tests are immutable. Additional boundary, reload, log-count, real-host, or soak tests may be added, but the two named regressions may not be weakened to accommodate an implementation shortcut.
  13. Same-process reconcile cannot regress live liveness. Track the latest durable continuation evidence applied for the active transaction. A wake/reconcile with no newer durable snapshot/message/outcome for that transaction—including a wake caused only by queued work—must preserve the current in-memory lastProgressAt, tool-stall/progress deadlines, phase epoch, active-tool correlation, and armed timer. Rehydrate/fold only when newer relevant durable evidence exists; immediate material transitions already flush the current live snapshot before that evidence becomes authoritative.
  14. Rollout and rollback are pi-vcc-only. Add a scoped ./install.sh --pi-vcc [package-source] mode that invokes only vendored pi-vcc stable-mirror synchronization and exact-one package registration. Candidate install uses the committed repo package; rollback uses a byte-preserved pre-install package bundle. Neither path refreshes prompts, extensions, skills, models, or unrelated packages.
  15. Package identity covers the copied tree. Use one shared standard-library package-tree identity algorithm in verifier and installer paths. It enumerates every entry in deterministic relative-path order; hashes entry type, relative path, and permission mode plus regular-file bytes; rejects symlinks and non-file/non-directory entries before any mutation; and verifies the copied stable tree has the same identity before registration. Temporary test-only node_modules must be removed and absent before every source identity, candidate install, and reinstall.
  16. Scoped installation is transactional. Copy the validated source to a uniquely created staging sibling on the stable mirror's filesystem, verify the staged full-tree identity, then rename the current stable mirror to a retained backup and atomically rename staging into place. Update exact-one registration only after the swap. Any staging, identity, swap, or registration failure automatically restores the prior mirror and prior settings before returning nonzero; the backup is deleted only after installed verification succeeds.
