Goal

Add pi-codex-goal to this repository's managed Pi package stack so ./install.sh --pi installs/updates it like the other package-managed Pi extensions, scripts/verify-pi-install.sh treats it as expected, and the Pi docs tell operators that Codex-style /goal functionality is installed by default.

After the repo change is verified, apply the managed install on both intended hosts: the current Dever machine and Aaron's MBP. The rollout should leave pi list showing npm:pi-codex-goal and the local Pi runtime able to resolve the /goal command on next Pi startup/reload.

Decision Attention / Low-confidence Areas

D1 — MBP access path is environment-dependent. The plan assumes the implementation agent can reach MBP through the operator's normal shell/SSH setup. If ssh mbp or the expected MBP repo path is unavailable, stop after committing the repo change and report the exact manual command for MBP rather than guessing host credentials or paths.

D2 — Do not vendor or fork yet. Research selected pi-codex-goal because it best matches simple Codex-style goals. This plan deliberately installs the npm package, not a custom fork. Forking is a future option only if real use exposes missing behavior.

D3 — Existing goal-like packages should not be removed unless present and conflicting. Current Dever settings did not show another pi-goal package. If MBP already has a different goal package, do not remove it automatically unless it registers conflicting /goal commands or tools; report the conflict and ask for a removal decision.

Why this plan exists

Pi currently stops more easily than desired during long tasks. The selected package, pi-codex-goal, provides a simpler Codex-style long-running objective loop: /goal, persistent session goal state, hidden continuation while active, completion via goal tools, and recovery behavior around overflow/provider interruptions.

The correct product behavior is for this capability to be installed by the normal ai-configs Pi setup path. Operators should not need a one-off manual pi install npm:pi-codex-goal that future ./install.sh --pi runs or host rebuilds may omit.

Product intent alignment

This is an operator/agent workflow change. The golden path is ./install.sh --pi: it should install the long-running goal capability without a separate tribal-knowledge step. Verification should make missing packages obvious through the existing scripts/verify-pi-install.sh comparison output.

Safe default: install pi-codex-goal through Pi's package manager like other npm-managed Pi packages. Self-healing expectation: rerunning ./install.sh --pi should add it if absent and update it if already registered. Fail-closed boundary: do not remove or replace other goal packages without evidence of a command/tool conflict.

UI impact: text-only. The change affects installer output, docs, and Pi slash-command availability after install/reload. It does not change a custom TUI component in this repo.

Locked decisions

  • Use pi-codex-goal. Install source is npm:pi-codex-goal.
  • No fork for the first integration. Forking remains a later response to observed gaps, not part of this implementation.
  • Installer owns persistence. Do not rely on one-off host-local manual installs as the source of truth.
  • Verification must use pi list. Package-managed installs should be visible through Pi's package registry, unlike repo-managed extensions under ~/.pi/agent/extensions.
  • Rollout covers Dever and MBP. Dever is local to this session. MBP may require remote command execution; if remote access fails, report an actionable blocker instead of silently declaring success.
