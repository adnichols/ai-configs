Product-owner context

Execution plans currently begin with useful context and goals, but they do not consistently give reviewers a concise product-style account of the change they are about to approve. As a result, a plan can be technically thorough while forcing a product owner, operator, or reviewing agent to reconstruct the actual before/after behavior from phases, file lists, and acceptance criteria.

Why now: an earlier implementation attempt proved the requirement is valuable but was built in stale worktrees. Since then, ai-configs moved plan review to a Herdr-backed architecture and deleted several legacy reviewer agents. Doct and Heddle also advanced substantially. The product requirement remains absent from current branches, but the old patch is no longer a viable merge unit.

Key conclusion: this is a planning-product and enforcement gap, not a customer runtime defect. The correct delivery is a fresh, narrow implementation against current branches: one canonical shared rule, active authoring/review references, and repository-local validator adapters.

What’s new — plans will announce the product change before explaining the build

Product promise: every non-trivial reviewed execution plan will tell a product owner, operator, or agent what will become different—clearly and early—before asking them to evaluate phases, files, or implementation mechanics.

  • Before: reviewers often infer the real behavior change from Goal, rationale, acceptance criteria, and technical phases.
  • After: a standalone early What’s new section provides a behavior-focused headline, one-sentence promise, concrete audience-visible changes, before/after workflow, observable result, and preserved guarantees.
  • What reviewers notice: the product delta is scannable near the top, and review gates flag sections that are missing, late, vague, or merely restate surrounding material.
  • What plan authors notice: active templates and prompts ask for the section directly, so compliance is the default rather than a reviewer repair.
  • Audience-visible result: reviewers can decide whether the planned outcome is correct before investing in technical-detail review.
  • Preserved guarantees and power: Product-owner context, Goal, Decision Attention, acceptance criteria, BDD, technical evidence, historical-plan readability, explicit migration escape hatches, and independent review authority all remain in place.

Goal

Deliver one coherent cross-repository contract on top of current branches:

  1. ai-configs defines the rule once and routes active authoring and Herdr-backed review paths to it;
  2. Doct’s current Markdoc template and config-driven registration/update validators require a compatible early whats-new section;
  3. Heddle’s current semantic HTML template and validator require data-section="whats-new" after the product summary with established historical compatibility;
  4. focused tests prove generation, ordering, rejection, review coverage, installation/synchronization, and migration behavior;
  5. the stale three-repository worktrees are retired only after their relevant intent is preserved and fresh replacements are safely committed or handed off.

Decision Attention / Low-confidence Areas

No product decision required. The desired behavior, repository-specific placements, enforcement surfaces, migration stance, and non-goals are locked below.

  • Repository freshness: implementation must not continue in the stale worktrees. Start from origin/main for ai-configs and current origin/develop for Doct and Heddle.
  • Doct legacy behavior: unchanged historical Markdoc remains readable. A future validated update must add the section or use Doct’s existing explicit, reason-bearing untemplated bypass. Do not invent version-aware template infrastructure in this change.
  • Heddle compatibility: use a new effective-date boundary following its existing current-contract warning/backfill model; do not invalidate completed historical plans merely because the contract advanced.
  • Transport boundary: skills/herdr-reviewers/SKILL.md remains generic review transport. Put the substantive section check in the reviewed-plan packet/gate, not in transport infrastructure.
  • Stale-worktree deletion: removal is allowed only after verifying no unrelated or unique uncommitted state would be lost. Otherwise preserve the worktree and report the blocker.

Why this plan exists

The previous patch touched the right broad product area, but it was based on older repository shapes. On current ai-configs main, eight previously edited specialist plan/reviewer agents no longer exist and reviewed-plan orchestration now uses visible Herdr tabs. Doct’s current template policy is config-driven across TypeScript API and Rust CLI validation, while Heddle’s active HTML contract includes a date-gated migration model. Reusing the old diff would either revive retired architecture or miss current enforcement seams.

This plan therefore preserves the product intent while discarding obsolete implementation assumptions. It favors one canonical semantic rule, adapters at real current boundaries, tests that exercise behavior rather than phrase presence alone, and explicit legacy handling.

Product intent alignment

The golden path is default compliance: a plan author should not need to remember a hidden review convention, and a reviewer should not need to reconstruct the product delta from technical material. Templates and authoring prompts supply the structure automatically; review and validators catch omission or misplacement; errors identify the missing section and expected position.

  • Default workflow: create a normal non-trivial reviewed plan and receive a populated early What’s new section.
  • Inference/defaults: no new flags or manual configuration are required; each repository’s existing template and review flow owns placement.
  • Self-healing: template-generated plans are correct by construction. Historical plans being resumed must be backfilled in the normal edit flow rather than requiring a separate migration command.
  • Fail-closed boundary: new/current-contract plans that omit or misorder the section cannot be marked execution-ready. Explicit legacy bypass remains available only where already supported and must retain its reason/audit trail.
  • Agent-legible errors: validator/reviewer feedback should say that What’s new is missing or misplaced, identify the expected early anchor, and distinguish structural absence from weak/restated content.
  • UI impact: text-only. The visible change is reviewer-facing plan structure and validation feedback; there is no application screen or interaction redesign.

Locked decisions

  1. One canonical semantic rule. skills/planning-workflow/SKILL.md owns the complete definition. Other ai-configs surfaces reference it and carry only the minimum local instruction needed to author or review correctly.
  2. Canonical ai-configs placement. New-plan order becomes Title → Status → Product-owner context → What’s new → Goal → Decision Attention. This preserves product-owner framing and puts the product announcement before technical or execution detail.
  3. Doct placement. The Markdoc section ID is whats-new, inserted after status and before goal in the current local template/config order.
  4. Heddle placement. The semantic HTML contract is data-section="summary" immediately followed by data-section="whats-new", before rationale, authority, functional-impact, and technical sections.
  5. Content contract. The standalone section contains a behavior-focused headline, one-sentence promise, concrete audience-visible changes, before/after workflow, observable result, and preserved guarantees. It must not restate Goal, why, phases, or acceptance criteria.
  6. Active architecture only. Do not restore deleted Pi plan/reviewer agents or retired plan-reviewer skills. Do not encode planning semantics in generic Herdr transport.
  7. Enforcement is layered. Authoring defaults prevent omission; reviewed-plan packets assess content quality and placement; Doct/Heddle validators enforce structural presence/order.
  8. Legacy behavior is preserved, not generalized. Doct retains its existing explicit untemplated/bypass path; Heddle uses its established effective-date warning/backfill policy. No new cross-repo migration framework is introduced.
  9. Trivial-work exemption is unchanged. Only work already exempt from a full execution-plan artifact is exempt from this section.
  10. Stale patches are reference evidence only. Rebuild from current remote branches and remove stale worktrees only after safe preservation and audit.
