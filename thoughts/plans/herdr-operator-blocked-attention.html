Herdr operator-blocked attention for workflow waits

Slug: herdr-operator-blocked-attention · Worktree: block-on-prompt · Repo: ai-configs

Make Herdr tabs/panes report blocked whenever a workflow needs operator action — password prompts, stage approvals, and other human waits — even when the coding agent itself is still working or has settled to idle without asking through Pi UI.

Product-owner context

Operators run multi-step agent workflows in Herdr. When a step needs a human — typing a 1Password password during release, or approving implementation after plan review — the tab often keeps looking busy or idle. The person does not get the same attention signal Herdr already uses for agent blocked (needs input). Work sits until someone notices the quiet prompt.

Key conclusion: this is an operator-attention gap in our workflow stack, not a Herdr product bug. Herdr already has blocked state and notifications. Our delivery and release workflows do not set that state when they need a human, and Pi's lifecycle reporter only marks blocked for Pi UI dialogs and hard failures — not chat-text approval pauses or shell password prompts on sibling panes.

What's new

Today, Herdr blocked mostly means “the coding agent integration said it needs input.” After this change, workflow orchestration can also own a temporary operator-wait signal: password gates, execution-ready approval pauses, and explicit delivery blockers light the same blocked attention path (and optionally a request notification), then clear it when the human action completes or the wait is cancelled.

The mechanism is dual-path because live Herdr behavior requires it: a secondary report-agent source cannot override a pane already owned by herdr:pi, but it can mark a shell-only pane blocked and that blocked pane bubbles to the tab even while another pane stays working. Pi-owned panes need a latch the existing Pi extension honors inside its authoritative reporter.

Goal

When an ai-configs workflow needs operator action, the relevant Herdr tab reports blocked (and preferably shows a short reason) until that action is done — including cases where the agent is not itself reporting blocked.

  • Release gate password prompt on the stable work pane grabs attention.
  • Delivery EXECUTION_READY (and other true operator-approval pauses) grabs attention on the planning pane/tab.
  • Explicit delivery blocker --mark-blocked also sets Herdr blocked attention, not only the ledger stage label.
  • Clearing is reliable: no stuck blocked after approval, gate success/failure, or blocker clear.

Why this exists

  • Heddle release opens an interactive 1Password gate via herdr pane run on the stable work pane. That pane is a shell, not Pi UI, so herdr-agent-state never sees a password prompt.
  • Delivery pauses at EXECUTION_READY for explicit operator approval. Agents often ask in chat and settle to idle; idle does not attract attention like blocked.
  • Live check (2026-08-02): while Pi owns a pane as source herdr:pi, herdr pane report-agent --source workflow:… --state blocked leaves agent_status as Pi's state. On a shell-only pane, the same call sets agent_status=blocked and the tab becomes blocked even if a sibling Pi pane is working.
  • Pi already emits blocked for UI methods (select, confirm, input, editor, custom) via herdr:blocked events. That path is correct and must keep working; this plan extends the same attention outcome to workflow-owned waits.

Product intent alignment

  • Golden path: needing a human automatically lights blocked attention; finishing the human step clears it without a separate remediation command.
  • Safe defaults: Herdr CLI calls are best-effort and never fail the workflow; marker latch still works without herdr on PATH so Pi panes can block; delivery respects DELIVERY_SKIP_HERDR.

  • Do not expand into automatic password detection heuristics or changing Herdr core binaries.

Locked decisions

  1. Dual-path attention helper. One CLI both (a) writes a per-pane operator-wait marker that Pi's herdr-agent-state honors as blocked, and (b) best-effort calls herdr pane report-agent --state blocked with the fixed workflow source for shell/non-Pi panes. Clear removes the marker and best-effort release-agent for that same source/agent pair.
  2. Pinned paths. Source file skills/herdr/scripts/herdr-operator-attention (Python 3 or bash+python, executable). Install copies/links to ~/.agents/scripts/herdr-operator-attention and ~/.local/bin/herdr-operator-attention beside delivery (install.sh near the delivery install block ~1469). Tests: tests/test_herdr_operator_attention.py and extended tests/test_herdr_agent_state.mjs. Heddle gate wrapper test: tests/test_heddle_release_operator_attention.mjs.
  3. Fixed source/agent labels only. Source workflow:operator-attention, agent operator-wait. No public --source override. Do not impersonate herdr:pi.
  4. Marker path and schema.
    • Directory: ${HERDR_OPERATOR_WAIT_DIR:-${XDG_STATE_HOME:-$HOME/.local/state}/herdr-operator-wait}
    • Filename: SHA-256 hex of the exact pane id UTF-8 bytes + .json (collision-free; no slash issues).
    • JSON fields: paneId (string, must equal target pane), message (string), setAt (ISO-8601 UTC), kind (string enum used by delivery: approval | blocker | password | generic), notifyOnSet (bool).
    • Pi reader: ignore missing file; ignore unreadable/malformed JSON; ignore when paneId ≠ current HERDR_PANE_ID; never throw from marker I/O.
  5. CLI surface. 
    herdr-operator-attention set --pane <id> --message "…" [--kind generic] [--no-notify]
herdr-operator-attention clear --pane <id>
herdr-operator-attention status --pane <id>   # exit 0 with JSON; inactive → {"active":false}
    Pane defaults to HERDR_PANE_ID when omitted. Exit codes: usage errors (missing pane/message/unknown subcommand) → non-zero; authoritative marker I/O failure (cannot create dir, write JSON, or delete active marker) → non-zero with stderr explaining the path/error; successful marker write/delete with Herdr CLI/socket failures → exit 0 (Herdr is best-effort only). Delivery and Heddle callers treat any helper non-zero as best-effort (log/ignore; do not fail the primary command).
  6. Idempotence and notifications.
    • set with same pane + same message + already-active marker: no Herdr notification; still best-effort re-publish report-agent blocked (shell path) so state can recover; refresh setAt optional but message unchanged.
    • set that creates a new marker or changes message: write marker; best-effort report-agent; notify once unless --no-notify.
    • clear when inactive: no-op success (delete absent file OK); still best-effort release-agent.
    • Clear never notifies.
  7. Missing Herdr CLI/socket vs marker I/O. When pane id is known, always attempt marker write/delete first. If marker I/O fails, helper exits non-zero (authoritative). If marker I/O succeeds, Herdr subprocesses are skipped or ignored on failure and the helper exits 0. Marker-only success is intentional so Pi-owned panes still latch blocked without herdr on PATH.
  8. Pi desiredState priority. After existing UI blockedCount and failure-blocked, honor operator-wait marker (still above working/idle). Message: UI block label if blockedCount>0, else failure message, else marker message.
  9. Delivery uses state reconciliation, not one-shot event pairs.

    After every ledger mutation that can change stage, blockers, or implementation approval, call one function sync_operator_attention(ledger) (best-effort; no-op under DELIVERY_SKIP_HERDR or missing pane) that derives desired attention from the resulting ledger:

    1. If stage == BLOCKED OR there is at least one uncleared blocker entry while stage is BLOCKED: set --kind blocker --message <latest blocker text> (if blockers empty but stage BLOCKED, message Delivery blocked).
    2. Else if stage == EXECUTION_READY AND implementation approval is not currently approved for the current plan fingerprint (pending/missing/stale/revoked): set --kind approval --message "Approve implementation to continue".
    3. Else: clear.

    Invoke sync_operator_attention after ledger fields update on every path that can change stage, blockers, implementation approval, or the plan fingerprint approval is bound to. Repo source-search baseline includes at least: cmd_stage; bootstrap/update/spawn paths that write a new stage; approve_implementation_locked / start_implementation_locked / revoke; cmd_blocker set and clear; cmd_set when --plan changes (calls reset_implementation_approval while stage may stay EXECUTION_READY); cmd_record when recording fresh planReadinessRequest=pass or changing plan path (both reset approval). During implementation, re-run rg reset_implementation_approval skills/delivery-run/scripts/delivery and wire any additional call sites — do not leave unlisted producers. Do not set operator-wait for completeness-review or quality advisories.

    Required transition tests: enter EXECUTION_READY → set approval; approve → clear even if launch fails; revoke while still EXECUTION_READY → set approval again; blocker --mark-blocked → blocker wins; blocker --clear --stage EXECUTION_READY with approval pending → approval set again; leave EXECUTION_READY → clear; approved EXECUTION_READY then plan/readiness mutation via delivery set --plan or record that resets approval → approval wait restored; DELIVERY_SKIP_HERDR → no helper calls.

  10. Heddle release open-gate. Extract a small testable helper (in the workflow file or _pi/workflows/lib/operator-attention.js) that shells out to herdr-operator-attention. Around interactive open-gate: set --kind password on gatePaneId before paneRunScript; clear in finally covering success, verify-fail return (~1168-1198), timeout, and thrown errors. Host Pi UI prompts stay on existing wrappers. No publish free-text expansion.
  11. Do not auto-move delivery stage to BLOCKED for approval/password waits. Attention blocked ≠ ledger stage BLOCKED.

Acceptance criteria

  1. A shared operator-attention helper can set and clear Herdr blocked attention for a target pane without requiring the coding agent to emit blocked itself.
  2. On a Pi-owned pane, setting the helper while Pi would otherwise be idle/working results in Herdr agent_status=blocked via the Pi extension latch (not only metadata labels).
  3. On a shell-only pane, setting the helper results in that pane agent_status=blocked, and a multi-pane tab becomes blocked when any pane is blocked.
  4. Delivery sync_operator_attention sets approval wait on the planning pane whenever the resulting ledger is EXECUTION_READY with approval not currently valid; approve clears even if agent launch fails; revoke while still EXECUTION_READY restores approval wait.
  5. delivery blocker --mark-blocked sets blocker attention; after blocker --clear --stage EXECUTION_READY with approval still pending, attention becomes approval wait again (not stuck clear).
  6. Heddle release interactive open-gate sets blocked on the work pane before the password prompt and clears after gate open or gate failure (including failure/timeout paths).
  7. Delivery does not treat completeness-review or other agent-owned waits as operator-blocked attention; only true human approval/blocker/password waits use the helper.
  8. Delivery/Heddle never fail the primary workflow because operator-attention helper exits non-zero; direct helper still reports marker I/O failure with non-zero for honest CLI use; marker write/delete proceeds when Herdr CLI is missing; delivery honors DELIVERY_SKIP_HERDR.
  9. Existing Pi UI blocked behavior and process/subagent working semantics remain green under node tests/test_herdr_agent_state.mjs and delivery CLI tests.

BDD scenarios

Shell password wait (release gate)

Given a Herdr tab with a Pi shell pane and a shell-only work pane
When the release workflow begins interactive open-gate on the work pane
Then the work pane reports agent_status blocked with a password/operator message
And the tab agent_status is blocked
When the gate verifies open (or the gate phase fails)
Then the operator-wait signal is cleared from the work pane

Execution-ready approval pause

Given a delivery ledger advancing to EXECUTION_READY on a Pi-owned planning pane
When stage becomes EXECUTION_READY and approval is not yet valid
Then sync_operator_attention sets approval wait even if the agent later settles idle
When the operator runs delivery approve-implementation
Then attention clears even if the dedicated agent launch fails afterward
When revoke-implementation-approval leaves stage EXECUTION_READY
Then approval wait is set again

Explicit delivery blocker vs approval

Given EXECUTION_READY with approval pending (approval wait active)
When delivery blocker "need auth decision" --mark-blocked
Then blocker message wins
When delivery blocker --clear --stage EXECUTION_READY
Then approval wait is restored because approval is still pending

Pi authority is not stolen

Given a pane owned by herdr:pi
When the helper sets operator-wait
Then Pi remains the lifecycle authority source
And blocked is achieved because herdr-agent-state reads the latch, not because a second source overwrote herdr:pi
