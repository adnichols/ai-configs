Summary

Decision: Pilot mixed routing, not a full OpenAI replacement and not a global default-model flip. Keep GPT-5.5 medium as the Pi default because the current coding-plan subscription economics are favorable. Add GLM-5.2 high as a scoped model for planning/orchestration sessions and explicit escalations; GPT-5.5 medium remains the normal code-writing route; GPT-5.5 high and Claude remain escalation/review backstops; Explore handles broad code discovery.

The recent activity profile shows that the largest model burn is long E2E/debug orchestration and repeated review loops, not ordinary implementation turns. The implementation should therefore reduce GPT-5.5 burn by adding an explicit GLM scoped route for orchestration-heavy work, narrowing review reruns, and forcing cheap exploration before expensive implementation packets—without changing the everyday Pi default away from GPT-5.5 medium.

Databricks benchmark alignment

  • Databricks found the coding-agent Pareto frontier includes OpenAI, Anthropic, and open models; this supports mixed routing.
  • They reported GLM-5.2 in the top capability tier and viable for daily-driver coding-agent work.

  • They warned token price alone is a poor predictor of task cost; this plan includes pilot metrics rather than assuming savings.
  • They found harness efficiency matters and Pi can send much less context per turn; this plan keeps routing inside Pi and tightens packets.

Scope and non-goals

In scope

  • Add a GLM orchestration profile distinct from existing GLM reviewer profiles.
  • Add a GLM-5.2 high UI design specialist profile for design direction, visual critique, UX tradeoff analysis, and UI implementation review.
  • Keep both GPT-5.5 medium and GLM-5.2 high in Pi scoped models so the operator can switch between them.
  • Preserve GPT-5.5 medium as the normal Pi default and code-writing route for favorable coding-plan economics.
  • Make Explore the default broad code-discovery path before GPT implementation.
  • Add or update E2E/test-running prompt guidance so long test loops are process/log driven and fixes are delegated narrowly.
  • Add verification and pilot metric collection guidance.

Non-goals

  • Do not remove GPT-5.5 from the system.
  • Do not weaken high-risk pre-PR review gates.
  • Do not migrate every implementation task to GLM.
  • Do not claim cost savings until pilot metrics show reduced GPT-5.5 turn count and token volume.

Workflow usage

run-plan optimized routing

  1. Start in the GPT-5.5 medium default session for ordinary plans.
  2. For plan construction that is orchestration-heavy, review-synthesis-heavy, UI-design-heavy, or dominated by long test/debug loops, use one of two explicit invocation paths: switch the active Pi scoped model to GLM-5.2 high before starting the planning/run-plan session, or keep the GPT-5.5 default parent and invoke orchestrator-glm as a subagent with a bounded planning packet.
  3. Use Explore before implementation whenever target files or contracts are not already known.
  4. Send developer-mid bounded implementation packets containing target files, intended behavior, verification commands, and relevant snippets.
  5. Escalate to developer-high only for complex implementation or when medium fails on a well-scoped task.
  6. Invoke ui-design-glm for UI intent before coding and for UI/UX review after implementation.
  7. Use risk-based review: GPT review remains the default substantive safety pass; GLM review is added where independent model diversity is valuable.

pre-pr-implementation-review optimized routing

  1. Use quality-reviewer for the primary production-safety review leg on substantive diffs.
  2. Use glm5.2-high for applicable normal high-risk bounded review; use glm5.2-xhigh only for very-high-stakes final/exceptional-risk review such as security-critical, data-loss, destructive migration, auth/privacy, major persistence/concurrency, release-blocking, or prior-review-missed-risk scenarios.
  3. Use Explore to cheaply verify file references, impact scope, and reviewer claims before spawning implementation fixers.
  4. Use developer-mid for concrete fixes and targeted tests; escalate to developer-high only for complex or failed fixes.
  5. Use orchestrator-glm for synthesis and routing when there are multiple findings, conflicting reviewer opinions, or expensive retry loops.
  6. Use ui-design-glm when the diff changes visible UI, interaction design, accessibility behavior, or design-system conventions.

  • E2E/test-running guidance separates long log/process supervision from code-writing fixes.
