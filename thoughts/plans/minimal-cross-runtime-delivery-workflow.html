Product-owner context

Conclusion: this is an operator workflow defect, not a stale-test or documentation-only problem. The current delivery CLI identifies itself as shared infrastructure but executes Pi-specific handoffs at launch, runtime verification, completeness review, and reflection. An OMP caller can therefore create a Pi session unintentionally.

OMP does not need Pi’s native-plan-mode assumptions to produce a reviewed Doct plan. The desired first release is deliberately narrow: retain trustworthy reviews but display only the operator’s real state—planning, implementing, reviewing, PR, done, or blocked.

Why this exists

The delivery CLI’s durable ledger, locks, fingerprints, evidence records, and Herdr label updates are valuable shared primitives. The Pi launcher, Pi environment validation, visible Pi/Grok completeness transport, and ~/.pi reflection sink are runtime-specific policy mistakenly embedded in the shared path. The smallest safe change separates that policy without rebuilding delivery.

Product intent alignment

The golden path makes the safe action obvious: detected runtime → persisted profile → only compatible handoffs. It removes an accidental cross-runtime transfer, fails closed for ambiguous ownership, and presents six labels rather than implementation-detail stages. No automatic recovery may change a ledger’s runtime after meaningful work begins; that boundary remains fail-closed and actionable.

Locked decisions

  • Runtime and profile are first-class ledger fields: omp-lite and pi-full.
  • Detection order is explicit CLI value, a fully identified ledger, OMPCODE=1, Pi markers, then a failure with --runtime omp|pi guidance.
  • A pre-profile schema-v1 ledger is a recognized legacy Pi run, not a new ambiguous run: atomically backfill it to runtime=pi/workflowProfile=pi-full with a history entry on first read. An explicit attempt to convert that legacy run to OMP fails and instructs the operator to start a new run. This compatibility backfill is not an operator-selected runtime change.
  • OMP Lite renders only PL:, I:, R:, PR:, D:, and B:. Its detailed-stage mapping and evidence gates are fixed below; REFLECT and ADVERSARIAL_QA never become visible OMP phases.
  • OMP Lite execution authorization keeps the current owner; it does not start a new implementation tab/process or choose a Pi model profile.
  • OMP Lite completeness is an independent @completeness task pinned to xai/grok-4.5:high. delivery completion-review --prepare creates and durably records a cryptographically random COMPLETENESS_REVIEW_RESPONSE_ID, then returns it in the reviewer packet. The driver writes thoughts/validation/<plan-slug>-completeness-review.md, which begins at byte zero with exactly these seven LF-terminated ASCII lines, in this order and with no leading/trailing whitespace: <!-- OMP_COMPLETENESS_RESPONSE -->; COMPLETENESS_REVIEW_RESPONSE_ID: [0-9a-f]{32}; REVIEWER_IDENTITY: [A-Za-z0-9._-]+; PLAN_SHA256: [0-9a-f]{64}; WORKTREE_FINGERPRINT: [0-9a-f]{64}; VERDICT: COMPLETE|INCOMPLETE; <!-- /OMP_COMPLETENESS_RESPONSE -->. The parser rejects missing/extra/reordered lines, non-exact casing or spacing, an invalid value, and any occurrence of an envelope field name elsewhere in the artifact. The driver then runs delivery completion-review --accept --artifact <path> --response-id <id>. Under the existing ledger lock/revision CAS, acceptance requires pending ID = CLI ID = artifact ID; artifact reviewer identity, plan SHA-256, and worktree fingerprint must each match both pending-request metadata and the current recomputed identity. One atomic ledger replacement consumes the pending ID and creates completeness evidence/history, so missing, malformed, duplicate, wrong, replayed, or mismatched responses fail without partial consumption. It never creates a Pi tab, invokes --kind pi, or requires Pi environment variables.
  • Pi Full remains behaviorally unchanged in this first slice. Pi-only lifecycle requirements stay inside Pi Full.
  • OMP Lite review retains a lightweight PM outcome check, canonical autoreview, and the completeness contract above; reflection and adversarial QA are not completion gates.

Acceptance criteria

  1. With OMPCODE=1, bootstrap/spawn persist runtime=omp and workflowProfile=omp-lite; explicit Pi persists pi-full. A pre-profile ledger atomically backfills only to pi-full; a new markerless run fails.
  2. A new ambiguous runtime exits non-zero with corrective --runtime omp|pi guidance and creates no misleading ledger. A legacy ledger cannot be changed to OMP in place after backfill.
  3. OMP spawn uses --kind omp; no OMP Lite command launches --kind pi, including execution authorization and completeness preparation/acceptance.
  4. Pi Full preserves its existing dedicated handoff, implementation profile checks, and visible completeness transport.
  5. For every OMP Lite detailed stage, status/board render the macro mapping below and never show Pi-only stage labels such as RF:.
  6. OMP planning guidance explicitly uses normal coding mode and never enables, reads as required, or recommends native plan mode.
  7. OMP Lite cannot reach PR without current PM outcome, autoreview, and an artifact beginning with the exact seven-line response envelope defined in Locked decisions. Pending, CLI, and artifact response IDs match; artifact metadata matches pending-request metadata and the current recomputed identity. It cannot reach DONE without final verification and PR evidence.
  8. Absent, malformed, duplicated, reordered, wrong, or replayed response-envelope fields; non-exact line syntax; an envelope-field occurrence outside the opening response block; INCOMPLETE verdicts; stale or mismatched fingerprints/reviewer identity; and Pi-transported OMP completeness evidence are rejected. Under the existing ledger lock/revision CAS, validation, pending-ID consumption, completeness evidence creation, and history recording occur in one atomic replacement; a conflict or interruption records neither acceptance nor consumption. Changing the plan or worktree after acceptance requires a fresh OMP reviewer invocation.
  9. Status, board, help, skills, and affected OMP/Pi quick-reference guidance name the persisted runtime/profile and the compatible next action.
