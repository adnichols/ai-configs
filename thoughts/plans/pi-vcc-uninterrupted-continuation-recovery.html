Pi VCC — Uninterrupted Continuation Recovery

Replace race-prone continuation inference and duplicate recovery paths with one explicit compaction-attempt contract, one coordinator authority, and real-host proof that active work resumes without an operator typing continue.

Product-owner context

Situation. Pi compacts long conversations to stay within model context limits. During NOD-1504, compaction repeatedly aborted active model turns and then left Pi idle. The operator had to type continue three times.

Why now. The live transcript supplies a deterministic failure signature: an active semantic compaction request is stranded, the 80% hard backstop later calls Pi’s aborting compaction API, and no continuation transaction is created. Existing tests passed because they bypass the real percentage-extension and next-turn timing.

Key conclusion. This is a runtime workflow defect, not stale evidence. The fix must make context maintenance transparent: active work resumes exactly once without operator intervention, while genuinely completed work stays complete.

What’s new — compaction becomes invisible maintenance

Promise: when Pi compacts during unfinished work, it resumes the next concrete step automatically and exactly once.

Deliver one coherent continuation flow in which every compaction attempt has explicit product intent, every active attempt reaches the package coordinator, and end-to-end verification proves that the reported NOD-1504 pause cannot recur without a loud terminal failure.

Why this plan exists

Prior continuation plans hardened individual races and added retries, but the current implementation still contains parallel authorities and schedule-time inference. The NOD-1504 session demonstrates that passing unit/soak suites do not prove the golden path. A zero-tech-debt cutover is required rather than another fallback.

Authority and inputs

  • NOD-1504 Pi transcript: compactions 4826c519, 4a4f32b4, and db1d1b32, each preceded by stopReason: aborted and followed only by manual continue.
  • ~/.pi/logs/pi-vcc.jsonl: those compactions have interruptedInFlightTurn:false, requiresContinuation:false, no intent, and no coordinator transaction lifecycle.
  • Pi 0.84.0 AgentSession.compact(): always calls abort() before manual compaction.
  • Source/live install verification: package and extension hashes match; exactly one package registration and extension path are active.

Current implementation reality

  1. compact_context creates pendingModelCompaction, but a stale global uninterpretedFailure can prevent it from running indefinitely.
  2. The 80% hard backstop can supersede that request. Its attempt omits semantic intent instructions and only supplies a resume message for provider overflow.
  3. The interruption snapshot is taken at turn_end after delivered tool IDs are removed, before the scheduled call to Pi’s aborting compaction API. It can therefore report no interruption while a subsequent model turn is actually aborted.
  4. The extension contains copied continuation protocol constants/wire construction, coordinator publication, legacy direct-send recovery timers, and runtime authority selection. The package separately owns the canonical coordinator.
  5. The package already rejects legacy authority, so the extension’s legacy authority branch has no supported runtime caller.
  6. resumePolicy:"auto" exists only to infer whether a model-requested compaction should resume. The product intent is clearer: compact_context means active maintenance; terminal commands are separate surfaces.
  7. The real-host fixture pi-vcc-actual-compact-context-trigger.ts directly calls ctx.compact(). It does not exercise the registered tool, percentage thresholds, stale failure state, hard-backstop supersession, or a model turn starting before compaction.

Intended end state

Compaction timing and continuation delivery are separate, single-owner concerns. The percentage extension creates one explicit attempt record and decides when to call Pi; the pi-vcc package coordinator is the only component that persists, sends, retries, reconciles, and settles continuation work.

Golden-path invariant: an active compaction attempt must produce exactly one durable coordinator outcome—settled after autonomous model progress, superseded by genuine independent input, or failed loudly with actionable guidance. Silent idle is not a terminal state.

Final product surface

  • compact_context has no resumePolicy argument. Invoking it always means “compact this active workflow and continue.”
  • /compact-now is terminal maintenance: compact without starting another turn.
  • /pi-vcc without follow-up text is terminal. Its explicit follow-up form remains terminal to the coordinator and sends that user message exactly once after successful compaction; failed/no-cut command attempts do not invent or replay follow-up work.
  • Hard-backstop intent is resolved at actual start from a monotonic agent_start generation plus an agentActive latch cleared only by agent_settled. A completed response stays terminal unless a later agent_start occurred; an unfinished scheduled response stays active even if settlement races the timer. turn_start, message_start, cleared tool IDs, and ctx.isIdle() never override that decision.
  • Host overflow is active only when overflowRequiresRetry is true. Pi host-threshold compaction is active only when the package hook’s interruption snapshot or explicit active intent says so; otherwise it is terminal.
  • A pending active semantic request is never anonymously replaced by the hard backstop. Threshold escalation starts that same attempt immediately.

Product intent alignment

  • Obvious default: active work continues; no flag or operator command is needed.
  • Self-healing: compaction aborts are absorbed into the same workflow through the durable coordinator.
  • Fail closed: duplicate ownership, invalid persisted protocol state, expired retries, or ambiguous independent input stop loudly rather than guessing.
  • Actionable failure: the coordinator is the source of truth and emits one ctx.ui.notify(..., "warning") at terminal failure. The literal contract is Pi-vcc continuation failed (transaction=<id>; attempt=<id>; retries=<count>/<limit>; reason=<terminalReason>). Inspect: jq -c 'select(.transactionId=="<id>")' ~/.pi/logs/pi-vcc.jsonl. Manual recovery: return to this Pi session, inspect the interrupted task state, then send “continue” once.
  • Dissonance cleanup: package README, tests, soak scripts, and real-host fixtures must describe and prove the same sole-authority architecture.

Locked decisions

  1. The package coordinator is the sole continuation authority. Delete extension-owned legacy send/retry queues, copied wire publication, and authority switching.
  2. Use two deliberately distinct types. Runtime CompactionResumeIntent = "active" | "none" exists only before/during compaction and is never serialized. Wire/persisted ContinuationResumePolicy = "active" | "terminal" remains the V2 protocol vocabulary. The sole translation occurs when compaction details or a coordinator request are created: runtime active maps to wire active; runtime none maps to wire terminal. Neither field is optional after attempt creation, and none is never a wire value.
  3. Keep V1 read adaptation because persisted session histories are real consumers; write only V2. V1 active/terminal preserve their meaning; V1 auto is accepted only for compact_context and deterministically adapts to active; V1 auto on any other origin and every V2 auto payload are invalid persistence. This is data compatibility, not a second runtime mode.
  4. Trust a standalone compact_context tool invocation as the model’s interpreted semantic boundary. Only same-batch outstanding siblings can defer it.
  5. If the hard threshold arrives while a semantic request is pending, escalate that attempt rather than create a replacement attempt.
  6. Track agentActive from agent_start until agent_settled and a monotonic agent generation. A scheduled attempt stores the generation and whether its source response was complete. At actual start: a pending semantic request is active; a source response that was incomplete is active; a completed response is active only if the generation advanced and the latch is active. Freeze that result on the attempt before calling Pi’s aborting API.
  7. Acceptance requires source and installed-candidate real-host runs. Mock-only soak success is insufficient.

Acceptance criteria

  1. AC-1 Autonomous active continuation. The exact NOD-1504 sequence reaches later assistant progress without any real-user continue message.
  2. AC-2 Exactly once. Every active attempt has one durable continuation acceptance and one terminal coordinator outcome; no duplicate delivery across retries.
  3. AC-3 Terminal restraint. Completed assistant responses and terminal maintenance commands do not trigger another model turn.
  4. AC-4 Pending intent survives escalation. A pending semantic request blocked by same-batch siblings retains its identity and active intent if the hard backstop fires.
  5. AC-5 No stale failure deadlock. An earlier tool failure cannot strand a later standalone compact_context request.
  6. AC-6 Sole authority. The extension contains no legacy authority switch, direct continuation send timers, copied protocol wire constructor, or duplicate retry state machine.
  7. AC-7 Honest real-host proof. Source and installed runs load the actual package plus percentage extension and exercise Pi 0.84’s real aborting compaction method with file-backed session persistence.
  8. AC-8 Loud bounded failure. If autonomous continuation cannot be accepted or progress within bounded retries, the coordinator emits exactly one warning notification using the locked literal contract: transaction, attempt, retry count/limit, terminal reason, transaction-filtered jq log command, and instruction to inspect the interrupted state then send one continue in the same Pi session.
  9. AC-9 Persisted compatibility. V1 active/terminal and compact-context auto→active reconcile without duplicate delivery; invalid V1 auto origins and every V2 auto record fail closed; all new requests are V2 without auto.
  10. AC-10 Install integrity. Source, stable mirror, and live extension hashes match with exactly one registration before live acceptance.

BDD scenarios

BDD-1 — semantic compaction after an interpreted failure

Given an earlier tool failure and a later standalone compact_context call, when its tool result is delivered, then the request compacts without waiting for a completed assistant response and resumes exactly once.

BDD-2 — reported NOD-1504 race

Given a completed source turn schedules compaction at generation N, when agent_start advances to N+1 before the timer calls Pi’s real compact(), then the actual-start latch marks the attempt active, the abort produces one coordinator request, and later assistant progress occurs without user input. The paired counterexample with no later agent_start remains terminal.

BDD-3 — hard backstop without semantic request

Given unfinished work crosses the hard threshold, when compaction aborts the active run, then the hard-backstop attempt resumes once and settles.

BDD-4 — final response at hard threshold

Given a completed final assistant response, when hard-backstop maintenance compacts, then no continuation request or new model turn is created.

BDD-5 — active no-safe-cut or cancellation

Given compaction already occurred, is too small, is cancelled, or fails, when active work was interrupted, then the coordinator retries/resumes once; the same outcomes on terminal maintenance do not resume.

BDD-6 — sibling tools still outstanding

Given compact_context shares a tool batch, when sibling results remain pending, then compaction waits; after all results are durable it starts the same attempt without losing intent.

BDD-7 — independent input supersedes

Given a queued continuation, when genuine model-driving user input arrives first, then the coordinator records independent_input and does not add another continuation.

BDD-8 — reload and persisted protocol

Given V1 active, terminal, or compact-context auto records, when Pi reloads, then active/terminal are preserved and auto deterministically becomes active without duplicate delivery. V1 auto from another origin and V2 auto are rejected as invalid persistence; no new V1 or auto record is written.

BDD-9 — bounded failure guidance

Given all coordinator acceptance/progress retries expire, when the transaction fails loudly, then the coordinator emits exactly one warning notification matching the locked literal contract; its jq command selects that transaction from ~/.pi/logs/pi-vcc.jsonl, and its manual action is to inspect the interrupted state then send one continue in the same session.

BDD-10 — repeated compaction soak

Given at least 100 mixed active/terminal/fault compactions, when the audit runs, then every active transaction has exactly one runtime-matching durable delivery and every transaction reaches an allowed terminal state.

BDD-11 — complete initiator and trigger coverage

Given every protocol initiator and percentage-extension variant, when its real dispatch path executes, then compact-context resumes; percentage/Grok resume only when active; host-threshold resumes only when interrupted; overflow resumes only when retryable; compact-now and plain pi-vcc remain terminal; and successful pi-vcc follow-up sends exactly one direct user message without coordinator duplication.

Verification strategy

  1. RED: actual stale-failure + pending semantic request + next-run abort fails before production edits.
  2. GREEN: focused extension/package tests prove the contract and deleted assumptions.
  3. Runtime smoke: deterministic Pi host runs the actual tool and compaction API, ending in later assistant progress.
  4. Persistence: file-backed session and log audit prove exact transaction lifecycle.
  5. Scale/fault: 100-compaction source and installed soaks cover retries, duplicates, aborts, no-cut, reload, and terminal restraint.
  6. Install: the scoped --pi-vcc transaction and injected-failure rollback tests cover package, registration/settings, and live extension as one unit; hash/registration checks prevent testing a different candidate than the live runtime.

Residual risk / not examined: a third-party provider may have unique streaming timing not reproduced by the deterministic faux provider. This does not weaken the pre-PR gate because the defect is in Pi host lifecycle ordering, which the real host exercises. A later live long-running delivery is useful observation, not a PR blocker.
