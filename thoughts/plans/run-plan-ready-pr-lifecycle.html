Goal

Update ai-configs workflow guidance so an agent running /run-plan <plan>, a Doct Build Plan request, or a pre-PR review inside run-plan no longer stops at a partial handoff. The expected golden path is one continuous lifecycle:

  1. execute the plan through implementation and phase verification;
  2. run an implementation-stage PM review and complete any plan-required corrective work it uncovers;
  3. run the GPT plus applicable GLM pre-PR implementation review using the current GLM routing rules;
  4. verify the branch is fresh with the target branch before PR creation, rebase automatically when safe, and rerun invalidated verification/reviews;
  5. commit, push, and open the PR without requiring the operator to ask again;
  6. monitor PR feedback, checks, review decision, and mergeability until the PR is ready to go, automatically rebasing and updating the PR when it becomes stale or conflicted and the conflict is within scope.

Decision Attention / Low-confidence Areas

No product decision required. The user intent is explicit: make the default plan-run workflow carry work all the way through PM review, applicable pre-PR review, PR creation, and mergeability-safe monitoring.

  • GLM routing is resolved: latest main split GLM review profiles into glm5.2-high and glm5.2-xhigh, with quality-reviewer-glm retained only as a legacy xhigh compatibility alias. This plan must preserve that routing and say “applicable GLM,” not mandatory quality-reviewer-glm for every PR.
  • Scope boundary: this plan changes repo-owned prompt/skill guidance and install/readme references only. It does not change Pi core, Doct services, GitHub APIs, or the doct-agent CLI.
  • Rebase safety: automatic rebase is required for routine stale branches, but must fail closed on conflicts outside scoped files or product decisions.

Why this plan exists

Observed workflow pain: plan runs often complete implementation but do not automatically run the full pre-PR gate, do not open the PR, or open a PR and monitor comments without checking mergeability and rebase/conflict state. That exports routine orchestration back to the operator, who then has to tell agents to run missing reviews, open the PR, or rebase after GitHub marks the branch out of date.

The fix is to make the shared workflow contract unambiguous and current with the latest GLM skill model routing. Agents should treat “run the plan” as “deliver a ready PR,” not as “finish code and wait for another command.”

Product intent alignment

This work affects agent/operator workflows. The correct path should be obvious and automatic: when a user asks to run a plan or clicks Build Plan, the agent should execute the plan through a ready PR instead of exposing internal review/PR/rebase steps as separate chores. Routine stale-branch and mergeability issues should be self-healed by fetching, rebasing when safe, rerunning affected verification, and pushing with lease. Locked decisions

  1. Run-plan is the source of truth. Do not duplicate lifecycle orchestration in Build Plan or pre-PR review; those surfaces hand off to or return to run-plan.
  2. Implementation-stage PM review is mandatory before PR creation. If it reshapes the plan, run-plan must execute the added corrective work and rerun invalidated gates before PR creation.
  3. Pre-PR review means GPT plus applicable GLM. GLM is used for high-risk scopes and can be truthfully skipped for low-risk/docs-only/UI-copy/tests/narrow follow-ups with a recorded classification.
  4. Final or exceptional-risk GLM uses glm5.2-xhigh. Normal high-risk bounded GLM uses glm5.2-high. Legacy quality-reviewer-glm remains compatibility-only.
  5. Mergeability is part of readiness. A PR is not “ready to go” unless GitHub reports it mergeable with the target branch after comments/checks/reviews are addressed.
  6. Automatic rebase is required for routine stale branches. Stop only when conflicts affect out-of-scope files or require a product decision.

BDD scenarios

BDD1 — PM review finds missing outcome work

Given an agent has completed all currently checked plan phases, when the implementation-stage PM review finds the shipped behavior does not fulfill the intended outcome, then run-plan updates the plan, executes the missing work, reruns affected verification and applicable reviews, and does not open the PR until the PM gap is resolved or blocked by a real decision.

BDD2 — Clean run proceeds to PR without another user command

Given implementation, PM review, scoped quality review, applicable GPT/GLM pre-PR review, final verification, and base freshness all pass, when run-plan reaches OPEN_PR_READY, then it continues immediately to commit, push, PR creation, and monitoring instead of replying “ready to open a PR.”

BDD3 — Low-risk GLM skip remains truthful

Given a docs-only or low-risk copy/test change, when pre-PR review classifies GLM as not applicable, then the artifact and PR body record the low-risk skip decision and do not invent a GLM verdict.

BDD4 — High-risk GLM uses active profiles

Given a plan touches auth, data loss, persistence, concurrency, migrations, release risk, or another P1/P2 surface, when run-plan or pre-PR review launches GLM, then it uses glm5.2-high for normal bounded review or glm5.2-xhigh for final/exceptional-risk review, not the legacy alias for new routing.

BDD5 — Branch is stale before PR creation

Given the target branch moved after implementation reviews, when run-plan performs the pre-PR freshness gate, then it fetches and rebases safely, reruns affected verification and any review gate made stale by changed diff context, and only opens the PR after the branch is fresh or reports a conflict blocker.

BDD6 — PR becomes unmergeable after opening

Given an open PR was previously clean, when GitHub reports the branch is out of date, conflicted, or not mergeable, then the monitoring loop fetches and rebases when conflicts are in scope, reruns affected verification, pushes with lease, and keeps polling until GitHub reports mergeable or an unsafe conflict requires a user decision.

BDD7 — Build Plan inherits full lifecycle

Given a Doct Build Plan comment invokes plan-reviewer-build, when the plan path is valid, then the bridge delegates to run-plan and keeps the Doct claim active until durable run state, PR URL, or a concrete blocker exists; it must not bypass PM review, pre-PR review, PR creation, or monitoring.
