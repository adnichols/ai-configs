Pi VCC Continuation Guarantee Plan

Make compaction transparent to an active Pi agent run: after any compaction attempt that intersects active work, the run either demonstrably continues or Pi surfaces a durable, actionable failure instead of silently settling.

Decision Attention

  • Guarantee boundary: an extension cannot guarantee provider/network availability. The product guarantee is therefore: pi-vcc never silently leaves an active run idle because of compaction. It retries recoverable delivery, confirms lifecycle progress, and fails loudly with durable evidence when Pi itself cannot start or sustain the next turn.
  • Required host contract: current ExtensionAPI.sendMessage() returns void, while Pi launches the async send in the background and reports rejection separately. Synchronous try/catch is not an acknowledgement. The implementation must not log “delivered” from that return alone.
  • Install topology: pi-vcc is a separately installed package while percentage-compaction.ts is copied as a standalone extension. A module singleton cannot be assumed to cross that boundary. The coordinator contract must be carried through typed session entries/messages and adapters, not a shared in-memory import.
  • Host-change gate: lifecycle attribution must be proven in a host-faithful harness before legacy recovery paths are removed. If current public events cannot correlate the injected custom message to the next run, stop this implementation slice and make a narrow change in the Pi source repository; never patch installed dist.
  • Upstream drift: the vendored package is reviewed only through upstream 0.3.18 while upstream is newer. Re-review host/API drift before modifying continuation semantics, but do not mix unrelated upstream uptake into this fix.
  • No product decision required: continue active work by default; only a real completed, blocked, awaiting-user, or explicitly stopped state may settle without auto-continuation.

Goal

Replace today’s collection of timers and fire-and-forget nudges with one compaction-local continuation transaction whose state is explicit, idempotent, observable, and driven by Pi lifecycle evidence.

Why this plan exists

Recent sessions show pi-vcc compacting large active histories and then injecting a continuation. The sampled 1pw-vault-alt event at compaction 6f06a6de did resume successfully, but the log called the message “delivered” immediately after a void API call. That proves the current success metric is weaker than the desired guarantee. Other unresolved risks—separate continuation authorities, indefinite waiting on missing tool IDs, stale semantic requests, exact English error matching, and event-order assumptions—can still strand work or hide a failed recovery.

Product intent alignment

  • Golden path: the agent calls compact_context or reaches the hard backstop; compaction happens; active work continues automatically with no user intervention.
  • Self-healing: transient busy/streaming/race conditions are absorbed by one pending transaction and retried at safe lifecycle boundaries.
  • Fail closed: do not start duplicate model turns, inject continuation ahead of unresolved tool results, or guess that blocked/completed work should continue.
  • Actionable failure: terminal recovery output names the attempt ID, compaction ID, last observed lifecycle state, pending tool IDs, retries performed, log path, and exact manual next action.
  • UI impact: text-only. Normal success stays quiet; only terminal recovery failure adds an operator-visible warning.

Locked decisions and invariants

  1. One logical owner with an install-safe protocol: the package coordinator is the sole state writer and continuation sender. The package hook and package /pi-vcc command call it directly. The standalone percentage extension first appends a durable pi-vcc-continuation-request custom entry, then emits a pi-vcc:continuation-requested wake on pi.events. The package listener reconciles unread request entries before acting, writes outcome entries, and unsubscribes/re-subscribes on reload so lost or duplicate wake events are harmless. No adapter holds an independent continuation retry timer, and no shared module singleton is assumed.
  2. Initiator matrix is exhaustive: package /pi-vcc, compact_context, hard-backstop, host threshold/overflow, no-safe-cut, cancellation, and failure each map to an origin, attempt ID, optional request ID, continuation policy, and typed outcome.
  3. Continuation required is explicit: capture the decision before compaction from active agent lifecycle plus branch shape. Completed/blocked/awaiting-user state is not inferred from brittle English regex when authoritative lifecycle or compact intent exists.
  4. Acceptance is not delivery: a call or queue insertion is submitted. Matching continuation custom-message message_start proves consumed; a non-error, non-aborted assistant result proves progressed; final agent_settled after progress proves settled. Generic agent/turn start is diagnostic only. Settlement without consumption re-arms; settlement after terminal error/abort retries within the deadline or becomes failed_loudly.
  5. Never wait forever: the watchdog starts when the transaction is created, including while waiting for outstanding tool results.
  6. At-least-once trigger, at-most-one active turn: retry submission only when no matching continuation has been consumed and no superseding real work has started. Once consumption is observed, retries stop until settlement classifies the outcome.
  7. Delivery mode is locked: use deliverAs: "steer" both while streaming and with triggerTurn: true while idle. Do not use nextTurn, because attaching recovery to a future user message obscures supersession and can replay stale work.
  8. New work supersedes recovery safely: a real user message or independently consumed non-continuation input marks the transaction superseded, not failed, and prevents a duplicate nudge.
  9. Semantic requests survive unrelated attempts: PendingModelCompaction has a requestId, and an attempt has originatingRequestId. Clear the pending request if and only if those IDs match, or the request is explicitly cancelled/superseded.
  10. Structured outcomes: recovery is driven by typed reason/outcome metadata, not exact error strings. Text matching remains only a compatibility fallback.
  11. Session teardown is terminal and durable: session_shutdown cancels timers and appends a sanitized terminal entry before quit/new/resume/fork. Reload persists the pending transaction and rehydrates it on session_start; other replacement reasons terminalize as superseded: session_replaced. No delayed send may target a replaced session.
  12. Log schema is allowlisted: info-level transaction events may contain only transaction/compaction/attempt/request IDs, typed reason/outcome, retry count, elapsed deadline, pending-tool count, and numeric lifecycle epochs. Never log preserve, message content, tool-result content, credential-bearing errors, or raw tool IDs.
  13. Compaction is optional; continuation is not: no-safe-cut, cancellation, summary failure, core race, and successful compaction all converge on the same continuation state machine when active work was interrupted.

Acceptance criteria

  1. AC1: Every active-turn compaction attempt reaches exactly one terminal continuation state: settled, superseded, or failed_loudly; none remain pending indefinitely, including across reload/session replacement.
  2. AC2: Package /pi-vcc, semantic/hard-backstop attempts, host/core attempts, cancelled/failed attempts, and no-safe-cut use the same persisted protocol and cannot create duplicate active turns despite separate install locations.
  3. AC3: Logs never claim continuation_delivered from a void sendMessage return. They distinguish created, waiting, submitted, consumed, progressed, settled, superseded, retrying, and failed using only allowlisted metadata.
  4. AC4: Async host rejection, queue insertion without consumption, matching-message consumption, settlement after success/error/abort, missing tool results, user intervention, replacement agent inputs, and session shutdown/reload have deterministic tests.
  5. AC5: A queued compact_context request is not lost because another compaction attempt completes or fails; mismatched request IDs cannot clear it.
  6. AC6: Terminal recovery failure is visible and actionable; normal recovery is silent except sanitized structured logs.
  7. AC7: The installed stable mirror and real Pi host pass an automated multi-compaction soak across active tool chains, completed turns, cancellations, and injected failures.
  8. AC8: Session quit/new/resume/fork cancels pending timers and writes a terminal disposition before teardown; reload rehydrates the transaction or writes failed_loudly, and no stale send fires in the replacement session.

BDD scenarios

S1 — Active tool chain, successful compaction

Given an agent has outstanding tool work, when pi-vcc compacts the turn, then one transaction waits for tool safety, submits once, observes a new agent/turn start, and the run continues without user input.

S2 — Async send rejection

Given the host accepts the extension call but its async prompt start rejects, when no attributable lifecycle start occurs, then the coordinator retries at a safe boundary and never records false delivery.

S3 — Queue accepted but never consumed

Given a steer continuation is queued during streaming, when the agent settles without a matching continuation custom-message message_start, then agent_settled re-arms recovery or fails loudly within the bounded deadline; settlement itself never counts as success.

S4 — Missing tool result

Given an outstanding tool ID never arrives, when the deadline expires, then recovery does not wait forever; it emits a fail-closed warning with the missing IDs and manual continuation instruction.

S5 — User resumes first

Given a continuation is pending, when a real user message starts a new run, then the pending transaction becomes superseded and cannot later inject a duplicate continuation.

S6 — Completed or blocked semantic boundary

Given compact intent explicitly says the task is complete, blocked, awaiting user, or no-auto-resume, when compaction completes, then no continuation transaction is created.

S7 — Concurrent semantic and hard-backstop attempts

Given compact_context request A is queued and unrelated hard-backstop attempt B races, when B completes or fails with a different originatingRequestId, then A remains pending and runs later exactly once.

S8 — Repeated compactions

Given a long autonomous session crosses multiple thresholds, when at least ten compactions occur under mixed tool/failure timing, then each required transaction terminates and the session never needs a human “continue.”

S9 — Terminal provider result after consumption

Given a matching continuation message was consumed, when the assistant ends with terminal error or abort and the agent settles, then the transaction is not successful; it retries within policy or becomes failed_loudly.

S10 — Session replacement and reload

Given a transaction is pending, when the session quits, switches, forks, resumes, or reloads, then timers are cancelled before teardown; replacement terminalizes as superseded, while reload persists and rehydrates or fails loudly without sending into the wrong session.

S11 — Manual package command parity

Given /pi-vcc or /compact-now is invoked during active work, when compaction succeeds, fails, cancels, or has no safe cut, then the same initiator/outcome protocol and continuation rules apply.

Verification strategy

  1. Pure transition tests prove all states and idempotence.
  2. Adapter tests prove existing cut/no-cut behavior remains safe.
  3. Host-faithful tests prove async failure and queue lifecycle semantics.
  4. Installed-runtime soak proves the shipped extension, not only source mocks.
  5. Session-log audit proves no transaction remains unresolved and no false “delivered” terminology remains.

Delivery order

P1 host contract/protocol gate → P2 shadow-mode adapter integration with legacy authority intact → P3 lifecycle/teardown → P4 semantic policy → P5 full fault/soak coverage and one-time authority flip → P6 rollout/audit. Legacy send paths remain authoritative through P4. Only P5 may atomically flip to the package coordinator and remove/disable legacy timers after all adapter and disposable soak gates pass. If P1 requires a Pi host API change, stop this repo's integration at the gate, land and install the source-host change separately, then resume P2.

  • Before installation, require a clean dedicated implementation commit and create a source archive or detached worktree for both that candidate and the pre-change known-good commit. Record stable-mirror/live-extension hashes.
  • Install only through ./install.sh --pi; never edit ~/.pi/agent/extensions, the stable mirror, or installed Pi dist directly.
  • If a disposable live session produces a duplicate turn, silent nonterminal transaction, stale cross-session send, or log privacy violation, run ./install.sh --pi from the recorded known-good archive/worktree, then run scripts/verify-pi-vcc-install.sh. Alternatively create a Git revert of only the dedicated implementation commit; never hard-reset or discard unrelated main-worktree changes.
  • Preserve the failed session JSONL, sanitized transaction log, source hashes, and audit output before rollback.

Non-goals

  • Fixing Pi/provider context percentage accounting.
  • Rewriting pi-vcc summarization, pruning, or recall ranking.
  • Guaranteeing continuation through machine shutdown, process kill, missing credentials, or permanent provider outage; those must fail loudly and resumably.
  • Broad upstream pi-vcc uptake.
  • Turning pi-vcc into a goal/task supervisor.
