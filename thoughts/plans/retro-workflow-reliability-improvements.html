Product-owner context

Recent delivery retros show the same reliability costs recurring across repositories: reviewers sometimes inspect the wrong checkout; long strict suites reveal inherited failures one at a time; temporary test data survives without clear ownership; final PR evidence becomes stale; installer rollback coverage drifts from the files the installer actually manages; and delivery callbacks can accept stale or ambiguously parsed state. These are workflow defects and evidence-quality gaps, not a newly discovered customer-runtime defect in an application.

Why now: the failures appeared repeatedly in the latest delivery reflections, including live-checkout review rejection, 30–40 minute fail-fast reruns, missed committed whitespace, stale plan progress, a changelog placeholder after PR creation, incomplete installer snapshot coverage, and a visible completeness verdict that could not be parsed despite being present in the transcript.

What's new — one bounded reliability path from review launch to install receipt

Promise: a delivery run will detect wrong-checkout review transport before spending reviewer turns, inventory test failures without alert storms, keep scratch data bounded and attributable, validate the final committed candidate, install from one managed-surface contract, and reject stale delivery evidence with actionable diagnostics.

  • Before: prose requires live checkout provenance, but the effective reviewer transport can still isolate; long suites fail one item at a time; final checks are scattered; installer surfaces are duplicated; ledger writes share a launch-only lock; transcript acceptance returns one generic mismatch.
  • After: deterministic preflights expose effective reviewer isolation and provenance; run-plan defines partitioned and bounded failure collection; final PR checks cover committed diff, plan progress, base freshness, and placeholders; installer mutation/rollback/verification share one manifest; all ledger writers use atomic revision-checked transactions; transcript rejection explains exactly what matched and what did not.
  • Observable result: operators receive compact pass/fail summaries, ownership/lock diagnostics, host-deduplicated install receipts, and precise next actions instead of repeated expensive reruns.
  • Planning result: the mandatory standalone eight-answer Socratic section is replaced by a conditional evidence checkpoint whose useful questions live in existing contract, acceptance, verification, decision-attention, and deviations sections.
  • Preserved guarantees: one active-harness reviewer, no implementation subagent, guidance-not-gates for advisory evidence, explicit implementation approval, foreign-file preservation, transaction rollback, and visible Grok completeness review remain unchanged. Deterministic defaults constrain agents, not operators: an operator may explicitly approve a documented exception, while an agent may not silently waive or override the process.

Goal

Create one cohesive reliability upgrade for the existing reviewed-plan → implementation → review → verification → PR workflow. Consolidate overlapping mechanisms rather than adding competing runners. The PR must cover reviewer provenance, bounded test evidence, installer transactions and transport, delivery-ledger concurrency, transcript diagnostics, final candidate checks, fixture setup consistency, and removal of the low-value universal Socratic prose block in favor of evidence placed where reviewers use it.

Locked contract details

Managed-surface manifest v1

scripts/pi-review-stack-managed-surfaces.json is a JSON object with exactly schemaVersion: 1 and surfaces: []. Every surface object requires id (stable unique string), kind (exact-directory, overlay-children, file, json-merge, symlink, or remove-set), source (repo-relative string or null only for removals/links), destination (HOME-relative template using only ${PI_AGENT_DIR}, ${SHARED_SKILLS_DIR}, ${AGENT_SCRIPTS_DIR}, or ${LOCAL_BIN_DIR}), scopes (non-empty array containing pi-review-stack and optionally full), mode (preserve or a four-digit octal string), preserveUnlisted (boolean), and rollbackBoundary (HOME-relative path). symlink additionally requires targetSurfaceId; remove-set requires sorted entries. Unknown fields, duplicate IDs/destinations, absolute or parent-traversing paths, unsupported variables, and rollback boundaries that do not contain their destination fail before mutation.

The initial manifest must enumerate these current families rather than hiding them behind another list: repo-owned prompt children, extension children, library children, exact agent directory, model/settings JSON merges, Pi README, APPEND_SYSTEM, retired/disabled extension removals, shared skills autoreview, claude-code-review, codex-review-partner, delivery-run, pre-pr-implementation-review, reviewed-html-plan, and run-plan; scripts review_orchestration.py, git-with-index-lock, ensure-git-with-index-lock, and delivery; and the three matching ~/.local/bin links. install.sh, transaction snapshot/restore, verifier, and tests must expand this same manifest and may not maintain a second independent list.

Install summary v1

--summary-json <path> is optional. When supplied, the installer writes one JSON object atomically through a mode-0600 sibling temporary file followed by replace. It creates missing parent directories, replaces an existing regular file, and rejects a symlink, directory, or non-regular destination. Once argument parsing succeeds, success and operational failure both attempt a receipt; an invalid receipt path is reported separately. No secrets, environment dumps, or command transcripts are included.

All top-level fields are required. Host records preserve first-seen order after trimming and exact-string deduplication; empty tokens are ignored. exitCode is an integer or null only for skipped work, and warning/reason/snapshotPath are strings or null. Normal non-strict remote failure yields overall partial with process exit 0; strict mode yields failed with non-zero exit. The remote command creates one mktemp -d staging directory, emits its path for the host record, explicitly cds there before invoking herdr/install.sh and kitty/install.sh, and removes it on exit.

Ledger transaction and callback identity

All ledger read-modify-write operations use .delivery/ledger.lock, separate from implementation-launch.lock. The transaction helper opens the lock mode 0600 and attempts an exclusive lock every 50ms for up to 10 seconds (override only in tests with DELIVERY_LEDGER_LOCK_TIMEOUT_SECONDS). The holder writes pid, command name, acquisition time, and expected revision to the lock file. Timeout diagnostics report those fields when readable. Under lock the helper reloads the ledger, requires the reloaded ledgerRevision to equal the caller's supplied revision, applies exactly one mutation, increments once, writes/fsyncs a sibling temp file, atomically replaces the ledger, and releases. A mismatch fails stale with current/supplied revisions; it never silently replays a mutation. The caller may retry by reloading and revalidating intent.

Callback identity is persisted in existing/current fields: implementation callbacks require implementationProfile.launchAttemptId, allowed status, current approval/plan fingerprint, and agent/pane identity; completeness callbacks require completenessReview.requestId, round, status, plan SHA, and worktree fingerprint. Add requestLedgerRevision to each request record for diagnostics. An unrelated note/evidence mutation does not by itself invalidate a current callback. At acceptance time, the transaction reloads under lock and rejects a changed request/attempt ID, round, status, plan/worktree fingerprint, or approval. If a concurrent unrelated write changes only ledger revision between command load and commit, the write fails stale and a retry must revalidate the same callback identity before applying.

Completeness response grammar

A response block starts with COMPLETENESS_REVIEW_RESPONSE_ID: followed by exactly 32 lowercase hexadecimal characters, either on the same line or the immediately following non-empty line. The block runs until the next response-ID label or transcript end. It must contain exactly one VERDICT: value—FINDINGS_TO_RESOLVE, COMPLETE, or BLOCKED_BY_QUESTION—on the same line as the label or its immediately following non-empty line. Other diagnostic lines inside the block are allowed. The parser trims surrounding whitespace but does not join arbitrary tokens or accept partial IDs.

For the current request, the latest block in transcript order is authoritative. Multiple complete older blocks are diagnostic only; a later complete block may supersede them. If the latest current-request block has zero or multiple verdicts, is cut off at the transcript boundary, or is otherwise malformed, acceptance fails closed rather than falling back to an older block. A missing current ID reports visible IDs; a present malformed block reports line range and parsed verdict count; a non-COMPLETE latest verdict reports that verdict; duplicate blocks report their count and selected range. The reader remains bounded to the current 500-line recent-unwrapped window and states when the first retained line appears to continue a block, so possible truncation is distinguishable from a genuinely absent response.

Product intent alignment

  • Golden path: the normal review/install/delivery command detects routine setup and evidence problems before expensive work.
  • Safe defaults: reviewer launch defaults to the live checkout; host lists deduplicate; scratch cleanup affects only owned paths; advisory checks remain non-blocking.
  • Self-healing: ordinary concurrency waits/retries through the transaction helper; successful runs clean owned scratch; install summaries retain warnings without pretending failure is success.
  • Fail closed: stale revisions, mismatched request IDs, ambiguous provenance, symlinked rollback boundaries, unowned scratch, and unsafe rebase/placeholder states stop with a concrete next action.
  • Actionable errors: diagnostics name current/supplied revision, lock owner or PID where available, parser match state, request IDs, paths, host, cwd, and retry command.
  • Operator agency: deterministic paths remain the agent default, but operator-approved, recorded exceptions remain possible. Agents cannot self-authorize an exception or reinterpret an advisory as a mandatory gate.

Locked decisions

  1. Extend existing workflow and installer mechanisms; do not create another review engine, test runner, or delivery service.
  2. Use one checked-in managed-surface manifest as installer mutation/rollback/verification authority.
  3. Add a deterministic no-model transport probe; do not spend a real model call for installer verification.
  4. Keep test execution repository-defined. Run-plan specifies partition discovery, bounded reporting, and merge-base classification rather than shipping a universal cross-language test runner.
  5. Use a blocking ledger transaction lock with revision compare-and-swap and atomic rename for all ledger mutations. Keep the implementation launch lease as an additional narrow writer-ownership boundary.
  6. Keep Amp-only limitations outside code unless an existing maintained integration action is discovered.
  7. Reliability checks govern agent behavior by default. They must not remove an operator's ability to explicitly approve a documented exception; no agent may create or exercise that exception without operator approval.

BDD scenarios

BDD1 — Live reviewer transport

Given reviewer frontmatter says isolation: none and a caller would otherwise request worktree isolation, when the deterministic transport probe resolves the launch, then it reports the live target checkout and no effective worktree isolation before any model call.

BDD2 — Harness isolation fallback

Given the harness still launches elsewhere, when the reviewer returns provenance over TARGET_CHECKOUT, then the coordinator accepts visible-code findings and identifies only genuinely unavailable dirty content.

BDD3 — Bounded failure inventory

Given a long strict suite has several independent failures, when fail-fast is disabled for one bounded inventory pass, then output records distinct failure families up to the configured cap, suppresses repeated alerts, and instructs the agent to reproduce representative failures at the merge base.

BDD4 — Inherited classification

Given a branch and merge base fail with the same signature outside a newly reachable domain, when final disposition runs, then it records inherited evidence instead of consuming repeated full-suite attempts.

BDD5 — Owned scratch lifecycle

Given a test run creates scratch under its declared root with an ownership marker, when the run succeeds, then owned scratch is removed and size/count is summarized; on failure it is preserved with the exact cleanup command. A missing/mismatched marker prevents deletion.

BDD6 — Final committed candidate

Given unstaged checks passed but the committed range contains whitespace or a changelog placeholder, when the pre-PR checklist runs, then PR creation stops with the exact file/line and remediation command.

BDD7 — Managed-surface rollback

Given any managed surface fails after mutation, when the transaction unwinds, then every manifest-owned byte/link/mode is restored and foreign siblings are unchanged.

BDD8 — Host deduplication and cwd

Given KITTY_REMOTE_HOSTS repeats a host, when deployment runs, then that host is contacted once, the remote shell enters the explicit deployment cwd, and the JSON summary contains one host record.

BDD9 — Concurrent ledger writers

Given two delivery commands start from the same revision, when both attempt to commit, then one commits and the other fails stale after acquiring the lock; after the caller reloads and retries, both intended independent mutations can be present, and the ledger is always valid JSON.

BDD10 — Stale completeness callback

Given round one returns COMPLETE after round two was requested, when acceptance runs, then round one is rejected and diagnostics show the visible request IDs and latest verdicts. An unrelated note written after round two does not invalidate round two; a concurrent write during acceptance produces a stale retry rather than accepting against unchecked state.

BDD11 — Explicit fixture axes

Given a workflow fixture declares Hub state, profile/account root, and transport result, when the test runs under a hostile inherited environment, then the declared fixture state controls the outcome; omission is reported as fixture setup failure.

BDD12 — Evidence without duplicate prose

Given a multi-surface plan changes an exact contract, when planning readiness is reviewed, then consumers, siblings, falsification, proof, residual risk, and expansion disposition are found in the contract inventory, acceptance/BDD, verification, decision-attention, and deviations artifacts; a separate Socratic heading is neither required nor accepted as a substitute for those artifacts.
