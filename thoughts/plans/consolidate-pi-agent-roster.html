Product-owner context

Pi currently advertises many narrowly named agents even though most of them perform one of four jobs: implement, plan, research, or review. The duplicated personas bake invocation details such as “PRD dependency lens” or “adversarial plan pass” into permanent agent prompts. That makes routing harder to reason about, duplicates policy text, and allows broad agents such as worker to act as an accidental second implementation route.

Key conclusion: this is an agent-configuration and workflow-governance cleanup, not a customer runtime defect. The correct target is four capability-oriented agents whose durable prompts define authority boundaries, while the driving workflow supplies the artifact, lens, output format, and stop conditions for each invocation.

Goal

Ship a tested Pi configuration with exactly four active repository-owned agents—developer-mid, planner, scout, and reviewer—plus the disabled Explore.md override, with no Pi agent or managed Pi model registration using GPT-5.4.

  • Most review definitions duplicate the same authority, materiality, output, and verdict instructions with only a lens or model name changed.

  • worktree-creator is the only Pi agent on GPT-5.4-mini; the same older models remain in the managed Pi model registry.
  • Several active prompts still hard-code specialized names, and the Codex review policy test enumerates the duplicated reviewer files.

BDD scenarios

BDD1 — Implementation stays medium

Given a bounded code-writing task, when the driving agent delegates implementation, then it selects developer-mid at GPT-5.6 Sol medium, and repeated bounded failure returns a blocker rather than selecting another implementation agent.

BDD2 — Plan details come from the caller

Given an HTML or repository-specific planning workflow, when it invokes planner, then the caller supplies the artifact path and format while the agent enforces planning-only authority.

BDD3 — One scout supports local and web evidence

Given either a local codebase question or an external precedent question, when scout receives a bounded packet, then it uses only the necessary local/web tools and returns the requested evidence format without mutating the repository.

BDD4 — Review lens is invocation data

Given a code, plan, or PRD artifact, when reviewer receives a named lens and verdict contract, then it reports only material evidence-backed findings within that lens and does not broaden scope.

BDD5 — Multi-lens PRD review preserves coverage

Given /review:prd, when the workflow launches its intent, product-principles, security/reliability, scope, and dependency passes, then each independent call uses the same reviewer definition with a distinct caller-supplied lens and output path.

BDD6 — Worktree creation is deterministic and safe

Given /cmd:start-linear-issue NOD-123, when the command runs, then the driving agent validates the clean tree and Linear project, uses branch nod-123 and sibling path <repo>-nod-123, writes the Linear context note, and reports the established success fields. If that path or branch already exists, it stops with the location and recovery choices instead of force-removing user work.

BDD7 — Managed GPT-5.4 entries are pruned safely

Given installed models.json and settings.json fixtures containing the two retired IDs, an unrelated provider, and a custom openai-codex CLI Proxy model, when Pi installation runs, then only gpt-5.4/gpt-5.4-mini and their enabled-model forms disappear while all caller-owned data remains unchanged.

BDD8 — Stale and non-roster workflow references fail the contract

Given a maintained Pi prompt or policy test that reintroduces a retired agent name or routes to a non-roster persona such as researcher, research, explore, general, or debugger, when the roster tests run, then verification fails with the exact stale route identified.
