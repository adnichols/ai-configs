Product-owner context

Situation. Customer screenshots and ZIP files are now being attached to Linear issues. Linear stores those files in private storage, so a naked https://uploads.linear.app/... URL commonly returns HTTP 401. ltui already knows how to fetch that host using its configured Linear credential, but its asset-list output exposes the URL without an equally prominent machine-readable instruction to keep retrieval inside ltui.

Why now. The first customer-issue workflow has already exposed that agents can see a valid-looking URL and attempt a separate fetch. That makes a supported capability appear broken and sends agents toward an unnecessary authentication workaround.

Key conclusion. This is primarily an agent-onboarding and CLI-response gap, not a missing Linear download capability. The change must steer agents from a private upload URL to the existing issues attachments --download-dir flow, while preserving opt-in local downloads and never revealing a credential.

CustomersAgents can reliably retrieve issue evidence such as screenshots and ZIPs instead of reporting a false 401 blocker.

Deployment / migrationNo migration. Ship the ltui release first, then refresh the ai-configs-managed installation; install updated agent skill guidance through the existing Hermes sync process.

What's new — attachment rows tell agents how to fetch private files

Promise: after this change, an agent listing issue attachments can distinguish a private Linear upload from an ordinary direct URL and receives an exact ltui download command instead of treating the raw upload URL as the next action.

Before: attachment rows expose url, and only a non-agent image probe in issues view sometimes supplies an image-specific download command. After: every private upload row has additive, deterministic retrieval metadata, and skills state that the local downloadPath is the handoff to downstream tools. Existing raw URLs, JSON envelopes, filtering, pagination, external link attachments, and opt-in download behavior remain available.

Goal

Make the authenticated attachment-download path the obvious default for agents by adding compact per-row cues in ltui, clear issue-view guidance when an attachment probe is requested, and consistent agent-skill/reference documentation. Prove that the actual request builder uses the configured API key as a Bearer token only for the exact HTTPS private-upload origin and never follows an authenticated redirect.

No product decision required. The user asked for better agent discoverability. This plan deliberately does not auto-download files, make upload URLs public, add a new download subcommand, or broaden credentials to external hosts. Those changes would alter security and local-file behavior beyond the request.

Locked decisions

  1. Use additive per-row cues. For every attachment row, add downloadAccess with value ltui_authenticated only when its parsed URL.origin is exactly https://uploads.linear.app; use direct_url for all other HTTP(S) attachments, including plaintext http://uploads.linear.app and any non-default port. Add downloadCommand only for ltui_authenticated rows; it is an exact issue-level ltui issues attachments … --download-dir command, including --scan-comments when the row came from a comment. Existing fields and raw URLs remain unchanged.
  2. Keep downloading explicit. Listing attachments never creates files. Agents must run the supplied command and then use the reported downloadPath; they must not fetch a private URL separately or expose the configured token.
  3. Make issue-view guidance asset-generic when probing. Preserve current image-specific fields for compatibility, and add generic private-upload download fields only if the user explicitly requests --attachment-probe or non-agent behavior already runs it. Do not enable the probe by default for agent mode, because that would violate current rate-budget behavior.
  4. One request-builder seam owns authorization. Extract a small, pure attachment-download request builder used by downloadToDir. It returns the fetch URL, headers, and redirect policy; it attaches a normalized Bearer token only to the exact HTTPS private-upload origin and uses redirect: "error" for that authenticated request. It has no token in rendered output. This makes the protocol/host/header/redirect contract directly testable without network calls.
  5. Fix stale docs in the same delivery. Every touched example uses positive --scan-comments. The relevant skills say that customer ZIPs are included by omitting --only-images.

Acceptance criteria

  1. A JSON attachment row whose parsed URL origin is exactly https://uploads.linear.app contains downloadAccess: "ltui_authenticated" and a deterministic downloadCommand using --download-dir; the command includes --scan-comments for a comment-derived row.
  2. A non-Linear/external attachment row keeps its raw URL, contains downloadAccess: "direct_url", and has an empty downloadCommand.
  3. The existing image-specific issues view fields remain compatible, and an explicit attachment probe additionally provides a generic private-attachment download cue that covers non-image assets.
  4. The private upload request builder sends exactly one Bearer authorization value only when the parsed URL origin equals https://uploads.linear.app, sends no Linear credential to HTTP, a non-default port, another host, a lookalike, or a redirect target, rejects authenticated redirects, and never exposes the credential in normal CLI output.
  5. Generic and Hermes agent skills instruct agents to use the supplied command or --download-dir, consume downloadPath, include --scan-comments when relevant, omit --only-images for ZIPs, and treat downloaded content as untrusted.
  6. The standalone README and ai-configs architecture/reference docs describe the authenticated private-upload rule and match actual parser/help output.
  7. The standalone ltui test suite, ai-configs documentation checks, and Hermes synchronization checks pass. The installed ltui points at the released revision before agents are told the capability is available.
