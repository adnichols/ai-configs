What this plan is actually doing

Pi's local session files contain enough structured error information to count recurring coding-agent failures, but this repository does not yet contain the analyzer or report contract that an earlier draft assumed existed. This plan therefore starts by creating and locking that small aggregate-only analyzer, then connects its output to the Good Morning report Aaron already reads every day.

Each participating computer produces a small aggregate report before Good Morning. Hermes reads the reports and adds a brief Pi Analytics section to the normal morning report. If the same failure category keeps appearing, the section suggests a human follow-up. Nothing is fixed, reconfigured, delegated, or turned into a task automatically.

Impact areaWhat changes
CustomersNo customer-facing change.
Runtime behaviorHermes adds one read-only analytics section to Good Morning.
Security and permissionsRaw Pi sessions remain on each host. Only aggregate counts move through C-Core.
TestingAdd sanitized analyzer-contract fixtures plus collection, rendering, privacy, failure-handling, host-ownership, and comment-action tests.
DeploymentEnable on mbp and dever in stages. If analytics fails, the rest of Good Morning still runs.

Why now: repeated structured Pi failures such as empty_stream are observable in current local sessions, but there is no durable aggregate contract or morning visibility. This plan creates that small contract and integrates it into the existing daily workflow.

Goal

Every morning, show a concise answer to: “Are the same Pi failures recurring, and is there anything worth looking at?” Use only privacy-safe aggregate data, show at most three suggestions, and keep Aaron in control of every follow-up.

Decisions already made

No further product decision is required. The plan uses the simplest behavior that matches the request.

D1 — Move aggregate reports through C-Core

Each host writes one small daily aggregate report into Aaron's C-Core private space. mbp reads those reports when it builds Good Morning. Raw session files never leave the machine where they were created.

In normal language: dever counts its own Pi failures, mbp counts its own Pi failures, and Good Morning reads the two sets of counts. It does not open or copy the underlying conversations.

D2 — Put the human choice on the Good Morning card

When Good Morning shows a recommendation, Aaron selects that card, enters one of four short commands, and submits it through Doct's routed Agent action. Ordinary conversation comments remain discussion-only. The routed action records what Aaron wants to do; it does not grant Hermes permission to edit code, change Pi, or create external work.

D3 — Collect before Good Morning

Each host runs the analytics collector before the existing 06:00 Good Morning job. Good Morning only reads the finished aggregate reports, so a slow analyzer cannot hold up the morning workflow.

D4 — What the four routed card actions mean

A recommendation card is one item in the Pi Analytics section, such as “empty_stream happened 8 times in 73 sessions on dever.” To act on it, Aaron selects that card, enters one exact command, and submits it with Doct's Agent action. An ordinary conversation comment is discussion only and never changes analytics state.

CommandPlain-English meaningEffect
pi-action acceptThis is worth acting on.Record the signal as selected and show its latest evidence for seven days under “Selected for follow-up.” No task is created automatically.
pi-action investigateI want more evidence before deciding.Record the signal and show its latest evidence for seven days under “Needs investigation.”
pi-action deferNot now.Hide that host/category signal for seven days, even if daily counts change, then allow it to appear again if it still crosses the threshold.
pi-action dismissThis recurring episode is not useful.Hide that host/category while it continuously remains above the threshold. The dismissal resets only after at least one fresh daily report falls below the threshold; a later threshold crossing is a new episode and may create a new card.

Deterministic identity: signal_key = SHA-256("pi-signal-v1\0" + host + "\0" + category). evidence_snapshot_id = SHA-256("pi-evidence-v1\0" + signal_key + "\0" + local_date + "\0" + occurrences + "\0" + total_sessions). The rendered card ID is pi-analytics-card-<signal_key>. Delivery idempotency uses document ID + integer document version + card ID + evidence snapshot ID; display state is keyed by signal_key. These are local display and audit choices only and cannot create Linear issues, Todoist tasks, benchmarks, code changes, configuration changes, or delegated agent work.

D5 — No automatic C-Core cleanup in v1

C-Core plain documents support the create/read path needed for the daily aggregate, but the current supported CLI does not provide document deletion. V1 therefore does not promise or attempt automatic C-Core cleanup. Reports contain aggregate counts only; raw sessions remain host-local.

Automatic retention is a future enhancement only after C-Core exposes a supported lifecycle for this report shape. The collector may prune its own host-local temporary/status files, but it must not claim that C-Core reports were deleted.

Product intent alignment

  • Obvious default: Aaron opens the same Good Morning report and sees one small Pi Analytics section. There is no new dashboard to remember.
  • Safe failure: missing or stale analytics produces a short warning inside the section. It never makes the rest of Good Morning fail.
  • Human authority: analytics may suggest a follow-up, but it cannot perform the follow-up.
  • Privacy: prompts, source, transcripts, credentials, tool arguments, and raw session records never leave their host or enter Doct.
  • Simple recovery: if one host report is missing, name the host and show the exact read-only status command to run on that host. Do not invent a cause.

Acceptance criteria

  1. A versioned analyzer contract exists in this repository, reads only explicit Pi session roots, classifies allowlisted structured errors plus other, and emits aggregate-only JSON.
  2. Each enabled host publishes exactly one schema-valid aggregate report for the completed Denver calendar day.
  3. The report contains aggregate counts only and passes privacy-sentinel tests proving raw prompt, source, transcript, path, credential, and tool text is absent.
  4. Good Morning shows either a no-action status, one incomplete-data warning, or at most three ranked recurrence cards.
  5. Analytics errors are nonfatal: ordinary Good Morning still completes and publishes.
  6. A card action is accepted only from a routed Doct Agent action authored by Aaron on the current Good Morning document/version/card/evidence snapshot. Ordinary comments do nothing, analytics actions never reach the generic Hermes worker, and repeated delivery records one decision.
  7. The four actions have exactly the visible behavior defined in D4 and no authority to create work or change systems.
  8. V1 performs no automatic C-Core report deletion and makes no false retention claim; only collector-owned host-local temporary/status files may be pruned.
  9. Only mbp owns the 06:00 Good Morning/Doct/Todoist/Discord publication path. Component installation on dever adds exactly one collector script/job and no code or cron entry that can publish those surfaces.

What appears in Good Morning

The section is intentionally small and deterministic. The expected report key is the completed America/Denver date at the start of the 06:00 Good Morning run. A host is fresh only when exactly one valid report exists for that host and expected date. Any older date is stale; a future date, duplicate title, schema failure, or unreadable report is invalid. The collector is due by 05:30 Denver; after that point a missing expected-date report is unavailable for that morning.

SituationWhat Aaron sees
One host report is missing, stale, invalid, or unreadableOne warning naming the host and the exact safe next check: run python3 ~/.hermes/scripts/pi_analytics_collector.py --status --json on that host. Do not show recurrence conclusions from partial data.
Both reports are valid but contain zero sessions“No Pi sessions observed for this reporting window.”
A failure category appears at least 3 times and in at least 5% of sessionsA recommendation card showing host, category, count, total sessions, percentage, and the four comment commands.
No category crosses that threshold“No actionable Pi analytics change.”

Rank cards by count and percentage, use a stable tie-breaker, and show at most three. The v1 contract has no before/after comparison payload, so the section must not say “improved,” “regressed,” or “unchanged.”
