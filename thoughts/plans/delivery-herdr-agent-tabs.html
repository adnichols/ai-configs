Give each delivery agent its own labeled Herdr tab

Stop packing delivery agents into ever-smaller same-tab panes. Launch each multi-agent role into its own clearly labeled Herdr tab so humans can read full-height transcripts while agents keep unique names and stable pane IDs.

Product-owner context

When delivery hands work to a second agent (implementation) or opens a visible completeness reviewer (Grok), Herdr currently splits the current tab into panes. Each new agent shrinks every window on that tab. Operators cannot comfortably read transcripts, and the workspace feels crowded even though only a few agents are running.

Why now: delivery intentionally launches multiple agents in one worktree. The pane-split default is now a daily readability problem rather than a rare edge case.

Key conclusion: this is an operator-tooling UX defect in the delivery/Herdr integration, not a customer product bug. Fix by launching each multi-agent role into a full-size labeled tab inside the same workspace, while keeping agent names and pane IDs as the machine identity.

Deployment / migrationNot applicable beyond shipping the skill/script changes in ai-configs. No data migration. Existing in-flight ledgers that already recorded a split pane keep working via stored paneId.

What's new

Headline: multi-agent delivery roles get their own full-height labeled tabs.

Promise: approving implementation or starting completeness review no longer shrinks the planning/driving tab; each agent opens in a clearly labeled sibling tab you can switch to full-size.

Before

  • herdr pane split … --direction right for implementation and completeness agents
  • All agents share one tab; panes get narrower with each launch
  • Docs say “adjacent pane”

After

  • herdr tab create --workspace … --label … --cwd … --no-focus
  • Each role has a human-readable tab label; agent name remains the control target
  • Docs/tests/supervise guidance say “labeled tab”

Preserved: unique Herdr agent names, --no-focus so the operator is not yanked away, worktree cwd, model pins, authorization gates, completeness request IDs, and ledger fields that already store paneId.

Goal

Change delivery’s multi-agent Herdr layout from same-tab pane splits to clearly labeled per-agent tabs so humans can read each agent full-size while agents remain uniquely addressable by name (and still record the pane/tab IDs needed for start/prompt/read/accept).

No blocking product decision. Tab-create response shape was verified live against Herdr 0.7.5: result.root_pane.pane_id and result.tab.tab_id. Label format and scope of the supervise skill are locked below with recommended defaults.

Why this exists

Delivery intentionally runs multiple agents (planner → dedicated implementer → visible completeness reviewer). Pane splits were a convenient default when Herdr guidance preferred sibling panes, but they fight human readability once more than one helper agent is open. Tabs preserve full viewport height and match how operators already navigate Herdr workspaces.

Product intent alignment

Delivery doctrine already prefers visible, resumable multi-agent work without hard-blocking operators. Full-size labeled tabs improve visibility without changing authorization boundaries (Sol-medium implementation handoff, completeness COMPLETE accept). Guidance remains “guidance not gates” for advisory evidence; launch topology is operator UX, not a new gate.

Locked decisions

  1. Topology: create a new tab in the same workspace; do not open a new workspace per agent.
  2. Focus: keep --no-focus so background launches do not steal the operator’s current tab.
  3. Cwd: new tabs use the delivery worktree root (--cwd), same as today’s split.
  4. Identity: Herdr agent name remains the primary control target for start/prompt/wait/read. Pane ID is still required by agent start --pane. Tab ID is recorded for humans/debugging and optional rename, not as a replacement for agent names.
  5. Labels: impl · <baseTitle>, complete · <baseTitle>, and for supervise docs supervise · <base or worker>, truncated with the existing short-label helper if needed.
  6. Storage: persist tabId alongside paneId on implementation profile and completeness review records. Do not store agent tab IDs in labels.herdrTabId.
  7. Rerun: completeness --rerun continues to reuse the recorded reviewer pane/agent; do not create a second tab on rerun.
  8. Workspace resolution: prefer resolve_herdr_targets().workspaceId; if missing, herdr pane get <source_pane> and read result.pane.workspace_id. Fail with an actionable error if still unknown.
  9. Failure contract: missing workspace after pane-get, missing root_pane.pane_id, missing tab.tab_id, or non-JSON herdr output → die with agent-legible text stating what failed, what was tried, and the next action (supply --pane / restore Herdr workspace context). Never fall back to pane split.
  10. Scope includes supervise docs: update supervise skill to the same tab pattern for consistency (manual skill, not delivery CLI).
  11. No auto-close: do not close agent tabs automatically when stages advance; leave cleanup to the operator/Herdr.
  12. Tests-first sequencing: each production change phase writes its failing CLI tests before production code; Phase 4 is full-suite + corpus only.

Acceptance criteria

  1. Implementation launch (approve-implementation / start-implementation) creates a labeled tab via herdr tab create and starts Pi in that tab’s root pane — no pane split.
  2. Completeness review production launch creates a labeled tab and starts Grok Pi on its root pane; --rerun reuses the existing reviewer without a second tab create or agent start; --dry-run documents the tab-create contract as a supplementary check only.
  3. Tab labels are human-readable role labels (impl · … / complete · …); agent names remain unique and used for prompt/read.
  4. Ledger records both paneId and tabId for launched agents; primary labels.herdrTabId is not overwritten by agent tabs; phase workspace rename still targets the primary delivery tab/workspace.
  5. Docs and prompts that instruct delivery multi-agent launch describe labeled tabs, not adjacent pane splits; supervise skill matches.
  6. skills/delivery-run/tests/test_delivery_cli.sh passes with fakes updated for tab create and the named coverage matrix below.
  7. Workspace discovery failures, missing root_pane.pane_id/tab.tab_id, non-JSON (or non-object JSON) herdr output for pane get/tab create, and incomplete responses die with actionable errors and never fall back to pane split or start an agent without a pane id.

BDD scenarios

BDD1 — Implementation agent opens in a labeled tab

Given a delivery ledger at EXECUTION_READY with current readiness/approval prerequisites
And HERDR_PANE_ID / workspace targets are available
When the operator runs delivery approve-implementation
Then delivery invokes herdr tab create with the worktree cwd, workspace id, --no-focus, and an impl · label
And starts the pinned Sol-medium Pi agent on the returned root pane id
And records implementationProfile.paneId and implementationProfile.tabId
And does not call herdr pane split

BDD2 — Completeness reviewer opens in a separate labeled tab

Given a delivery worktree ready for completeness review
When delivery completion-review runs (not --rerun)
Then a complete · labeled tab is created and the Grok Pi agent starts there
When delivery completion-review --rerun runs
Then no new tab is created and the recorded agent/pane is prompted again

BDD3 — Primary tab phase labels stay independent

Given the planner tab id is stored in labels.herdrTabId
And an implementation agent tab was created
When delivery stage advances and maybe_herdr_label runs
Then the workspace/primary tab rename still targets the planner delivery tab
And the implementation tab keeps its impl · label

BDD4 — Docs no longer teach pane splits for these launches

Given the skill and prompt corpus for delivery/run-plan/supervise
When an agent follows the documented launch path
Then it is instructed to create a labeled tab (or call delivery which does)
And not to split the current pane for implementation, completeness, or supervise helpers

BDD5 — Fail closed without pane-split fallback

Given a delivery launch that needs a new agent tab
When workspace id cannot be resolved (targets empty and pane get fails)
Or pane get / tab create returns non-JSON or a non-object JSON root
Or tab create returns JSON missing root_pane.pane_id or tab.tab_id
Then the command exits non-zero with an error naming the failed step, discovery tried, and next action
And the herdr command log contains no "pane split"
And no agent start is attempted without a pane id
