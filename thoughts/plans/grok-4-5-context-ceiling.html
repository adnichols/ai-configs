Grok 4.5 pi-vcc Context Ceiling

Force pi-vcc compaction at 180,000 estimated tokens and block outbound opencode/grok-4.5 provider requests at or above 200,000 tokens.

Product-owner context

Situation. Pi advertises opencode/grok-4.5 as a 500K-context model. Repo-managed percentage-compaction.ts uses one 80% hard backstop for every model, so Grok 4.5 auto-compaction starts around 400K. That is far above the requested 180K operating limit.

Why now. Grok 4.5 is enabled in operator settings and the current percentage-only policy cannot express an absolute 180K trigger or a hard 200K outbound-request stop. Pi 0.82.1 exposes before_provider_request (payload rewrite only) and context (message transform only), but not a documented synchronous cancel-and-compact result at dispatch time.

Key conclusion. This is an operator/runtime configuration defect, not a customer-application bug. The fix requires a shared Grok policy in ai-configs plus a minimal Pi-core pre-dispatch gate so “never above 200K” applies to outbound provider requests, not merely to stored transcript size.

What's new

Grok 4.5 gets an absolute context ceiling instead of a shared 80% backstop

Promise: Operators using opencode/grok-4.5 get deterministic pi-vcc compaction at 180K and a hard stop before any Grok provider request reaches 200K.

  • Before: Grok 4.5 inherits the universal 80% policy (~400K trigger on a 500K window) and may dispatch oversized requests after large tool results because extension hard compaction is deferred through setTimeout(..., 0).
  • After: Exactly opencode/grok-4.5 uses absolute 180K/200K policy values, advertises a 200K model window, triggers pi-vcc at turn boundaries without the zero-delay deferral, and Pi core refuses or compacts synchronously before dispatch when the rebuilt request would still be ≥200K.
  • Observable result: /compact-status and status notifications show Grok-specific thresholds; real-host validation records every outbound Grok request as strictly below 200K.
  • Preserved: Non-Grok models keep 60%/75% nudges and the 80% pi-vcc backstop; pi-vcc summary, recall, redaction, and continuation semantics stay unchanged.

Goal

For sessions whose active model is exactly provider opencode and model ID grok-4.5:

  1. Pi requests pi-vcc compaction when estimated request context reaches 180,000 tokens.
  2. Pi must not dispatch a Grok 4.5 provider request whose estimated context is 200,000 tokens or more.

Scope boundary: The guarantee applies to the outbound provider request. Persisted raw JSONL entries may briefly exceed 200K before the next dispatch boundary; those bytes are not sent to Grok once the gate compacts or fails closed. Arbitrary input/tool-output truncation to cap stored transcript size is out of scope.

Decision attention / low-confidence areas

D1 — Locked: two-track delivery (2026-07-27)

Decision: Ship ai-configs policy/tests in this repo and a minimal upstream Pi-core pre-dispatch gate in parallel. Do not claim production hard-ceiling compliance until both land and the real-host Grok scenario passes on an installed Pi build.

Why: Extension-only changes cannot prove fail-closed dispatch because Pi 0.82.1’s before_provider_request only replaces payloads and hard pi-vcc scheduling currently uses setTimeout(..., 0). Pi already runs _checkCompaction after assistant responses and before user prompts, but not synchronously before every in-turn LLM call after large tool results.

Distribution path for Pi core: Minimal PR to @earendil-works/pi-coding-agent (agent-session request path). Do not hand-edit global node_modules.

Low confidence resolved: Installer retirement removes bare grok-4.5 and grok/* entries but preserves provider-qualified opencode/grok-4.5; add a regression test to keep that true.

Why this plan exists

Operator request: use pi-vcc so Grok 4.5 never sends provider requests above 200K and compacts reliably at 180K. Current repo policy and Pi 0.82.1 dispatch semantics cannot meet that invariant without the changes below.

Current implementation reality

  • HARD_AUTO_COMPACTION_PERCENT = 80 in percentage-compaction.ts; Grok hard trigger ≈400K today.
  • Hard pi-vcc path uses schedulePiVccCompaction → setTimeout(..., 0).
  • ctx.getContextUsage() is null immediately after compaction until a post-compaction assistant response.
  • Pi native threshold uses contextTokens > contextWindow - reserveTokens (default reserve 16,384).
  • session_before_compact in pi-vcc already supplies deterministic summaries; reuse that path.
  • install.sh strips retired bare grok/* models but not opencode/grok-4.5.

Locked decisions

  1. D1: Two-track delivery — ai-configs policy/tests plus upstream Pi pre-dispatch gate (see #decision-d1).
  2. Policy identity: Exact provider/model pair opencode / grok-4.5 only.
  3. Thresholds: Trigger 180,000; ceiling 200,000; single typed source in shared policy module.
  4. Model window: Override advertised contextWindow to 200,000 for Grok 4.5; cap maxTokens to leave headroom (default 8,192 unless P0 reserve contract requires otherwise).
  5. Grok hard trigger scheduling: For Grok at/above 180K, call triggerCompaction directly; do not use schedulePiVccCompaction / zero-delay timer.
  6. P0 compaction handshake: Pi P0 uses compaction reason: "context_ceiling" with willRetry: true when interrupting an in-flight turn; extension session_before_compact must treat context_ceiling like overflow (never cancel for sub-80% percent) and must not cancel while the gate owns the attempt.
  7. Canonical request estimate: One exported function in the policy module estimates post-transformContext provider input as trailing-aware message tokens plus configured output reservation; P0 gate and P4 recorder both call it.
  8. Legacy Grok routes: Bare grok/* and unqualified retired IDs stay removed; explicitly configured opencode/grok-4.5 is supported.

Acceptance criteria and BDD

  1. At 179,999 estimated Grok tokens, the special hard trigger does not run. At 180,000 it requests pi-vcc compaction exactly once per dedupe rules.
  2. Every observed Grok 4.5 provider request is strictly below 200,000 estimated tokens, including a tool-output jump from below 180K to above 200K.
  3. Successful compaction rebuilds context and resumes through the existing continuation protocol.
  4. No-safe-cut or compaction failure at the ceiling produces no Grok provider call and an actionable operator message.
  5. Non-Grok models retain 60%/75%/80% behavior unchanged.
  6. Model switch resets Grok-specific dedupe/latch state.

BDD

  • G1: Grok at 180K with valid cut → next request compacts first; provider input <200K.
  • G2: Below 180K then large tool result → pre-dispatch gate compacts; recorded input <200K.
  • G3: Ceiling with no legal cut → no provider call; operator told to start new session.
  • G4: pi-vcc failure at guard → fail-closed; no retry loop.
  • G5: Non-Grok at same absolute count → percentage policy only.
