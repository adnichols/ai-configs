Pi VCC Compaction Race Recovery Plan

A narrow plan to make pi-vcc/percentage-compaction recover safely from cancellation and race failures without becoming a task tracker or workflow supervisor.

Goal

Fix pi-vcc and percentage-compaction so compaction failure, cancellation, and observed Pi-core race conditions do not strand execution, without adding task tracking, goal interpretation, or broad workflow state.

Target invariant: if pi-vcc attempts or intercepts compaction during an in-flight turn, it must either compact safely or fail/decline safely while preserving Pi’s normal ability to continue the same turn.

Non-goals

  • Do not make pi-vcc track whether the user’s broader task is complete.
  • Do not inspect goals, todos, Linear issues, PR state, or app-specific workflow status.
  • Do not broaden the fix into context-percentage accounting or footer/UI rendering.
  • Do not force unsafe cuts or mark failed/no-op compactions as successful.
  • Do not add multi-turn supervision beyond compaction-local recovery.

Core diagnosis to fix

  1. pi-vcc/percentage-compaction triggers or intercepts compaction at a turn boundary.
  2. Pi core may already be entering auto-compaction.
  3. pi-vcc cancellation/defer paths return { cancel: true }.
  4. Pi core/UI renders that as Compaction cancelled.
  5. Concurrent/manual ctx.compact() can overlap with core auto-compaction.
  6. Pi core can re-read a mutable abort controller after an await and throw Cannot read properties of undefined (reading 'signal').
  7. No pi-vcc continuation is delivered because there was no successful session_compact.

The problematic path is not “agent unfinished work” in general. It is specifically compaction attempting to interrupt or gate a turn and then failing/cancelling without restoring normal continuation.

Design principle

Compaction is best-effort context maintenance. A failed, cancelled, or declined compaction must be recoverable at the turn boundary. pi-vcc may remember only enough local compaction context to resume the turn it interrupted.

Progress

P1 — Add single-flight compaction ownership in percentage-compaction.ts

Prevent pi-vcc from scheduling or starting overlapping compaction attempts while core auto-compaction is already entering a compaction path.

type CompactionOwner = "pi-vcc" | "core" | undefined;

let activeCompactionOwner: CompactionOwner;
let scheduledPiVccCompaction: ReturnType<typeof setTimeout> | undefined;

Rules

  • If pi-vcc has scheduled or started compaction, do not schedule another.
  • If core is already in session_before_compact, pi-vcc must not call ctx.compact() from the same boundary.
  • If pi-vcc decides to defer/cancel core compaction, it should set same-percent backoff so core does not immediately re-trigger.
  • Clear scheduled timers and owner state in every completion, error, cancellation, and skipped-timer exit path.

State table

StateEntryAllowed behaviorExit / cleanup
idle No scheduled or active compaction. turn_end may schedule pi-vcc; session_before_compact may observe core. No cleanup required.
scheduled_pi_vcc turn_end crossed hard backstop and set a zero-delay timer. If core session_before_compact arrives first for the same high-percent boundary, cancel/defer core once with same-percent ratchet and keep the scheduled pi-vcc attempt as the owner. Do not start a second pi-vcc attempt. Timer fires → active_pi_vcc; timer is skipped because owner changed → clear scheduledPiVccCompaction and owner.
core_observed session_before_compact fires while no pi-vcc attempt is scheduled. Apply existing gating policy. If pi-vcc cancels core, ratchet lastAutoCompactionPercent before returning { cancel: true }. If core is allowed, do not call ctx.compact() from pi-vcc at that boundary. On cancel/allow return, clear transient core-observed state. Persistent same-percent ratchet remains until percent changes or a new safe opportunity is detected.
active_pi_vcc The scheduled timer calls triggerCompaction and ctx.compact(). No additional pi-vcc or core-owned attempt may start from the same boundary. Capture exactly one interrupted-turn snapshot for this attempt. On success, error, cancel, no-safe-cut, or terminal delivery failure, call the shared finish routine that clears owner/timer/attempt state.
finishing ctx.compact() completion, onError, no-cut classification, or cancel path begins cleanup. May queue at most one continuation for the attempt if gates pass. Must not schedule a replacement attempt synchronously. Clear owner, clear pending timer handle, clear continuation attempt id, then return to idle.

P2 — Do not call ctx.compact() synchronously from turn_end

Replace direct triggerCompaction(ctx, ...) calls at turn_end with a scheduler that runs on the next tick after Pi core’s own post-turn compaction machinery has had a chance to enter session_before_compact. If core enters first, pi-vcc keeps the scheduled attempt as owner and cancels/defer-ratchets the core attempt exactly once for that same-percent boundary.

const schedulePiVccCompaction = (ctx, options) => {
  if (compactionInFlight || scheduledPiVccCompaction) return false;

  scheduledPiVccCompaction = setTimeout(() => {
    scheduledPiVccCompaction = undefined;
    if (compactionInFlight) return;
    triggerCompaction(ctx, options);
  }, 0);

  return true;
};

This reduces the race surface without depending on broader Pi-core behavior changes. The timer callback must re-check owner state before calling ctx.compact(); if another owner took over, it must clear the timer handle and exit without side effects.

P3 — Snapshot “interrupted compaction turn” as compaction context only

When pi-vcc is about to compact or cancel/defer compaction, capture only the local state needed to decide whether a compaction failure should trigger a continuation.

interface InterruptedCompactionTurn {
  interrupted: boolean;
  pendingToolCallIds: Set<string>;
  reason: "hard_backstop" | "compact_context" | "core_deferred" | "compaction_error";
}

Use existing helpers such as isInterruptedAgentWork, outstandingAssistantToolCallIds, isCompletedAssistantResponse, and deliveredToolCallIds. Do not add work/task state.

P4 — Centralize continuation delivery for compaction failures only

Create one helper for recoverable compaction failure/cancel/no-cut paths. This helper becomes the only failure-path continuation authority for each pi-vcc-owned compaction attempt; successful session_compact continuation remains owned by the existing pi-vcc hook.

const queueCompactionContinuation = (
  ctx: ExtensionContext,
  reason: "cancelled" | "failed" | "no_safe_cut",
  interrupted: InterruptedCompactionTurn,
) => { ... };

The helper should send the same kind of model-visible steer pi-vcc already sends after successful active-turn compaction:

pi.sendMessage(
  {
    customType: "pi-vcc-continuation",
    content:
      "Pi-vcc compaction did not complete cleanly, but the interrupted turn should continue. Continue from where you left off; use vcc_recall if needed.",
    display: false,
    details: { compactor: "pi-vcc", reason },
  },
  { deliverAs: "steer", triggerTurn: true },
);

Continuation authority and gates

  • Only queue this if the captured attempt snapshot says compaction interrupted an active tool/assistant turn.
  • Do not queue if the latest assistant response is completed.
  • Do not queue if pi-vcc/core metadata says willRetry and Pi will immediately retry compaction through an existing safe path.
  • Queue at most one continuation per compaction attempt id.
  • Clear the attempt id on session_compact, on new compaction attempt start, or on terminal continuation delivery failure.
  • Preserve the existing pi-vcc-no-cut-continuation behavior as the bounded-retry delivery path; route new failure/cancel classifications into that authority instead of creating a parallel continuation loop.
  • Do not inspect goals, todos, or task status.
  • Do not generate workflow-specific instructions.

P5 — Use continuation recovery on ctx.compact().onError

Change compaction failure handling from a terminal error notification into a recoverable compaction failure. The handler must use the continuation authority from P4, not a second ad hoc pi.sendMessage path.

ctx.ui.notify(
  `Compaction failed: ${err.message}; continuing interrupted turn if needed.`,
  "warning",
);
queueCompactionContinuation(ctx, "failed", interruptedTurn);
finishCompaction();

Special cases

  • Already compacted → route through reason: "no_safe_cut".
  • Nothing to compact (session too small) → route through reason: "no_safe_cut".
  • Compaction cancelled → route through reason: "cancelled" if a turn was interrupted and no continuation has already been queued for the attempt.
  • Cannot read properties of undefined (reading 'signal') → route through reason: "failed"; repeated identical failures from the same attempt must still produce at most one continuation.

P6 — Change session_before_compact cancellation branches to avoid loops

Where percentage-compaction.ts returns { cancel: true }, set same-percent backoff before returning.

lastAutoCompactionPercent = usage.percent;

Apply this to:

  • awaitingPostCompactionAssistantResponse
  • stale auto-compaction percent
  • no-cut retry state
  • repo-managed hard-backstop cancellation
if (awaitingPostCompactionAssistantResponse) {
  lastAutoCompactionPercent = usage.percent;
  ctx.ui.notify(
    "⏸️ Delayed auto-compaction: waiting for the next assistant response after the last pi-vcc compaction",
    "info",
  );
  return { cancel: true };
}

P7 — Preserve successful session_compact continuation behavior

Do not replace the existing successful-compaction path in _pi/packages/pi-vcc/src/hooks/before-compact.ts. It already performs the narrow intended job:

  • detect active-turn compaction,
  • write compaction details,
  • send pi-vcc-continuation on session_compact,
  • suppress continuation when core will retry.

P8 — Optional host race appendix, not required for pi-vcc acceptance

The required implementation path is the repo-owned pi-vcc/percentage-compaction fix in P1–P7 and P9. Do not edit global installed Pi core files as part of this plan unless the user separately approves host hardening.

The observed host race remains useful evidence: installed Pi core currently re-reads mutable compaction abort-controller fields after awaits. If host hardening is approved later, patch the source-of-truth Pi package rather than hand-editing installed node_modules dist files, and ensure the change survives reinstall/update.

const abortController = new AbortController();
this._compactionAbortController = abortController;
const signal = abortController.signal;

Host hardening shape: use the local signal after awaits instead of re-reading this._compactionAbortController.signal, then clear only if the instance still owns that controller:

if (this._compactionAbortController === abortController) {
  this._compactionAbortController = undefined;
}

This appendix is deliberately excluded from the required acceptance criteria so the pi-vcc fix remains narrow and repo-owned.

Test plan

Tests for percentage-compaction.ts

  1. Hard backstop schedules, not immediate-compacts: at 80% on turn_end, assert ctx.compact is not called synchronously, then advance timers and assert one call.
  2. Compaction failure sends continuation: mock onError(new Error("Cannot read properties of undefined (reading 'signal')")) and assert one pi-vcc-continuation with triggerTurn: true.
  3. Compaction cancelled sends continuation when interrupted: mock onError(new Error("Compaction cancelled")) and assert continuation.
  4. Completed assistant response does not continue: latest turn is completed assistant response; assert no continuation.
  5. Core deferred branch ratchets percent: session_before_compact with awaitingPostCompactionAssistantResponse returns { cancel: true }; next same-percent event does not trigger another pi-vcc compaction attempt.
  6. Integrated observed-race regression: in scripts/percentage-compaction.test.ts, use fake timers or controlled callbacks to model an active tool-use turn at hard threshold, pi-vcc scheduling instead of immediate compact, core session_before_compact arriving before the timer and being ratcheted/cancelled exactly once, then the timer/error path producing Compaction cancelled plus two .signal failures. Assert exactly one continuation is sent and subsequent same-percent events do not call ctx.compact again.
  7. No safe cut continues existing behavior: Already compacted and Nothing to compact route through no-cut recovery for interrupted turns without duplicating the integrated failure-path continuation.

Tests for the pi-vcc package

Keep existing active-compaction continuation tests. Add or preserve coverage for active-turn state after canceled compaction so the next successful compaction can continue normally.

Acceptance criteria

  • No repeated visible loop of delayed auto-compaction, Compaction cancelled, and duplicate .signal failures.
  • If pi-vcc compaction fails during an interrupted turn, exactly one pi-vcc-continuation steer is sent with triggerTurn: true for that compaction attempt.
  • If compaction fails after a completed assistant response, no continuation is sent.
  • pi-vcc does not inspect or track tasks, goals, todos, Linear state, PR state, or completion semantics.
  • pi-vcc tracks only compaction-local interrupted-turn state and clears it on every attempt exit path.
  • Successful pi-vcc compaction and vcc_recall behavior are unchanged.
  • The integrated observed-race regression proves delayed core cancellation, cancellation/error handling, duplicate .signal errors, single continuation delivery, and same-percent retry suppression in one test.
  • Host Pi core abort-controller hardening is documented as optional/out-of-scope for this pi-vcc acceptance path unless separately approved.
