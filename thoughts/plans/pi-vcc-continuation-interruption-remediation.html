Product-owner context

Situation: Pi VCC compacts a long-running agent session and injects a hidden continuation message so work resumes. The continuation coordinator added on July 10 records a transaction and tries to prove that the hidden message was accepted, consumed, made progress, and settled. Recent sessions show that the proof model does not match the real Pi host lifecycle.

Why now: the failure remains reproducible after the continuation-guarantee rollout. The last week contains one confirmed silent continuation loss on dever, 31 deadline failures across mbp and dever, repeated false supersession, and two queued transactions activated with only about five seconds left.

Key conclusion: this is a runtime coordination defect plus an observability defect. Most recorded failures are false failures while the agent is still working, but at least one is a real continuation loss that ended the session. Both must be fixed because false terminalization can release later queued work into an active turn and turn monitoring noise into a real interruption.

Goal

Make the normal compaction path self-healing: after pi-vcc interrupts active work, exactly one continuation is durably accepted, the coordinator recognizes active tool-driven progress without a false deadline, queued work receives a full activation budget, unrelated extension status messages do not cancel recovery, and true delivery failures retry safely before ending with actionable evidence.

Decision Attention / Low-confidence Areas

No product decision required. The evidence supports an ai-configs-owned first remedy: use the matching durable custom_message session entry (or matching continuation message_start) as the sole acceptance boundary, then use later correlated lifecycle activity as progress evidence, rather than depending on the void ExtensionAPI.sendMessage() return. A Pi host API change is an escalation gate only if the real-host RED tests prove that durable entry correlation cannot distinguish accepted from lost sends.

Implementation attention: the persistence contract is locked below as protocol version 2 with dual-read/version-2-write compatibility. Do not convert routine continuation recovery into a manual “send continue” workflow, and do not treat arbitrary extension-generated status messages as independent user intent.

Why this plan exists

The July 10 continuation coordinator was designed around an absolute 60-second transaction deadline, message_start consumption, and a void send call. Real sessions show four mismatches:

  1. Pi persists accepted continuation messages as top-level custom_message entries, while the audit and some lifecycle assumptions look for a normal message entry with role custom.
  2. Long continuation work emits assistant toolUse messages for minutes before a final stop, but the coordinator does not count tool-driven work as progress.
  3. sendMessage() returns before the async host prompt completes. A rejected idle prompt can therefore look accepted to pi-vcc while producing no durable continuation entry.
  4. The deadline starts at request creation, so queued requests and active tool work consume the same budget.

Current implementation reality

  • DEFAULT_DEADLINE_MS = 60_000 and the deadline is anchored at transaction creation.
  • submit() persists submitted, calls the void pi.sendMessage(), and then only arms the absolute deadline. It retries synchronous throws, but not a silent async prompt rejection.
  • Consumption requires a matching message_start; persisted custom_message acceptance is not reconciled.
  • Assistant toolUse is ignored by classifyAssistantResult; only stop, error, and aborted are classified.
  • Any non-continuation custom message can supersede an active transaction as independent_input.
  • Queued deadlines are refreshed only after they have already expired. A request activated shortly before expiry receives only its remaining few seconds.
  • The package load marker is a presence flag, not a singleton guard; a second load can register a second coordinator before/without being rejected.
  • The audit aborts on malformed JSONL, does not recognize top-level custom_message continuation entries, and treats copied entry IDs across resumed/forked branches as duplicates.
  • The install verifier uses Bash readarray, which fails on the default macOS Bash used by mbp.

Product intent alignment

  • Golden path: a user starts a long Pi task; compaction is invisible recovery infrastructure and work continues without a manual prompt.
  • Self-healing: silent send loss, temporary host unavailability, queued requests, and aborts are retried safely inside the original workflow.
  • Fail closed: real user input, session replacement, or persistent provider/host failure stops automatic recovery with a durable, actionable outcome.
  • Actionable errors: terminal failure says which phase failed (acceptance, execution, retry, session replacement), what was attempted, and the exact manual recovery action.
  • Repository alignment: update README/validation commands so operators do not rely on the currently broken whole-history audit or macOS-incompatible verifier.
  • UI impact: text-only. Notifications and audit summaries become more precise; no screen or visual design changes.
  • Current/target text evidence: current failures collapse to “continuation failed” plus a generic manual “send continue.” Target output names the failed phase, whether durable acceptance/progress was observed, retry count/backoff, the transaction identifier, and one exact next action only after automatic recovery is exhausted.

Locked decisions

  1. A persisted, transaction-matching top-level custom_message is the current host’s durable acceptance evidence. sendMessage() returning is not acceptance.
  2. Delivery/acceptance timeout ends only when a transaction-matching durable continuation custom_message is persisted or the matching continuation message_start is observed. Tool/assistant lifecycle activity before that boundary is non-authoritative and cannot establish acceptance. Only post-acceptance active work is governed by the separate progress watchdog.
  3. Queue wait does not consume the activated request’s acceptance budget.
  4. Real user input, session replacement, terminal resume policy, explicitly independent/replacement-marked custom messages, known model-driving custom types, and unknown unmarked custom messages supersede fail-closed. Only matching continuation messages and explicitly classified status-only messages are neutral.
  5. Retries use host readiness plus the locked 1_000 ms/2_000 ms schedule; 100 ms rapid-fire retry loops are removed.
  6. The package owns a single coordinator process-wide. Duplicate initialization is idempotently rejected before any handlers are registered.
  7. Audits are branch-copy aware and malformed-line tolerant. Malformed persistence remains a finding, but one bad line does not hide all later evidence.
  8. Raw session content is not committed. Regression fixtures contain only the minimum anonymized entry shapes and identifiers needed to reproduce lifecycle ordering.
  9. A Pi host API change is not required initially. If P1 cannot prove safe acceptance from durable entries, stop and create a separate upstream plan for an awaitable/acknowledged send contract.
  10. Protocol compatibility: introduce protocol version 2 and continue parsing version-1 request, snapshot, outcome, safety-ready, and continuation-message entries. New writes use version 2 only. Version-1 entries are never rewritten in place; reconciliation adapts them in memory and persists a version-2 snapshot only when the transaction next changes or when the active transaction is first rehydrated.
  11. Version-2 lifecycle representation: retain the externally useful lifecycle states, add a non-terminal fail-closed stalled state, and make timing evidence explicit with queuedAt, activatedAt, submittedAt, acceptanceDeadlineAt, acceptedAt, lastProgressAt, progressDeadlineAt, toolStallDeadlineAt, nextRetryAt, and a monotonic phaseEpoch. Milestone timestamps remain immutable once observed; only phase deadlines and retry scheduling fields are cleared when their phase ends.
  12. Clock ownership: createdAt/queuedAt are diagnostic and do not consume the active acceptance budget. Activation records activatedAt; each submission records submittedAt and a fresh acceptanceDeadlineAt; matching durable persistence or matching continuation message_start records acceptedAt and clears the acceptance deadline. Only assistant/tool activity occurring after that acceptance boundary may record lastProgressAt and refresh progressDeadlineAt; pre-acceptance activity is ignored for transaction progress. Retry scheduling records nextRetryAt. Every timer callback must match transaction ID and phaseEpoch.
  13. Version-1 reconciliation: first correlate any durable matching continuation message and later assistant/tool evidence. A version-1 submitted entry with a durable match becomes accepted without resubmission; without a match it receives one fresh acceptance window from reconciliation time. Version-1 consumed/progressed map to accepted/active evidence, retrying maps to a paced retry wait, and terminal outcomes remain terminal. Reconciliation persists the adapted version-2 snapshot before arming a timer or sending.
  14. Locked timing defaults: acceptance must persist within 15_000 ms of each submission; active work without outstanding tools uses a 60_000 ms inactivity window; outstanding tools use a 900_000 ms hard silence ceiling. The existing retry limit remains two retries (three total submissions), with deterministic delays of 1_000 ms then 2_000 ms. These constants are named, logged, configurable only through the existing coordinator test/options seam, and covered by fake-clock boundary tests.
  15. Lost-tool fail-closed behavior: tool start/result or other correlated progress refreshes the tool-stall ceiling. At the 15-minute ceiling, persist stalled, warn once with the outstanding-tool count and exact recovery action, retain transaction ownership, and do not resend or activate queued work. Later correlated progress returns to active; real user input/session replacement may supersede; agent settlement without successful progress follows the normal bounded retry/failure path.
  16. Custom-message intent contract: classify matching protocol continuations first. A non-matching custom message is neutral only when details.piVccInputIntent === "status" or its exact custom type is in the audited status-only compatibility allowlist (initially ad-process:update). Explicit independent/replace-continuation markers, known model-driving types such as vcc-recall, claude-review-completion, and compaction-nudge, and unknown unmarked custom messages supersede fail-closed. The classifier and allowlist live in one tested module; producers must not be inferred from display text.
