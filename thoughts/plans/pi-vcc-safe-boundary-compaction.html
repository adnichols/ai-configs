Pi VCC — Extension-Only Settled-Run Compaction

Remove synthetic continuation entirely. Record semantic compaction intent during a run, compact only after Pi reports the run settled and idle, and let the next genuine user request continue from the compacted context.

Product-owner context

Situation. pi-vcc previously kept work moving after compaction by aborting the current run and injecting hidden continuation messages. Those queued messages could survive Escape and make Pi appear impossible to stop.

Why now. The upstream/fork approach is explicitly rejected. The replacement must work entirely inside ai-configs using only released Pi extension APIs and must never publish or require a third-party Pi change.

Key conclusion. Released Pi cannot let an extension replace the live context inside an active run. Therefore the safe extension-only behavior is to finish the current run normally, compact after agent_settled, and wait for genuine user input. Automatic same-run restart is deliberately removed.

Testing / release confidenceTests prove idle-only compaction, zero synthetic messages, zero extra provider calls, abort quiescence, native retention, and installed parity.

UI impact: text-only interaction guidance. Tool and status messages change from “continue in the same run” to “compact after this run settles.”

Goal

Ship a single-repository pi-vcc implementation that performs semantic maintenance only after a settled run, creates no executable continuation state, requires no Pi fork or patch, and leaves Escape with nothing to drain.

Decision Attention / low-confidence areas

No product decision required. The operator selected the extension-only tradeoff: no same-run context replacement and no third-party Pi change.

Implementation caution. ctx.compact() is aborting when called during streaming. Production code must invoke it only from agent_settled after confirming idle state. Tests must reject calls from turn_end, tool execution, or active streaming.

Why this plan exists

The earlier architecture optimized for automatic continuation after compaction. That requirement caused the queue, persistence, retry, and rehydration machinery responsible for post-Escape activity. This plan changes the contract: context maintenance may happen automatically, but task execution restarts only on genuine user input.

Authority and inputs

  • Released Pi ExtensionContext exposes ctx.compact(), ctx.isIdle(), ctx.signal, and lifecycle events including agent_settled.
  • Released AgentSession.compact() calls abort() first, so it is safe for this design only after the run is idle.
  • Released Pi owns threshold and overflow recovery after agent_end; pi-vcc can customize session_before_compact without taking ownership of retries.
  • The current ai-configs branch already removed the old coordinator but incorrectly depends on requestCompactionAtTurnBoundary; this plan removes that dependency.
  • Repository authority guidance forbids third-party PR interaction without exact operator permission.

Current implementation reality

  1. percentage-compaction.ts calls a fork-only ctx.requestCompactionAtTurnBoundary().
  2. The pi-vcc hook already uses native CompactionPreparation for ordinary retention and retains custom cutting only for explicit keep:N.
  3. The continuation coordinator and most active continuation machinery have already been deleted on the current branch.
  4. Historical continuation records are classified for recall but do not need runtime rehydration.
  5. The deterministic candidate harness previously carried a misleading real-host name. It imports the selected candidate against the installed Pi module surface but manually dispatches callbacks; it must be treated as candidate-contract proof, not real lifecycle proof.

Product intent alignment

  • Golden path: the agent finishes its response; maintenance runs while idle; the user continues normally.
  • Safe default: no extension-generated turn and no hidden work queue.
  • Self-healing: Pi’s native threshold/overflow path remains responsible for urgent recovery.
  • Fail closed: abort, shutdown, session replacement, or compaction cancellation clears pending maintenance.
  • Actionable status: messages state whether compaction was queued for settled idle time, completed, skipped because another compaction already satisfied it, or cancelled by abort.

Locked decisions

  1. No Pi changes. Do not edit, patch, build, install, push, or open PRs for a Pi checkout.
  2. No synthetic continuation. Do not use sendMessage, sendUserMessage, followUp, triggerTurn, timers, persisted transactions, or rehydration to resume after compaction.
  3. Pending intent only. compact_context stores one coalesced in-memory request with reason/boundary/preserve data.
  4. Settled-run execution. Consume the request from agent_settled only when ctx.isIdle() and no abort was observed.
  5. Abort is terminal. An assistant stopReason: "aborted", aborted compaction signal, shutdown, or session replacement clears the request and schedules nothing.
  6. Native compaction satisfies pending intent. A successful Pi-owned session_compact clears the pending request so agent_settled does not compact twice.
  7. Native retention by default. Use Pi’s preparation and firstKeptEntryId; custom user-turn cutting remains explicit keep:N only.
  8. No custom hard-backstop orchestration. Soft/strong nudges may remain, but urgent threshold/overflow handling stays with released Pi.
  9. Historical records are inert. Keep only classification/recall compatibility; no executable legacy path survives.

Acceptance criteria

  1. AC-1 Released Pi only. Production and verification compile/run against the installed released Pi API with no fork-only symbol.
  2. AC-2 No interruption. Calling compact_context does not abort the active response or sibling tools.
  3. AC-3 Idle-only compaction. A pending request invokes ctx.compact() once after agent_settled and only when idle.
  4. AC-4 No automatic continuation. Compaction creates no provider request, custom continuation message, follow-up, or triggered turn.
  5. AC-5 Escape terminality. Abort before settlement or during compaction leaves the session quiescent until genuine user input.
  6. AC-6 No duplicate maintenance. Pi-owned compaction clears a pending semantic request and prevents a second compaction at settlement.
  7. AC-7 Native retention. Ordinary compaction preserves Pi’s token-bounded recent tail and complete tool pairs.
  8. AC-8 Explicit override. /pi-vcc keep:N remains supported and is the only custom cut.
  9. AC-9 Legacy inertness. Historical continuation entries remain recallable but cannot schedule runtime work.
  10. AC-10 Install parity. Source, stable package mirror, live extension, and settings registration agree; source and installed candidate-contract cases pass. Real Pi lifecycle dispatch is not claimed by this harness.
  11. AC-11 Authority guard. Repository guidance explicitly blocks third-party fork PR interaction without exact operator permission.

BDD scenarios

BDD-1 — semantic request during tool work

Given the model calls compact_context alongside or before other tools, when the tool turn completes, then the run continues normally and no compaction starts while streaming.

BDD-2 — settled idle maintenance

Given a pending request and a normally completed run, when agent_settled fires, then one manual compaction starts with semantic instructions and no agent turn follows.

BDD-3 — Escape before settlement

Given a pending request, when the active assistant response is aborted, then settlement clears the request and never calls ctx.compact().

BDD-4 — Escape during idle compaction

Given settled-run compaction is running, when Escape cancels it, then no retry, message, timer, or provider call appears afterward.

BDD-5 — native compaction wins

Given semantic intent is pending and Pi performs threshold or overflow compaction first, when session_compact fires, then the intent is satisfied and settlement does not compact again.

BDD-6 — recent context survives

Given multiple recent conversational and tool turns within keepRecentTokens, when pi-vcc summarizes, then they remain verbatim and paired.

BDD-7 — next genuine request

Given settled-run compaction completed, when the user later submits a real prompt, then that prompt starts the only new provider turn using the compacted session.

BDD-8 — legacy session reload

Given old continuation records, when the session loads, then no coordinator, timer, send, or provider work is created.

Verification strategy

  1. RED: tests fail because the current extension calls the fork-only boundary API and claims same-run continuation.
  2. Lifecycle GREEN: registered events prove pending intent, idle-only compaction, native-compaction satisfaction, and abort clearing.
  3. Negative proof: source search and runtime traces prove no continuation sender, follow-up, trigger, timer, or extra provider request.
  4. Retention proof: actual pi-vcc hook uses native preparation and preserves complete recent tool turns.
  5. Installed proof: scoped install changes only ai-configs-managed surfaces and passes deterministic cases against released Pi.

Residual risk / not examined: a single active run can still grow until Pi’s native overflow recovery intervenes because extension-only semantic maintenance cannot replace live context between provider turns. The deterministic candidate harness manually dispatches registered callbacks and does not prove Pi extension-loader or real lifecycle dispatch behavior. These are explicit limits of the no-Pi-change scope and must not be represented as tested host guarantees.
