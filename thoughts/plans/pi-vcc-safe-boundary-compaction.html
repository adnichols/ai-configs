Pi VCC — Safe-Boundary Compaction Simplification

Move compaction into Pi’s existing between-turn boundary, keep the newest token-bounded conversation verbatim, and delete the hidden continuation queue that can restart work after Escape.

Product-owner context

Situation. Pi compacts long conversations so an agent can keep working within a model’s context limit. The current ai-configs implementation performs compaction by aborting the active run, then creates a durable hidden continuation transaction that injects another turn. That recovery system can outlive the operator’s Escape key and behave like a backlog that must drain before Pi actually stops.

Why now. The failure is recurring and makes the harness feel uncontrollable. Comparison with Pi’s native compaction and Oh My Pi shows that the complexity is not inherent to summarization: ongoing tool work can be compacted after a completed tool turn and before the next provider request, while recent raw messages remain in context.

Key conclusion. This is a runtime architecture defect, not merely a retry-count bug. Pi already exposes a prepareNextTurnWithContext boundary in the installed 0.84.2 agent core. The correct fix is to use that boundary for compaction and remove pi-vcc’s execution ownership.

What’s new — compaction no longer restarts the task

Promise: Pi can compact during ongoing work and keep moving without a synthetic “continue” message, while Escape prevents every further model turn until the user submits new input.

Goal

Replace abort-and-resume compaction with safe-boundary context replacement, align default retention with native token-bounded behavior, and remove every pi-vcc mechanism that can create a post-Escape continuation backlog.

Why this plan exists

The prior sole-authority continuation work made abort-and-restart more reliable, but reliability is not the right target for an unwanted restart. The system now has a large protocol, coordinator, timers, snapshots, audits, and real-host fixtures because compaction is occurring outside the active loop. This plan removes the cause rather than further hardening the recovery queue.

Current implementation reality

  1. compact_context and the 80% hard backstop ultimately call ctx.compact(), which invokes aborting manual compaction.
  2. The percentage extension maintains pending semantic requests, tool-batch/sibling tracking, active-generation inference, interruption snapshots, no-cut retries, and continuation-facade calls.
  3. The package hook infers interrupted work, writes continuation details, queues post-compaction requests, and hands them to a durable coordinator.
  4. The coordinator writes V1/V2-compatible snapshots and manages acceptance, retries, progress deadlines, settlement, reload reconciliation, and loud-failure output.
  5. Pi 0.84.2 already has the essential safe boundary. prepareNextTurnWithContext receives the loop’s current context after assistant and tool-result events have been emitted and persisted, and may return replacement context for the next provider request.
  6. The default pi-vcc cut is more aggressive than native Pi/OMP: it keeps one user turn unless that tail alone exceeds keepRecentTokens.

Product intent alignment

  • Obvious default: context maintenance should be invisible to task execution.
  • Absolute interruption: Escape means no more model turns until new user input.
  • Self-healing: ordinary threshold and semantic compaction complete inside the same run; no manual continue is required.
  • Fail closed: if the active signal is aborted or context replacement cannot be committed safely, discard the run-scoped request and do not create replacement work.
  • Actionable error: a failed compaction reports that the current run was stopped or left unchanged; it never tells the user to drain a continuation queue.
  • Dissonance cleanup: package README, installer checks, tests, and runtime logs must stop describing pi-vcc as a workflow continuation authority.

Locked decisions

  1. Use Pi’s existing between-turn hook. Extend coding-agent’s existing prepareNextTurnWithContext wrapper; do not add another generic loop callback.
  2. Add one request-only extension method. Introduce ctx.requestCompactionAtTurnBoundary({ reason, customInstructions? }): boolean, where reason is the existing "manual" | "threshold" vocabulary. It accepts requests only during an active, non-aborted run.
  3. Keep the request ephemeral. One run-scoped latch is consumed at the next completed turn boundary. It is cleared on consumption, Escape/abort, settlement, reload, session replacement, or new run. It is never persisted and never rehydrated.
  4. Coalesce, do not queue. A semantic compact_context request retains its custom instructions; a later threshold request may make it urgent but cannot replace the semantic request or create a second compaction.
  5. Reuse the active abort signal. Boundary compaction must stop before appending a compaction entry when the run signal is aborted. Escape during boundary compaction aborts both summary work and the agent run.
  6. Use native retention by default. pi-vcc compiles preparation.messagesToSummarize plus any split-turn prefix and returns preparation.firstKeptEntryId. The host’s keepRecentTokens decides the ordinary cut.
  7. Keep explicit keep:N only. The custom user-turn cut remains solely for explicit manual /pi-vcc keep:N; no implicit one-turn policy remains.
  8. No threshold continuation. Continuing tool loops compact before their next provider call. A terminal answer may compact and remain idle. Only core overflow/incomplete-output recovery may directly retry, and that retry must remain within the current AgentSession loop and respect abort/new-input state.
  9. Historical data is inert. Keep only the minimal classifier needed to hide/read old continuation records safely. Delete coordinator rehydration and every writer, timer, retry, activation, and synthetic continuation message.

Acceptance criteria

  1. AC-1 Same-run progress. When a continuing tool loop requests semantic or threshold compaction, the next provider request occurs in the same agent run using the compacted context and without any injected user/developer continuation message.
  2. AC-2 Escape is terminal. Escape before, during, or immediately after boundary compaction results in zero later provider requests until genuine new user input.
  3. AC-3 Native recent-tail retention. Ordinary compaction preserves the configured token-bounded recent tail verbatim; it does not collapse to one recent user turn.
  4. AC-4 Tool integrity. The completed assistant tool call and every matching tool result are persisted before compaction and remain paired after context replacement.
  5. AC-5 Terminal restraint. A completed final answer may be compacted but never causes another provider request.
  6. AC-6 No continuation authority. No ordinary compaction path writes continuation protocol records, queues synthetic prompts, schedules acceptance/progress retries, or rehydrates prior transactions.
  7. AC-7 Explicit override compatibility. /pi-vcc keep:N still applies the requested user-turn cut; all calls without keep:N use native retention.
  8. AC-8 Safe cancellation. An abort during summary generation commits no compaction entry and clears the pending request.
  9. AC-9 Legacy inertness. Existing V1/V2 continuation entries can be loaded and recalled but cannot create runtime work.
  10. AC-10 Install integrity. The scoped installer and verifier deploy the simplified package and extension atomically without requiring deleted coordinator files.

BDD scenarios

BDD-1 — semantic compaction inside a tool loop

Given the model calls compact_context and sibling tools finish, when the turn boundary is reached, then Pi persists the full batch, compacts, replaces the loop context, and issues the next provider request without another prompt.

BDD-2 — hard threshold inside a tool loop

Given usage crosses 80% while tools are continuing, when turn_end fires, then the extension requests one boundary compaction and the same loop continues from the compacted context.

BDD-3 — Escape during boundary compaction

Given summary generation is active, when the operator presses Escape, then the active signal aborts, no compaction entry is appended, the latch is cleared, and no provider request follows.

BDD-4 — repeated Escape has nothing to drain

Given an aborted compaction request, when Escape is pressed repeatedly and all timers/microtasks advance, then the session remains idle with no continuation record, queue item, or new run.

BDD-5 — final answer at threshold

Given the assistant has returned a terminal answer above threshold, when Pi performs maintenance, then the session is compacted and remains idle.

BDD-6 — recent raw context survives

Given several recent user/assistant/tool turns totaling less than keepRecentTokens, when compaction runs, then all of them remain verbatim and only the older region is compiled into the pi-vcc summary.

BDD-7 — one huge turn

Given one turn exceeds the retention budget, when native preparation creates a split-turn cut, then pi-vcc summarizes the prefix and keeps a valid assistant/tool boundary with no orphan result.

BDD-8 — explicit manual override

Given /pi-vcc keep:2, when manual compaction runs, then the last two user turns are preserved even if that differs from the token-bounded default.

BDD-9 — historical continuation data

Given a session containing old pending/progressed continuation snapshots, when the session is resumed, then the entries remain non-model-visible/inert and no timer, send, or provider request is created.

BDD-10 — overflow recovery remains bounded

Given a genuine retryable overflow, when core compaction succeeds, then core retries directly once; Escape or new input before the retry prevents it, and pi-vcc creates no continuation transaction.
