Product-owner context

Situation. The existing pre-pr-implementation-review skill reliably coordinates bounded Codex and applicable Claude Code review before a pull request. Its mechanics are working, but its behavioral contract can more explicitly require concrete evidence, complete first-pass reporting, verification of dependency assumptions, and stronger protection against review-triggered scope expansion.

Why now. The desired review standard is clear: require a concrete failure path, freeze review scope before reviewing, constrain the shape of fixes, report known blockers in one pass, distinguish source review from behavioral proof, verify dependency contracts, and apply release freeze discipline. The user also prefers the shorter autoreview name.

Key conclusion. This is an agent-workflow and documentation improvement, not a customer runtime defect. The repository should keep its existing review mechanics, adopt autoreview as the canonical public skill, retain the old name as a compatibility alias, and integrate only the bounded behavioral rules.

Goal

Make /skill:autoreview the obvious, canonical entry point for the current bounded pre-PR implementation review workflow, improve its review-quality instructions without broadening scope, migrate maintained callers and documentation, and preserve /skill:pre-pr-implementation-review as an indefinite compatibility alias.

Why this plan exists

The current gate already bounds review cycles and prevents optional polish from becoming required work. The useful opportunity is not another reviewer engine; it is a better reviewer contract. The change must improve discovery of concrete in-scope defects while reducing plausible-sounding findings, serial one-finding-per-cycle review, contract assumptions, and release-closeout scope expansion.

BDD scenarios

BDD1 — Canonical command uses the preferred name

Given an agent needs a bounded pre-PR review, when it follows current AGENTS or Pi documentation, then it invokes /skill:autoreview and receives the existing Codex/applicable-Claude review workflow.

BDD2 — Existing automation remains compatible

Given a historical prompt invokes /skill:pre-pr-implementation-review, when the skill loads, then it forwards to the canonical autoreview policy with the same arguments and does not require the operator to repair the command.

BDD3 — Concrete current-path defect blocks

Given a diff exposes a valid supported input to an incorrect path, when a reviewer can show the trigger, reachable path, observable impact, and relationship to the diff, then it reports the finding with existing severity and scope labels and the gate blocks when required.

BDD4 — Speculative hardening does not widen scope

Given a reviewer imagines unsupported future scale or an unrelated architecture improvement, when it cannot demonstrate a current accepted behavior failure, then it omits the finding or records a non-blocking evidenced follow-up rather than changing code or tests.

BDD5 — Review fix would change the contract

Given an accepted finding appears to require a new protocol, config surface, migration, public API, ownership move, or release-process change, when the coordinator classifies the fix, then it stops with an actionable scope/product-decision blocker instead of implementing the broader design.

BDD6 — Reviewer knows more than five blockers

Given a reviewer identifies more than five in-scope P1/P2 findings, when it returns the initial review, then it details the five highest-impact findings and reports the count and failure families of the remaining known blockers rather than releasing them one per later cycle.

BDD7 — Clean source review does not bypass verification

Given source review is clean for a UI, CLI, HTTP, MCP, or generated-artifact change, when the plan requires behavioral proof, then autoreview records the clean review but the caller still runs the required runtime verification before completion.

BDD8 — Dependency behavior is uncertain

Given a finding depends on third-party behavior, when the reviewer or coordinator cannot validate it from authoritative docs, types, or source, then the claim is not accepted as a blocking finding.

BDD9 — Release closeout finds non-blocking design debt

Given a release or hotfix review discovers a maintainability or broader hardening concern, when the current release is not unsafe without it, then the concern remains outside the release change and is not used to widen the branch.

P1 — Canonical autoreview policy

End State

  • explicit stop conditions for contract/protocol/config/storage/migration/release-process expansion;
  • all-known-blocker one-pass behavior with five detailed findings plus overflow families;
  • source-review versus behavioral-verification separation;
  • authoritative dependency-contract verification;
  • release freeze discipline;
  • the existing targeted rereview and three-cycle ceiling.

Work

  1. Copy the current full policy into the new canonical skill, rename its frontmatter and public usage examples to autoreview, and preserve runtime-specific Codex/Pi/Claude mechanics verbatim unless a naming reference must change.
  2. Add a pre-review scope baseline covering task/plan, intended behavior, supported paths, non-goals, owner boundaries, product surfaces, and initial changed files.
  3. Add the concrete-failure evidence threshold to severity/scope rules and the reviewer prompt. A blocker must show trigger/state, reachable path, observable impact, and why the diff introduces or exposes it.

  8. Add release freeze discipline covering release, beta/stable, hotfix, backport, signing, packaging, deployment, and release-infrastructure work. Keep non-blocking design/hardening outside the release lane.
