Decision Attention / Low-confidence Areas

None. The user approved a repo-owned, purpose-built Pi extension that does not use pi-interactive-shell. A later production audit replaced the original session-scoped lifecycle with detached-supervisor durability and persisted recovery.

Goal

Create one claude_review tool that always runs the canonical interactive-tmux Claude launcher invisibly in the background, returns immediately, and notifies Pi exactly once with a validated artifact or truthful infrastructure failure.

Why This Plan Exists

The inner Claude launcher is deterministic, but Pi launch presentation and lifecycle vary between blocking shell calls and interactive-shell foreground/background modes. Reliability requires making the background controller code-owned rather than prompt-owned.

Authority and Inputs

  • User approval in this session.
  • Written design spec at the path above.
  • AGENTS.md repo rules.
  • Pi extension API documentation.
  • Existing canonical launcher, guardrail, tests, install, and verification scripts.

Current Implementation Reality

  • skills/claude-code-review/scripts/claude_interactive_review.py owns tmux, interactive Claude, auth/readiness, extraction, and artifacts.
  • Pi prompts currently tell agents to execute the launcher command directly.
  • pi-interactive-shell is unnecessary because the launcher already owns a real TUI inside tmux.
  • Repo-owned extensions are copied from _pi/extensions by install.sh --pi.
  • Node 26 provides the built-in test runner and TypeScript type stripping for dependency-free core modules.

Product Intent Alignment

  • Golden path: write prompt, call claude_review, continue working, consume completion artifact.
  • Safe defaults: no overlay, no silence kill, fixed launcher and timeouts.
  • Fail closed: missing/malformed output is infrastructure failure, not a clean verdict.
  • Actionable errors: include job, output, stdout/stderr, transcript, and inspect paths where available.
  • No hidden remediation loop or fallback transport.

Locked Decisions

  • Repo-owned extension at _pi/extensions/claude-review/.
  • No dependency on pi-interactive-shell or pi-processes.
  • Argument-array spawn with shell disabled.
  • Review timeout 3600s; outer watchdog 4200s. Smoke timeout 120s; outer watchdog 300s. Outer budgets cover login-shell discovery, auth preflight, TUI readiness, boundary setup, answer timeout, teardown, and margin.
  • No output-quietness timeout.
  • Model/effort remain launcher-owned.
  • Routine session shutdown stops local observation but accepted jobs continue under detached supervisors; explicit cancellation and watchdog timeout reap active jobs.
  • Known direct Pi launcher routes are blocked; non-Pi consumers retain direct launcher access.

Acceptance Criteria

  1. Pi required reviews use only claude_review.
  2. Start returns immediately and never invokes overlay APIs.
  3. Agents cannot choose transport, presentation, model, effort, launcher path, or timeout policy.
  4. Long output silence does not terminate a healthy review.
  5. Completion wakes Pi exactly once with a validated artifact.
  6. Malformed/missing artifacts and nonzero exits fail truthfully without fallback; workflow verdict interpretation remains separate from transport validity.
  7. Routine shutdown preserves accepted work, while explicit cancellation, timeout, and interrupted-supervisor recovery do not leak launcher children.
  8. Source, installed, stress, launcher-regression, and bounded real E2E evidence pass.

BDD Scenarios

Background happy path

Given a valid prompt and output path, when Pi calls claude_review start, then it receives a job id immediately, no overlay opens, and one completion notification identifies a validated artifact.

Healthy silence

Given a fake review that emits no output beyond the old quiet threshold, when it later succeeds, then the job remains running and completes normally.

Misleading success rejected

Given a launcher exits zero without a valid artifact, when completion is processed, then the job is infrastructure failure rather than success.

Classified failure

Given the launcher reports auth, rate-limit, readiness, boundary, or timeout failure, when it exits, then the same classification and recovery evidence are surfaced without fallback.

Concurrent isolation

Given jobs with distinct outputs, when they complete out of order, then each sends exactly one correct notification; a duplicate active output is rejected.

Shutdown safety

Given an active review, when Pi shuts down or reloads, then the detached supervisor continues the job and persists a recoverable terminal state; only explicit cancellation or watchdog timeout terminates the launcher.
