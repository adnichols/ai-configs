Make the Managed Codex Reviewer Safe on macOS

Remove Linux-only process supervision assumptions from the canonical Codex review launcher and Pi extension without weakening identity-safe cleanup, timeout, restart reconciliation, artifact, or notification guarantees.

Product-owner context

Situation: Pi’s required Codex reviewer is managed by a repository-owned extension, but its canonical launcher and cleanup logic were implemented against Linux process facilities. On macOS, the launcher first depended on an externally installed setsid executable and then called Linux-only prctl and /proc. A real required plan review failed before Codex started, even after setsid was made available.

Why now: NOD-1368 and two independent NOD-1367 review jobs all failed with CODEX_REVIEW_LAUNCH_FAILED and dlsym(RTLD_DEFAULT, prctl): symbol not found. The missing review blocked otherwise complete planning work, so macOS support is a current workflow outage rather than hypothetical portability debt.

Key conclusion: this is a defect in the shared Codex reviewer stack, not in the reviewed Heddle plans and not in Codex model output. The fix must cover both the shell/Python launcher and the Pi extension’s process-identity and cleanup layer; changing only PATH or skipping prctl would expose the next Linux-only /proc failure and would not restore the promised lifecycle guarantees.

Goal

Make the canonical managed Codex review path a first-class Linux and macOS capability while preserving the existing reliable-review contract: immediate dispatch after durable state, one validated final artifact, deterministic timeout/cancellation, no surviving reviewer descendants, identity-safe restart reconciliation, and exactly-once eligible completion delivery.

Decision Attention / Low-confidence areas

No product decision is required. The defect and required parity are established by repository policy and live evidence. The technical design is locked below from available OS APIs.

  • High-attention boundary: do not “fix” macOS by merely bypassing prctl, installing Homebrew setsid, or downgrading cleanup to best effort. Those changes leave /proc-based identity and restart logic broken.
  • Validated Darwin capability: macOS exposes proc_listallpids and proc_pidinfo(PROC_PIDTBSDINFO) through /usr/lib/libproc.dylib; proc_bsdinfo includes PID, PPID, PGID, status, and microsecond process start time. Python provides os.setsid() on this host.
  • Review substitution for this plan only: because the defect prevents the canonical Codex gate from running, the requested independent plan review uses the repo’s developer-mid GPT-5.6 Sol medium subagent. This is recorded as an explicit temporary review transport substitution, not a change to maintained review policy.

Why this plan exists

The original managed-review plan correctly required identity-safe process-group cleanup, but its implementation and tests encoded Linux as though it were the host contract. The launcher uses an external setsid, calls prctl(PR_SET_PDEATHSIG), and reads /proc/<pid>/stat plus Linux boot ID. The extension independently reads and enumerates /proc for owner identity, descendant groups, cleanup, and restart reconciliation. Its production-topology and launcher tests also use Linux-only process and GNU stat -c assumptions.

Therefore the complete promised slice is cross-platform process supervision plus regression and installed-host proof. A PATH workaround alone is explicitly incomplete.

Product intent alignment

  • Golden path: codex_review works from Pi on supported Linux or macOS without an operator installing setsid, editing PATH, or knowing the host’s process APIs.
  • Safe inference: the process adapter selects Linux or Darwin from sys.platform/process.platform; callers do not supply a platform flag.
  • Self-healing: routine PATH absence disappears because Python calls os.setsid() directly. The system does not silently install OS packages or mutate PATH.
  • Fail closed: unsupported OS, unavailable Darwin libproc, malformed adapter output, identity mismatch, or unverified cleanup cannot become a review result or a claim that descendants were reaped.
  • Actionable errors: preflight and terminal failures name the platform, missing capability, evidence paths, and whether a rerun is unsafe until cleanup is resolved.
  • Policy continuity: maintained workflows continue using codex_review; no GPT-subagent fallback is added to runtime policy.

Locked decisions

  1. One shared process adapter: add a Python standard-library helper under skills/codex-review-partner/scripts/ that emits a versioned JSON process snapshot. Linux uses existing /proc fields and boot ID. Darwin uses ctypes with /usr/lib/libproc.dylib, proc_listallpids, and proc_pidinfo(PROC_PIDTBSDINFO); boot identity comes from the kernel boot time. Normalize PID, PPID, PGID, POSIX session ID (SID, via os.getsid(pid)), zombie/alive state, and a start identity precise enough to reject PID reuse. Unknown platforms fail explicitly.
  2. No text ps parsing as authority: tests may use ps for diagnostics, but production identity and cleanup decisions use kernel-backed structured adapters. This avoids locale, truncation, timestamp-resolution, and formatting ambiguity.
  3. Maintained Python supervisor: move the embedded supervisor/watchdog logic into a review-skill script that imports the process adapter. The supervisor calls os.setsid() itself before publishing identity, eliminating external setsid. It launches Codex in its private session/group, owns the inner deadline, handles TERM/HUP/INT, and performs TERM-to-KILL cleanup before exit.
  4. Approved custom implementation and dependency evaluation: user authorization to continue executing this reviewed plan covered the locked shared-adapter and maintained-supervisor decisions above, including the archived instruction not to introduce a third-party dependency. Three maintained candidates were evaluated: psutil provides useful cross-platform snapshots but adds a compiled dependency to the system-Python install and does not supply the private-session supervisor, owner-loss monitor, atomic evidence protocol, or verified fixed-point cleanup; supervisor is a daemon/configuration-oriented process manager that would require a separately installed service and does not expose the per-job PID/start/boot/SID reconciliation contract; circus is likewise an external process/watchdog stack with additional runtime dependencies and no direct fit for the repository-owned sidecar, exactly-once terminal state, and in-process Pi lifecycle. Retaining the standard-library implementation keeps the transactional install self-contained and couples the unusual identity protocol to its only consumer. Re-evaluate this exception by January 2027 or sooner if a maintained library provides the complete contract without a host-level service.
  5. Portable owner-loss handling: keep Linux PR_SET_PDEATHSIG only as an optional fast path when available, but make correctness depend on portable identity monitors for both the immediate launcher and the Pi owner process. Before spawning, runtime.ts persists the Pi owner PID/start/boot identity and passes that exact identity through argument-array launcher options into the supervisor. The supervisor snapshots and validates its immediate launcher parent too, then exits through the same verified topology-cleanup path when either the launcher identity or the Pi owner identity disappears or changes. This ensures abrupt Pi loss is detected even while the detached shell launcher remains alive waiting for the supervisor; Darwin receives bounded orphan cleanup without pretending to provide prctl.
  6. Runtime adapter boundary: replace direct /proc reads/enumeration in runtime.ts with a small injected process-inspector interface backed by the shared helper. Tests can inject deterministic snapshots; production uses argument-array execFile/spawn with shell:false. Malformed, stale, mismatched, or unsupported helper results are identity uncertainty, never permission to signal.
  7. Cleanup parity with private-session capture: the supervisor creates one private POSIX session with os.setsid(); its SID is the durable topology boundary. Cancellation, outer timeout, post-spawn persistence failure, graceful shutdown, launcher death, and next-start reconciliation validate the session leader identity, freeze its root group, enumerate every live process whose SID equals the persisted private SID (not only current PID/PPID descendants), freeze every identity-matched group in that session, and re-enumerate fresh session membership until two consecutive snapshots are stable. Reparenting therefore cannot remove a process from cleanup authority. Only after the bounded fixed point may cleanup send TERM, CONT where required, bounded wait, KILL, verify the private session is empty, and publish terminal state. Any SID change, identity change, inspection failure, inability to freeze a session group, or failure to stabilize fails closed with retained evidence.
  8. Identity protocol versioning: bump the process-identity sidecar protocol and include platform, normalized boot identity, leader PID/PGID/SID/start identity, nonce, and adapter version. Runtime accepts old Linux v1 evidence only for safe reconciliation compatibility; new launches write the cross-platform version.
  9. Two-platform release bar: portable fake tests must pass on both Linux and Darwin. Linux-specific assertions remain platform-gated and Darwin receives equivalent real identity, descendant cleanup, PID-mismatch, cancellation, timeout, and restart tests. A real installed macOS smoke plus tiny review is required before the fix is considered complete.
  10. Transactional adoption: source verification precedes bash scripts/install-pi-transactionally.sh. The installer’s existing recursive skill/extension copy is the adoption path; modify install code only if a regression test proves new files are omitted.

BDD scenarios

S1 — macOS golden path

Given Darwin, system Python, a valid Codex session, and no Homebrew setsid on PATH, when Pi starts a smoke or tiny review, then the launcher creates its private session through os.setsid(), publishes Darwin identity, returns running state, and later delivers exactly one validated completion.

S2 — Linux parity

Given Linux and the same request, when the new adapter/supervisor runs, then public artifacts, classifications, lifecycle, and cleanup match the pre-change supported path.

S3 — Cancel and descendant cleanup

Given Codex has a TERM-ignoring descendant, when the user cancels on Linux or macOS, then identity is revalidated, the complete private topology receives TERM then KILL as needed, no member remains, and only then is cancellation delivered.

S4 — Abrupt launcher/Pi loss

Given a running review whose Pi owner disappears without shutdown while the detached shell launcher may remain alive, when the supervisor’s owner-identity monitor detects the Pi PID/start/boot identity loss or change, then it cleans its private reviewer topology and exits within the bounded monitor/deadline contract. The same path applies when the immediate launcher identity disappears. On restart, the extension reports interruption without signalling an unrelated reused PID.

S5 — Reparented group during cleanup discovery

Given a Codex descendant creates a new process group in the supervisor’s private session and its parent exits while cleanup is discovering the topology, when cancellation or timeout runs, then SID-based enumeration still finds and freezes the reparented group and re-enumerates until two consecutive session snapshots are stable before TERM/KILL. If private-session stabilization cannot be proven within the bound, the job reports cleanup uncertainty and retains evidence.

S6 — PID reuse or stale evidence

Given a process now has the persisted PID but a different start identity, boot identity, PGID, or nonce, when cleanup/reconciliation runs, then no signal is sent, evidence is retained, and the job is classified identity-uncertain with an exact next action.

S7 — Unsupported capability

Given an unsupported OS or inaccessible Darwin libproc, when a review starts, then preflight fails closed with platform/capability details and no Codex child or accepted reviewer result.

S8 — Review output contract unchanged

Given a valid final response or malformed/progress-only response, when the process completes on either platform, then the same verdict validation, no-clobber publication, status classification, and completion eligibility rules apply.

Risks and mitigations

  • Darwin struct drift: define the exact public proc_bsdinfo layout, assert returned byte count, and fail capability preflight on mismatch rather than reading partial memory.
  • PID reuse: compare platform boot identity plus microsecond process start identity, PGID, and nonce before every signal decision.
  • Parent monitor race: snapshot expected parent identity before readiness publication, check it again immediately before Codex exec, and use a short bounded monitor interval plus the inner deadline.
  • Cross-group descendants: preserve topology enumeration and evidence-backed group discovery; do not assume every child stays in the supervisor PGID.
  • Helper failure during cleanup: retain evidence and report cleanup uncertainty; never claim success or remove all identity evidence.
  • Live installation regression: use only the existing transactional bounded installer and its rollback/parity gates.
