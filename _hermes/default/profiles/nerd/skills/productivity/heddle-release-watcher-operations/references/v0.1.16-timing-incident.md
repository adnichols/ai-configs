# Heddle v0.1.16 watcher timing incident

Session lesson: do not infer timely autonomous watcher behavior from the fact that a GitHub release exists now.

## Evidence from incident

- PR #93 (`Release v0.1.16 to main`) merge commit: `81e6c0d07df72bca570563e3bc21533113b07bc3`.
- GitHub `gh pr view 93` reported `mergedAt: 2026-05-10T17:43:59Z`.
- Cron output around `2026-05-10_17-42-57.md` still responded `NOOP`.
- Release checkout reflog showed first fetch/fast-forward to `81e6c0d` at `2026-05-10 11:48:42 -0600`.
- Release log `release-20260510-114842-81e6c0d07df7.log` showed build started after that and GitHub release published at `2026-05-10T17:50:00Z`.
- User correction: the release did not happen until the issue was investigated; answering "it did happen" was misleading because it ignored timeliness/causality.

## Fix pattern applied

- Do not let `last_seen_main_sha == origin/main` alone suppress work.
- Compute expected tag from `origin/main:package.json`.
- Only consider release complete when:
  - expected tag points at `origin/main`, and
  - GitHub release exists, and
  - expected installer asset exists.
- Use deterministic scheduler script wrapper instead of an LLM-interpreted cron prompt for release/failure notification.
- Configure cron with `no_agent: true`, `deliver: origin`, and a profile-local script shim.

## Future investigation checklist

1. Check current GitHub release state, but treat it as current state only.
2. Compare PR `mergedAt` with cron output timestamps and checkout reflog/fetch times.
3. Compare release log timestamps and GitHub `publishedAt`.
4. If there is a gap, say so directly. Do not defend the automation just because it eventually completed.
